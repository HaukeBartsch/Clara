# User Interface — Design

**Project:** Clinical Study Management System (REDCap API Replacement)\
**Implements:** `Requirements/User_Interface_Requirements.md`\
**Date:** 2026-09-22

## 1. Purpose and Conventions

Fixes the *shape* of the web UI: the PHP route set, the page inventory, the layout of every page, the components on each page, and the client-side interaction behavior. The requirements document fixes *what* (which views exist and what is gated); this document fixes how they are rendered and how the user operates them.

Not fixed here, and fixed by the documents referenced:

- Data contracts (every request/response shape): `API_Endpoints_Design.md`.
- Value rules, expression grammars, and evaluation semantics: `Data_Validation_Design.md`.
- Session, trust model, login/logout sequences, CSRF: `Authentication_Authorization_Design.md`.
- Persistence (data dictionary, survey links, DAG, i18n tables): `Database_Schema_Design.md`.
- Stack, repository layout, Bootstrap version, CSP: `Technology_Stack_Design.md`.

Common conventions (REQ-UI-001…008), binding on every page:

- **Stack** (REQ-UI-001, REQ-TECH-001): plain HTML + vanilla ES2020 + vendored Bootstrap 5.3.x (CSS + bundle JS only); no frontend framework, no build step. Pages are rendered by the PHP layer, which delegates **all** data access to the API (REQ-TECH-006). Client scripts are ES modules loaded with `<script type="module">`, same-origin, unbundled (REQ-UI-045): `web/assets/app.js` is the shared runtime, and each page additionally loads the module of the logical section it hosts (`web/assets/js/record.js`, `js/setup.js`, …) — §3.7, tree in `Technology_Stack_Design.md` §4. Relative specifiers only, so no import map is needed and the CSP script source stays `'self'` (§3.2, REQ-TECH-020).
- **Browser boundary** (REQ-UI-002, GD-1): the browser talks only to the PHP routes of §2 and never to `/api/v1/*` or the data API directly.
- **Permission gating** (REQ-UI-003, REQ-AUTH-027): a page, section, or action is present **only** when the acting user's effective permissions allow it — "hidden" means absent from the DOM, not merely disabled. Gating is computed server-side at render time; the API re-checks on every call (REQ-AUTH-033), so client-side gating is presentation, never enforcement.
- **Escaping** (REQ-UI-004): stored free-text values are the only content rendered as HTML — and only because they were sanitized to the allowlist at store (`Data_Validation_Design.md` §5.2). **All other** content (choice values, field labels, record names, user names, audit fields, translated strings) is escaped server-side (REQ-TECH-020). The `Content-Security-Policy` header is sent on every response (REQ-TECH-020).
- **CSRF** (REQ-UI-005, REQ-AUTH-037): every state-changing browser request is a `POST` (form or fetch) carrying the per-session `csrf_token` — hidden `csrf_token` form field for forms, `X-CSRF-Token` header for fetch calls.
- **Language** (REQ-UI-008, GD-12): English is the default and fallback; `nb` and `nn` are the first targets. Translations are applied **server-side at render time** — no i18n JavaScript library (REQ-TECH-001); §9 covers how JavaScript-originated messages are translated.
- **Time** (GD-7, GD-16): **system** timestamps (audit, history, account fields) are displayed as UTC, in the `YYYY-MM-DD HH:MM:SS` form the API returns. Clinical date/date-time **values** are displayed **exactly as stored** — canonical form **including the collection timezone offset** (e.g. `2026-03-01+01:00`, `2026-03-01 09:30+01:00`); the UI performs no locale reformatting of stored data and no timezone conversion (resolves ASM-UI-1). When the user enters a date/date-time in the data-entry form, the form submits it as typed (the field's `validation_format`) — for the two default formats through the browser's native date control plus a **now** button (REQ-UI-072, §8.2) — and the browser's timezone is sent as the collection zone (GD-16, REQ-VAL-041 — the PHP layer resolves the browser zone to the offset and passes `tz`).
- **Layout** (master spec, "User interface details"; DEV-UI-14): the left panel belongs to the page that has switchable sections. The signed-in surface has four shells — the **project overview** (`/`) is a single content panel with no left panel; the **project page** (`/projects/{id}…`) carries the project's functions in a left panel and shows the selected one on the right; the **Control Panel** (`/admin`) does the same for the administration sections, and the **account page** (`/account`) for the user's own settings (§2.4). Selecting a section (e.g. *Setup*) renders that page in the right-hand panel. This is a shared multi-page layout, not a single-page app: each route of §2.1 renders the same shell and swaps the panel content (consistent with REQ-UI-001 — no framework). The shells, visual style, and interaction style follow the historic FIONA reference in `assets/table_based_authentication_plus_user_management/` (master spec, "Details"; REQ-UI-032, REQ-TECH-025): left panel + content panel, `table-sm` tables, responsive layout, and a client that populates data regions from JSON — realized in Bootstrap 5.3.x and vanilla ES2020.

### 2.2 Login page (`GET /login`, REQ-UI-007)

- **Source-name picker** (REQ-UI-042, master spec "Authentication order"): the page leads with the distinct set of configured authentication-source names ("Hospital 1", "Hospital 2", … — from `OAUTH2_N_NAMES`, `LDAP_SERVER_N_NAMES`, `LOCAL_LOGIN_NAMES`, REQ-CFG-032) as a radio group, in name order with a name carried by the local source alone (e.g. "Local") placed last (`Auth::sourceNames()`, REQ-UI-042), drawn as a horizontal, wrapping row of square tiles (house icon left, name right; the chosen tile framed in the theme's primary colour, the others greyed out). No name is preselected, and nothing renders below the picker — no credential form, no provider button — until the user chooses one. Choosing a tile submits the choice at once (`login.js`; there is no confirm button, so the login page requires JavaScript — DEV-UI-13); the selection is stored in the session (`auth_source_name`, `Authentication_Authorization_Design.md` §3) and everything below re-renders for it. With exactly one distinct name the picker is skipped; changing the selection clears any entered credentials before re-render (REQ-UI-042).
- **What renders under the selected name** (`Authentication_Authorization_Design.md` §2.9):
  - a single OAuth2 source and no credential sources → PHP initiates that provider's Sequence A redirect directly (REQ-AUTH-066);
  - several OAuth2 sources → one button per provider — "Sign in with `<provider name>`" — each initiating its own Sequence A;
  - local and/or LDAP sources → the **email + password form** (on a first installation without an IdP it is the **only** path, GD-18, REQ-AUTH-051). Submitting dispatches the credential race for the selected name — the local verify of Sequence F and the LDAP binds of Sequence B in parallel, first "login ok" wins (`Authentication_Authorization_Design.md` §2.9) — there is no sequential fallback to present or to wait through. The password travels only browser→PHP (TLS) and PHP→the sources under the selected name; it is never stored in plaintext and never logged (REQ-AUTH-036, REQ-AUTH-063).
- **"Forgot password?"** — a translated link beside the form to `/password-reset` (§2.6, GD-23, REQ-AUTH-062). Meaningful only for local accounts; the request page answers generically so the link discloses nothing.
- Failure presentation: a single translated error line per the API reason — provider unavailable / state mismatch / **bad password** / bad credentials (LDAP) / **account disabled** (incl. "disabled after inactivity — an administrator must re-enable") / **account expired** ("validity period ended — an administrator must extend it") — no internals. Rate-limit rejection (429) shows the lockout duration (REQ-AUTH-035).
- **Two-factor step** (GD-21, REQ-UI-038): on 401 `mfa_required` the page switches to a second panel — one code field with method-specific help ("Enter the code from your authenticator app" / "We sent a code to your email address" + a resend action, rate-limited) and an "use a recovery code" toggle. PHP holds the first-factor success in the pre-auth `tfa_pending` session (`Authentication_Authorization_Design.md` §2.7); no other page is reachable while it stands. 401 `bad_mfa_code` re-shows the panel with the failure line; on success the response completes the login exactly as without a second factor.
- **Mandated enrollment** (GD-21, REQ-AUTH-059): on 401 `tfa_enrollment_required` (`AUTH_REQUIRE_2FA` on, account has no method) the page shows the enrollment wizard of §2.5; completing it resumes the login.
- Ended sessions (`Authentication_Authorization_Design.md` §3.1): any request whose session has ended redirects to `/login` — with `?next=` for a page request, so signing in returns there — and the login page shows one translated line saying why: idle (`session.ended.idle`), past its absolute lifetime (`session.ended.expired`), revoked because the account changed (`session.ended.revoked`), or ended everywhere after a replayed session id (`session.ended.replayed`, a danger alert that asks the user to tell their administrator if it repeats). A data request (`Accept: application/json`) answers 403 `forbidden` instead, which the client treats as "session over" (REQ-UI-007, REQ-AUTH-015/073/074).

### 2.3 No-access page

A user who is neither an administrator nor a member of any project MUST be shown an information page, not an empty dashboard (REQ-UI-006, REQ-AUTH-028). Presentation:

- Title: "No projects yet" (translated); a short explanation that access is granted when an administrator adds them to a project (or grants the administrator flag).
- `is_admin` users never see this page: they see every project (REQ-API-049), so an empty list only means the installation has no projects yet, and the project overview (§4) renders with its empty grid; the header's Control Panel button is the way to create one (§2.4, §5.2). Owner decision 2026-10-03.
- The page renders as the single content panel of the project-overview shell (§2.4 A) — no left panel.

### 2.4 Application layout — the shells (master spec, "User interface details"; DEV-UI-14, DEV-UI-18)

Every authenticated page renders in one of the shells below, and **a left panel appears only where it switches between sections** (REQ-UI-046). All share the header described here; there is no footer (DEV-UI-18).

```
┌───────────────────────────────────────────────────────────────────────────┐
│ header  CLARA · <project name>   [ Training ] [ Control Panel ] [Name ▾]  │
├───────────────────────────────────────────────────────────────────────────┤
│                                                                           │
│  A · project overview (`/`)      B · project page, Control Panel, account │
│  ┌────────────────────────────┐  ┌────────────┬───────────────────────┐   │
│  │  single content panel      │  │ left panel │    content panel      │   │
│  │  boxes sized by recent use  │  │ Overview   │   the selected        │   │
│  │  first + largest (§70/71)   │  │ Setup      │   section's page —    │   │
│  │                            │  │ Record …   │   its own headings,   │   │
│  │  no left panel             │  │ Export …   │   forms, tables       │   │
│  └────────────────────────────┘  └────────────┴───────────────────────┘   │
│                                                                           │
└───────────────────────────────────────────────────────────────────────────┘
```

- **Header** (all shells): the brand (`CLARA`, linking to the project overview `/`) and, inside a project context, that project's name linked to its Overview (`/projects/{id}/overview`) as a breadcrumb. On the right, for every signed-in user, the **Training** link → `/training` (§2.7, REQ-UI-059), beside it, for `is_admin` users only, the **Control Panel** button → `/admin` (REQ-UI-009/047) — absent from the DOM for every other user (REQ-UI-003); nothing else administration-related appears in the header — and last, for every signed-in user, the **account menu** (REQ-UI-063): a dropdown button carrying the user's display name (cut with an ellipsis when long) whose menu offers **Account** → `/account` (§2.8) and **Sign out** (`POST /logout`, CSRF token, REQ-UI-007), so signing out stays one click away on every page. The menu is user-scoped rather than project-scoped, so it sits in the header and stays put while a panel changes.
- **A · Project overview** (`GET /`, §4): one content panel below the header with **no left panel** — the first screen after login is information about the projects, not navigation (REQ-UI-009).
- **B · Left-panel shells** — the **project page** (§6.1), the **Control Panel** (§5) and the **account page** (§2.8). The left panel lists that page's sections as links in its canonical order; the current one is marked `active`. Selecting an entry loads the corresponding page in the right-hand panel (master spec): mechanically plain navigation — a `GET` to the route of §2.1 rendered into the same shell, with no client-side page switching and no SPA (REQ-UI-001). An entry whose permission the acting user lacks, or whose section this build does not serve, is absent from the panel rather than disabled (REQ-UI-003).
- **No footer** (DEV-UI-18): what the footer carried — the language and theme selectors, the two-factor and password links, the user's name and Sign out — lives on the account page (§2.8) and in the header's account menu.
- **Responsive collapse** (REQ-UI-008): below the Bootstrap `lg` breakpoint a left panel collapses to the standard off-canvas/overlay pattern (Bootstrap navbar + offcanvas) with its toggle in the header; no mobile-specific optimization beyond Bootstrap defaults (ASM-UI-1).
- The login page (§2.2), the public password pages (`/password-reset`, `/set-password`, §2.6), and the public survey page (§8.8) render a single centered panel with **no** left panel, no header navigation, and no account menu — there is no session to scope them by (DEV-UI-1 pattern).

### 2.5 Two-factor settings (`GET /account/two-factor`, REQ-UI-039)

A section of the account page (§2.8), reachable by every signed-in user (also rendered standalone inside the mandated-enrollment flow of §2.2 before a session exists). Data: `GET /api/v1/users/me/tfa`.

- **Current method** badge: off / authenticator app (`totp`) / email (`email`), with enrollment date.
- **Enable TOTP**: button → the API's returned secret rendered as a QR code (client-side from `otpauth_uri`, no external service) plus the manual-entry key with a copy affordance; one confirmation-code field; on success the **recovery codes** appear exactly once in a monospace block with a copy button and an explicit "I saved them" acknowledgement (`POST …/totp/enroll`, `POST …/totp/confirm`).
- **Enable email**: "Send code" → six-digit confirmation field (+ resend, rate-limited); the option is absent when SMTP is not configured — `POST …/email/start` 409 maps to a hidden control server-side (REQ-AUTH-057). Recovery codes shown once as above.
- **Disable**: asks for a current code or recovery code before `POST …/tfa/disable`; explains that the mandate re-prompts enrollment at the next login when on.
- The secret and codes never re-render after their one-time display; reload shows status only (REQ-AUTH-056). All actions CSRF-protected (REQ-UI-005); strings translated server-side (REQ-UI-008).

### 2.6 Password change, reset, and invite completion (GD-22/GD-23)

**Change own password (`GET /account/password`, authenticated, in the shell).** A section of the account page (§2.8), offered in its panel only when the account has a local credential (GD-23). One form: current password, new password + repeat; submits `PUT /api/v1/users/me/password` (CSRF, REQ-UI-005). A wrong current password shows the generic bad-password line (`API_Endpoints_Design.md` §4.2); success shows a confirmation and clears the fields. The account's **email address is displayed read-only** — identity changes go through an administrator (REQ-AUTH-061). The change signs the account out everywhere else; the session that made it stays signed in under a new id (REQ-AUTH-074).

**Forgot password (`GET /password-reset`, public, standalone panel).** One email field; submits `POST /api/v1/auth/password-reset/request`; the page always shows the same translated line — "If that address has an account with a local password, a reset link has been sent" — never revealing whether it did (REQ-AUTH-062). Rate-limit rejection (429) shows a retry-soon message.

**Set password (`GET /set-password?token=…`, public, standalone panel).** Reached from the invite or reset email. Renders two new-password fields (+ repeat, client-side match check plus authoritative server check); on submit PHP routes by purpose — `POST /api/v1/auth/invite/complete` or `POST /api/v1/auth/password-reset/complete`. Any token failure (unknown, expired, consumed) shows one generic translated line with a link back to `/login` and, for the reset case, an offer to request a new link (`invalid_setup_token`, `API_Endpoints_Design.md` §4.2). Success: invite → "Password set — sign in" link to `/login`; reset → same. The token never re-renders into the page beyond the hidden form field carrying it; no session is established by this page (Sequence H, `Authentication_Authorization_Design.md` §2.8).

### 2.7 Training page (`GET /training`, any authenticated, REQ-UI-059)

Short step-by-step guides to common tasks, reached from the header's **Training** link (§2.4) — on every page, so also from the project overview (master spec: "linked on the first project selection screen header (next to 'Control Panel')"). The page renders in the single-panel shell of the project overview (§2.4 A): a heading, one intro line, and a responsive grid of Bootstrap cards (`row-cols-1 / -sm-2 / -lg-3 / -xxl-4`).

**Where the plans live.** One directory per plan under `web/assets/training/` — not in the database and not behind the API: the plans describe the application rather than a project, and an operator adds or edits one by dropping files there (master spec: "stored in individual sub-directories inside assets/ (so they are easy to add/edit)"). `web/assets/training/README.md` documents the format for editors.

```
web/assets/training/<plan>/      <plan> = [a-z0-9][a-z0-9_-]*; directory-name order is the card order
    plan.md                      the text, English (without it the directory is not a plan)
    plan.<language>.md           optional, the text in a UI language (nb, nn, …)
    *.png | *.jpg | *.gif | *.webp   the pictures, in natural file-name order; the first is the card's
```

- **Text format** — a small Markdown subset, parsed in PHP (`Clara\Training`): the first line `# Title`; paragraphs; `## ` headings; `1. ` and `- ` lists (an indented line continues the item above); `**bold**` and `` `code` `` inline. The first paragraph is the card's short text and also opens the modal's text. Nothing else is interpreted — HTML in a plan file stays literal text (§3.2, REQ-UI-004).
- **Language** — the acting user's UI language picks `plan.<language>.md` when present; otherwise `plan.md` (REQ-UI-008). The language only ever selects a file name matching a language tag.
- **Pictures** — served by the static asset handler like every other file under `web/assets/` (revalidated, ETag; `jpg`/`jpeg`/`webp` join the media-type map). SVG is not accepted as a picture. Only file names of letters, digits, `.`, `-`, `_` are listed.

**Data region.** The route's `plans` region (REQ-UI-044) is the list of plans, each `{id, title, summary, images: [url…], blocks}`, where a block is `{type: paragraph|heading, text: runs}` or `{type: list, ordered, items: [runs…]}` and a run is `{text, strong, code}`. `assets/js/training.js` (REQ-UI-045) builds the cards and the modal from it with `createElement`/`textContent` only (§3.7). The region reads files; it makes no API call.

**Card.** The plan's first picture as `card-img-top`, cropped to 16:10 from its top-left corner (a screenshot's header and left panel identify the page), the title as the card's link (`stretched-link`, so the whole card opens the plan), and the short text. A plan without pictures shows a card without one. With no plans installed, the grid shows one empty-state line.

**Modal** (`modal-xl`, scrollable, full screen below `lg`): the plan title; then the **gallery** — a Bootstrap carousel (no auto-play) of the pictures, each fitted to half the viewport height and linking to the full-size file, previous/next controls, a "Picture n of N" counter and a thumbnail strip (the current one marked) — and below it the plan's text. The arrow keys page through the pictures while the dialog is open; touch swipes do as well. A plan with one picture shows no paging controls; one with none shows its text only. Opening a plan puts its id in the address fragment (`/training#<plan>`), so a plan can be linked to directly; closing removes it.

### 2.8 Account page (`GET /account`, any authenticated, REQ-UI-063)

The signed-in user's own settings in one place (DEV-UI-18), reached from the header's account menu (§2.4). ## 3. Common Components and Rendering Rules

These rules apply on every page of §2.1 and are the single implementation of the REQ-UI-001…008 conventions.

### 3.1 Permission gating (REQ-UI-003, REQ-AUTH-027)

- A single PHP helper resolves, per request, the acting user's effective permissions for the target project (via the API — the API re-checks on every call, REQ-AUTH-033) and the template renders conditionally. The `permissions` object of `GET /api/v1/projects/{id}` (REQ-API-126) is that read: `project_admin` plus the data access and export level of every arm, so no page needs a second round trip to know what it may offer. "Hidden" = **absent from the DOM** — no `display:none`, no disabled control.
- Consequence table (normative): a control whose permission is missing MUST NOT be emitted — not as a disabled button, not as a link to a 403 page. This holds for left-panel entries (§2.4), the header's Control Panel button, page action buttons, and per-row actions (e.g. the per-member token rotation, §5.3).

### 3.2 Escaping and free-text (REQ-UI-004, REQ-TECH-020)

- Server-side escaping for **all** content: choice values, field labels, record names, user names, audit payloads, translated strings — every interpolation into HTML.
- **Exception** (the only one): stored free-text values render as HTML — they are allowlist HTML because the store sanitized them (`Data_Validation_Design.md` §5.2). They appear in: data-entry form values, per-field history (REQ-UI-026), record view, audit details.
- The `Content-Security-Policy` header is sent on **every** response (REQ-TECH-020) and is the backstop, not a substitute, for escaping.
- Its one script-source relaxation is `'wasm-unsafe-eval'`: compiling WebAssembly is judged against `script-src` even when the bytes were fetched from this origin, so the assistant's model library (`AI_Assistant_Design.md` §5) needs it. It grants WebAssembly compilation and nothing else — no `'unsafe-inline'` anywhere, and never the bare `'unsafe-eval'` that would let script `eval` strings (`Response::CSP`, checked by `tests/php/rendering_test.php`).

### 3.3 State-changing requests (REQ-UI-005, REQ-AUTH-037)

- Every mutation is a browser `POST` (form submit or `fetch`) carrying the per-session `csrf_token`: hidden `csrf_token` field for forms, `X-CSRF-Token` header for `fetch`. No `GET` performs a write.
- The PHP route validates the CSRF token first; on failure it renders the page again with an error alert and no API call is made.

### 3.4 API errors → user messages (REQ-API-006, REQ-API-007)

The PHP layer maps the stable `error` code of `API_Endpoints_Design.md` §4.2 to a **translated** user message; the API's `message` is shown only when it is a design-time reason the requirements mandate displaying (validation reasons, REQ-VAL-029). Mapping:

| API `error` / status | User presentation |
|---|------|
| `invalid_request` (400) | "The form contains invalid values" + the API `message` when it names the offending attribute; where PHP rejects a posted value itself, the line names the responsible form field(s) (e.g. ": event, instrument") — an alert never blames the form without naming at least one control |
| `validation_error` (400) | the `message` verbatim (design-time expression/dictionary reason — REQ-VAL-029, REQ-UI-021/022) |
| `forbidden` (403) | "You do not have permission for this action" — uniform; never "project not found" (REQ-API-007) |
| `conflict` (409) | the `message` (duplicate name, still-in-use resource, §5.5 group deletion) |
| `not_found` (404) | "The object does not exist or you do not have access" (uniform with 403 for protected resources) |
| `account_not_found` / `bad_password` / `account_disabled` / `account_expired` (login) | the login-page failure line of §2.2 (reason-specific text; auto-disabled and expired accounts point the user to an administrator) |
| `mfa_required` (login, GD-21) | not an error — switches the login page to the two-factor panel (§2.2) |
| `bad_mfa_code` (login) | "That code is wrong or has expired" on the two-factor panel; resend stays available until the lockout line replaces it (REQ-AUTH-058) |
| `tfa_enrollment_required` (login) | not an error — opens the enrollment wizard (§2.5, §2.2) |
| `session_revoked` (401) | not a line on the current page: the session is ended and the browser goes to `/login`, which shows `session.ended.revoked` (§2.2, REQ-AUTH-074) |
| `service_token_invalid` / `internal` (500) | a generic failure line + the operator is notified by the application log — never internals (REQ-API-006); the line carries the request's correlation reference, and in development the technical detail as well (REQ-UI-050) |
| transport failure — the API never answered (`unreachable`, web-layer 502) | a dedicated line naming the backend service as responsible ("The application could not reach its backend service…"), never the form-blaming `invalid_request` text; it carries the same reference and development-detail suffixes as the generic line (REQ-UI-050) |
| data-API `import_record_id = 0` | the per-field validation detail from `import_form_name` (`Data_Validation_Design.md` §3 codes), §8.6 |

**Correlation reference (REQ-UI-050).** Every request handled by the PHP layer carries an opaque per-request reference (`Request::ref()`, generated in `fromGlobals()`). The web logger stamps it into every log line of that request, and a generic failure line — flash alert, 500 page, fatal fallback — appends `error.reference` ("Reference: {ref}") so a user report finds the logged cause; JSON failures carry the same token as an additive `ref` field. Nothing about the reference encodes internals. When `APP_ENV=development`, the generic line additionally renders the technical detail the screen otherwise never shows (API code, status, failing call, message; exception class and origin for fatal errors) — the same development/production split `configFailure()` uses.

Success confirmations (created/updated/removed) are one translated alert line at the top of the panel; they name the object (e.g. "Event `follow_up` updated") — never identifiers of other users beyond what the page already shows.

### 3.5 Confirmations and destructive actions (GD-3, REQ-UI-015/027)

- Destructive or hard-to-reverse actions open a Bootstrap **modal** stating the consequence, requiring an explicit confirm click (which carries the CSRF token): delete record/scoped values (§8.7), remove member (§5.3), delete group (§5.5), delete field with stored values (§7.2), revoke survey link (§8.7), delete arm/event where supported.
- Token display (add/rotate, §5.3): the new token appears **exactly once**, **masked** — a read-only `<input type="password">` that is empty (a row of bullets as placeholder), so the page does not hold the value — with a **Show** button and a warning line that it will not be shown again (REQ-API-055, REQ-UI-013/062). Show is a form `POST …/members?action=show_token`: PHP has the view recorded (`POST …/users/{uid}/token-viewed`, `token_viewed`, REQ-AUD-033) and only on success redirects to the same reveal unmasked — a read-only text input, **Hide** (`action=hide_token`, nothing recorded) and **Copy**. A failed record keeps it masked with the §3.4 line. No copy is offered while masked, so every sight of the value is in the trail. Between the add/rotate redirect and the Show/Hide redirects PHP keeps the value in the session (`Session::holdReveal`), never in the browser; any other render of Members drops it, so a reload ends the reveal. The admin's copy is not the only one: the member can later see their own token on the account page behind the same audited Show (§2.8, REQ-API-162), and PHP fetches it for UI data entry per REQ-API-102 (§8.6).

### 3.6 Lists, pagination, empty states

- Paginated endpoints (audit, record history) render a Bootstrap table + "Next/Prev" controls carrying the opaque `cursor` and the active `limit` (`API_Endpoints_Design.md` §1); the URL query string carries `cursor`/filters so a page is reloadable (GET-only).
- Every list has a translated empty state that says what is empty and, when actionable, the one action that fills it (e.g. roles: "No roles yet — members without a role have full permissions (REQ-AUTH-022)").

### 3.7 Client-side data binding (REQ-UI-032, REQ-TECH-025, REQ-UI-044/045)

The reference application's interfacing style (master spec, "Details"; `assets/table_based_authentication_plus_user_management/` — `/php/*.php` JSON endpoints, `js/all.js` fetch-and-populate) is adopted for the presentation layer, in vanilla ES2020:

- **Server renders the shell and static content.** Each route of §2.1 returns the page shell — header, the left panel where that page has one (§2.4), headings, forms, empty data containers — fully rendered, permission-gated (REQ-UI-003), and with UI strings translated (REQ-UI-008).
- **Client binds data regions.** The page's modules fetch JSON from the route that served the page — the same route, content-negotiated (REQ-UI-044), proxying the API server-side (REQ-TECH-006, GD-1) — and populate data regions: list rows, table bodies, and `<select>` options. They write with **safe DOM APIs** — `createElement`/`textContent` for all content except the stored free-text allowlist HTML (the §3.2 exception); `innerHTML` with user data is forbidden (REQ-UI-004, REQ-TECH-020).
- **Where the JSON comes from — one mechanism, in the router** (REQ-UI-044). A data region is served by the page's own route, selected on `Accept`: a request preferring `application/json` (which the client always sends) receives that route's data region as JSON, anything else receives the rendered page. The decision lives in the front controller/router, before the controller runs — a controller exposes one handler per §2.1 route and declares the regions it can serve, so **adding a page adds no routing code** and no page re-implements the negotiation. Because dispatch happens after the session guard and the permission gate, a data request is authorized exactly like the page render it stands for and discloses no more than that page would (§3.1, REQ-UI-003); its failures carry the HTTP status and stable `error` code of `API_Endpoints_Design.md` §4.2, which the client renders through the §3.4 table.
- **Which script does it** (REQ-UI-045). `web/assets/app.js` is the shared runtime — the fetch helper (sets `Accept: application/json`, attaches `X-CSRF-Token`, reads the §9 string block once and exposes it), the data-region binders, and the defaults every table shares (Tabulator configuration, empty states per §3.6). One module per view or logical section lives beside it under `web/assets/js/` (`record.js`, `record-status.js`, `setup.js`, `design.js`, `members.js`, `admin-users.js`, `survey.js`, …) and carries that surface's behaviour: the advisory validation and branching evaluator of §8.4 (shared by `record.js` and `survey.js` as a module both import), the expression editors of §7, the submission-policy diff of §8.6. A page emits `<script type="module" src="…">` for the runtime plus the modules it needs — relative paths, unbundled, same-origin (`Technology_Stack_Design.md` §4).
- **Background refresh.** A page that re-reads a region on its own timer may mark the read with `X-Clara-Refresh: 1` (`fetchJson(path, { refresh: true })` in `app.js`). The router then runs the session lifecycle, guard and permission gate as for any request but leaves `last_seen_at` alone, so the read does not count as activity for the idle bound (REQ-AUTH-015, `Authentication_Authorization_Design.md` §3.1) and a page left open still ends its session. The header can only end a session sooner, never keep one open, so it is taken from the client as sent; it counts on a `GET` data read only, never on a page render or a `POST`. The project overview uses it (§4, REQ-UI-073). The Monitoring poll (§5.11) does not, and still counts as activity.
- **No page switching.** Data binding fills targets within the current page; navigation is still a full `GET` to a §2.1 route (no SPA — REQ-UI-001, REQ-TECH-001).
- **Mutations are unchanged.** Every state-changing request is still a CSRF-protected `POST` to a PHP route (REQ-UI-005, §3.3); after a successful mutation the client re-fetches the affected data region rather than mutating the DOM by hand.
- **Subordinate to the fixed conventions.** Where the reference diverges — its Bootstrap 2.x, jQuery, JSON-file store, and md5-in-transport password — it is **not** adopted (REQ-TECH-001, REQ-TECH-020/024, REQ-AUTH-036).

### 3.8 Theme rendering and selection (GD-26, REQ-UI-040/041)

- **One stylesheet per page.** The PHP shell links exactly one Bootstrap stylesheet in the `<head>`: the standard `vendor/bootstrap/bootstrap.min.css`, or the selected theme's `vendor/bootstrap/themes/<name>/bootstrap.min.css` (vendored per `Technology_Stack_Design.md` §2/§4; themes are full replacements — never both, never layered). All other assets (bundle JS, Tabulator, Geist) are theme-independent and unchanged.
- **Resolution at render time.** The effective theme is the acting user's override (`users.ui_theme`, from the session's user object) when set, else the installation default `UI_THEME` (REQ-CFG-031). Only installed theme identifiers resolve; the value never comes from the request, so no arbitrary path lands in the `href` (REQ-TECH-027). The login page, the public password pages (§2.6), and the survey page (§8.8) have no user context and render with the installation default.
- **Theme selector** (account page — Profile, §2.8; REQ-UI-041): a `<select>` beside the language selector listing the installed themes (`Standard`, `Darkly`, `Yeti` — translated display names) plus **"Default"** (= follow the installation theme, i.e. clear the personal override). Choosing one is a CSRF-protected `POST /theme` (form submit, redirect back to the account page like `POST /lang`) → `PUT /api/v1/users/me/ui-theme` (REQ-API-122); the new stylesheet applies **from the next page load** — the current page keeps its already-rendered theme.
- **Markup is theme-neutral.** No page structure or component changes with the theme (REQ-TECH-027): `table-sm`, the offcanvas collapse (§2.4), modals, and badges render from the same markup under every installed theme. The CSP of §3.2 already allows only same-origin styles — a theme introduces no new source.

- **A bento grid of boxes, one per visible project** (REQ-UI-070): `.clara-projects` is a CSS grid of `auto-fill` tracks of at least 15rem, so the panel's own width decides how many columns there are and a phone gets one. Packing stays in order — deliberately **not** `dense`, because the page promises that the most recently used project appears first and dense packing would buy tidiness by pulling an older box up beside it; a row that cannot host the next wide box simply ends short.
- **Every box carries the same five facts**: project name, organization where there is one, when the acting user last used the project, and all three counts as returned by the endpoint (`record_count`, `instrument_count`, `field_count` — REQ-UI-009, REQ-API-049). What changes with size is their **arrangement**, and it follows the shape of the box rather than a per-tier template: `.clara-project-cell` is a query container and at 26rem and above the box lays the identity down one side and the statistics across the other (name top-left, counts on the bottom edge at the far corner), while a narrower box stacks them — name, organization, last used, then the counts as a key/value list with the figures in a column. The same project therefore reads across on a desktop and down on a phone without losing or duplicating a fact (REQ-UI-070). A browser without container queries keeps the stacked arrangement: complete, only less fitted.
- **Tier is size and weight, never information** (REQ-UI-071): used within a week → the wide box (two tracks) with the largest type; within a month → one track; older or never opened → one track, lighter. The span applies from 576px up, where a second track exists to span.
- **Last used** is `last_accessed_at` — the acting user's own newest audit event in that project (REQ-API-049) — rendered relative while the answer is two days long ("today", "yesterday") and dated beyond them, with the year once it is no longer this year; `null` renders as a translated "never opened" line rather than an empty date. The API's UTC text is parsed as UTC (the stamp carries no offset) and formatted in the browser's locale, while the words around it stay the application's language (REQ-UI-008). Ordering happens here, in `dashboard.js`, over the endpoint's alphabetical list: newest first, never-used last, name order within a day.
- **The project name is the link** and the whole box takes its click (the stretched link of the name), so one box is one tab stop; [Open project] appears as text in a wide box only, where there is room to name what the box already does. Hover and focus mark the frame — the same affordance the Training cards use (§2.7). Markup stays theme-neutral, so every installed theme renders the same grid (REQ-UI-040, §3.8).
- **Kept current** (REQ-UI-073): `dashboard.js` re-reads the region every 2 s while the document is visible — one read at a time, the next timed from the end of the one before, paused while the tab is hidden and read at once on return. A read that brings the same list on the same day touches nothing, so hover and focus are undisturbed (the day is part of the comparison because "today", "yesterday" and the tiers move at midnight). A changed one updates the grid in place: each project keeps its box from read to read, a changed fact — name, organization, last used, a count, the tier — is rewritten where it stands, a new project gets a new box, one no longer visible loses its own, and a box moves only when the order changed; the heading's count (`[data-clara-project-count]`) follows. Rebuilding the grid instead made Safari return the page to the top on every redraw, so the reader keeps their place, and keyboard focus stays on the link of the project that had it (given back without scrolling when its box moved); while a box plays its opening animation the grid is not redrawn. A failed refresh keeps the boxes it has — the failure line and its retry are only for a grid that never loaded — and a refused (`forbidden`) refresh on a page that has shown its list reloads it, so the guard decides: an ended session goes to the login page with its reason (REQ-AUTH-015), a withdrawn last membership to the no-access page (§2.3). A page that never listed anything stops refreshing instead of reloading, so a refusal cannot turn into a reload loop. Refreshes go out as background reads (§3.7) and do not move the idle bound. Each one costs one `GET /api/v1/projects`, which counts records rather than reading them.
- **The header carries the [Control Panel] button for `is_admin` only** (REQ-UI-003/009) — the single entry point to §5, replacing the former dashboard `[Administration]` link and the Administration sidebar section.
- **Data access groups** (REQ-UI-010): for a member with one or more assigned groups, the box shows the **currently active group** and a switch control listing the member's assigned groups. Switching `POST`s to the PHP route → `PUT /api/v1/projects/{id}/active-data-access-group` (REQ-API-090); the switch takes effect on the **next** data page load (the current page's data was already scoped). A member without any assignment sees no group control — they see all records of the project (GD-10).
- No projects and not `is_admin` → the no-access page (§2.3). An `is_admin` user sees every project; with none in the installation the grid shows one line saying so (§2.3), and a failed load replaces the grid with that line and a retry — the region's loading, empty and failure states all occupy the grid rather than a table cell (REQ-UI-032).

## 5. Administration Interface — the Control Panel (`GET /admin`)

One page carries every installation-administration function (REQ-UI-047, DEV-UI-15): the **Control Panel**, reached from the header button of §2.4 and from nothing else. It is a left-panel shell (§2.4 B) whose panel lists the sections in this order — **Projects** (`section=projects`, §5.2), **Users** (`section=users`, §5.1), **Audits** (`section=audits`, §5.6), **Translations** (`section=translations`, §5.7), **Settings** (`section=settings`, §5.8), **Monitoring** (`section=monitoring`, §5.11), **Authentication Test** (`section=auth`, §5.12), **Configuration Check** (`section=check`, §5.10), **API documentation** (`section=api`, §5.9) — and whose right-hand panel shows the section selected there. `GET /admin` with no `section` renders the first available one — Projects, the section an administrator needs most often; a section this build does not serve is absent from the panel rather than disabled (REQ-UI-003). Mutations stay `POST /admin?section=<name>&action=<name>` (§2.1, REQ-UI-005), and a JSON request's data region is that section's (§3.7, REQ-UI-044).

§5.3/§5.4/§5.5 are **project-scoped** and live on the project page's left panel (§6.1 — master spec: the project offers "administer users in the project"); they are not Control Panel sections, because their permission comes from the project rather than from the installation (REQ-UI-047).

### 5.1 Users section (`GET /admin?section=users`, `is_admin`, REQ-UI-011)

Data: `GET /api/v1/users` (the full user object, `API_Endpoints_Design.md` §4.3/§4.4). Table columns: `email`, `display_name`, `enabled` (badge), `is_admin` (badge), `auth_source` (`oauth2`/`ldap`/`local`), **`last_login_at`** (UTC; "never" when `null`), **`valid_until`** ("indefinite" when `null`), the derived **status** badge — `active` / `disabled` / `expired` / `auto_disabled` (GD-19, REQ-AUTH-052/053) — and the **two-factor method** badge `off` / `totp` / `email` (GD-21, REQ-API-116). An `auto_disabled` row is visually distinct and shows the inactivity reason ("no login for more than `AUTH_INACTIVITY_LIMIT_DAYS` days — re-enabled by an administrator").

### 5.10 Configuration Check section (`GET /admin?section=check`, `is_admin`, REQ-UI-061)

`INSTALL.md` as checks: one table per source, each row a status badge (OK, Warning, Problem, Info, Not checked), the check, the finding with its remedy, and the guide's section. A summary line above counts problems and warnings; **Check again** reloads. Nothing on the page writes anything.

- **Sources**: `Clara\ConfigCheck::probe()` reads the PHP process (version, extensions, OPcache, `proc_open` and the CLI interpreter `Clara\PhpCli` finds, `post_max_size`/`upload_max_filesize`/`memory_limit`, `HTTPS` and `Host` of the request, its connection address (`REMOTE_ADDR`) beside any forwarded `X-Real-IP` — which of the two names the caller is a configuration question worth showing (REQ-API-125) — the `.env` file's mode, writability and `CHANGE_ME` variables, the session directory's mode and place, writable `web/` subtrees); one read of `GET /api/v1/system/check` (`API_Endpoints_Design.md` §4.24) supplies the API, host and database facts. `ConfigCheck::evaluate()` rates both; the controller only renders. An API that cannot answer becomes the *API answers* Problem row and the database group shows *Not checked* — the page itself still renders.
- **Groups**: PHP runtime · Web application configuration and files · API service and host · Database (on SQLite only the engine and schema rows) · Web server, as your browser sees it · Check by hand (firewall, certificate trust and the HTTP redirect, `mariadb-secure-installation`, backups — `INSTALL.md` §17 items no process on the host can observe).
- **Severity**: a finding that breaks a function is a Problem (missing extension, `CHANGE_ME`, weak secret in production, writable audit tables in production, tables without `UPDATE`/`DELETE`, SQLite in production, a world-readable `.env`, sessions under the document root, an exposed internal path). Hardening a development checkout lacks by design (plain HTTP, writable code and `.env`, development secrets, the install-state grants, an open bind address, a non-root or SELinux finding, a forwarded caller address from a peer `TRUSTED_PROXY_CIDRS` does not list, no connection address at all) is a Warning under `APP_ENV=production` and Info under `development`; `APP_ENV=development` itself is a Warning. Facts that are neither (SMTP off, local sign-in only, schema version, no forwarded address where `fastcgi_params` already carries the client through) are Info; a value the platform cannot report is Not checked.
- **Browser probes**: `web/assets/js/config-check.js` fills the browser rows — rendered *Not checked … needs JavaScript*, then *Checking…* — with `fetch` calls made the way an outside caller makes them (`credentials: "omit"`, `redirect: "manual"`, `cache: "no-store"`): `/api/v1/health` and `/docs`, `/openapi.json`, `/healthz` must answer 404; `/assets/vendor/bootstrap/bootstrap.min.css` must answer 200 `text/css` and `/assets/app.js` carry `Cache-Control: no-cache`; on HTTPS, `Strict-Transport-Security` must be present. The `/api/v1/` request is REQ-UI-002's one exception: it expects no answer. The probe lines travel in the data-i18n block.
- **Secrets**: no value of a secret is ever read into the page — `.env` placeholders and weak secrets are named by variable.
- **Layout**: `table-sm` tables with fixed column widths shared by every group; below the `sm` breakpoint each row stacks (status beside the check's name, finding and section beneath), so nothing scrolls sideways on a phone.

### 5.11 Monitoring section (`GET /admin?section=monitoring`, `is_admin`, REQ-UI-064)

The API's own live numbers, refreshing once per second while the page is visible: stat cards up top (requests/s, interval mean latency, goroutines, heap in use, pool connections in use over max, blocked addresses, uptime), eight small-multiple d3 line charts sharing one x axis of the configured period (`MONITORING_PERIOD_MINUTES`, ten minutes by default, REQ-CFG-034) — requests per second, interval mean latency, goroutines, heap in use, database pool `in_use` against a dashed `max_open` ceiling, pool waits per second, last GC pause, response bytes per second — and below them the **Blocked IP addresses** table (`table-sm`: address, blocked until, seconds remaining) with an explicit empty state that distinguishes "nothing is blocked" from "rate limiting is off."

- **Data**: one data region call per tick — `GET /admin?section=monitoring` with `Accept: application/json` answers `{metrics, rate_limit, stress_test}`: the snapshots of `GET /api/v1/system/metrics` (§4.25) and `GET /api/v1/system/blocked-ips` (§4.26) passed through, plus the background stress-test status (REQ-UI-068); each API key is null plus an `error` code when its endpoint failed, and an API that cannot answer is itself the shown finding (like §5.10), never an error page. The browser never reaches `/api/v1/*` (REQ-UI-002).
- **History**: the endpoint carries counters as of now, not a series — the page accumulates its samples in memory, so the charts cover the configured period (`MONITORING_PERIOD_MINUTES`, ten minutes by default, REQ-CFG-034) **as observed since the page was opened** and an API restart (negative deltas) reads as a gap. The buffer is bounded to that period: every timepoint older than it is dropped when a sample arrives, both by age and by count, so a section left open for a day — or fed snapshots whose `generated_at` never advances — keeps one period and no more. Only the period's own samples are drawn and take part in the y scale. Polling pauses while the document is hidden and resumes on return; a tick never overlaps its predecessor. `generated_at` from the snapshot aligns the x axis instead of the client clock, and the charts row's `data-clara-mon-period-minutes` is how the script learns the period (the browser reads no environment, REQ-UI-002).
- **Gaps**: a stretch with no sample in it breaks the line — it ends at the last observed value and a new line starts at the next one — instead of drawing straight across time nobody sampled (REQ-UI-064). A sample is contiguous with its predecessor while it arrives within `4 × POLL_MS` of it: `generated_at` has second resolution, so a healthy 1 Hz poll reads 1–2 s apart and anything wider is not jitter but the page having stopped watching (tab hidden, machine asleep, API unreachable for a few seconds). The late sample carries no rates — an interval nobody sampled measures nothing about this interval — which breaks the four rate charts on its null values, and it is flagged so the four gauge charts start a new line at it too: their values stay true at their own timestamp, so they keep their points and their share of the axis extrema. `linePath` therefore emits one subpath per contiguous run rather than trusting d3's `defined` filter alone, which can only drop a point, not leave it unconnected. The four rate stat cards follow the same rule: when the newest sample carries no rate, the card shows the em dash instead of holding the number from before it — a card that never changes reads as one that is live. Uptime counts in seconds (`45s`, `3:07:41`, `2d 4:12:09`, mirrored in the PHP first paint) for the same reason: at minute resolution the card holds one string for sixty ticks.
- **Y-axis**: every chart shows exactly two labelled ticks at the observed minimum and maximum of its non-gap values in the displayed history. The tick labels use the chart's value format and units; the pool's dashed `max_open` reference line does not replace either observed-value tick.
- **Rendering**: the vendored d3 v7 (`Design/Technology_Stack_Design.md` §3) draws inline SVG — no canvas, no chart library beyond d3 — styled entirely through `currentColor` and CSS custom properties so both themes restyle it untouched. The blocked table is a plain `table-sm` re-rendered each tick (a bounded list of tens of rows appearing and expiring; Tabulator's machinery would add cost and flicker, not performance).
- **Self-polling**: the page asks for two API requests per second from PHP's source address; with a low `rate_limit_rpm` it can spend its own budget and display itself blocked — honest behaviour of §4.26, noted there.
- **Stress Test** (REQ-UI-068): an administrator starts a background run with a CSRF-protected POST to `/admin?section=monitoring&action=monitoring_stress_test`. `monitoring.js` submits that POST in place of letting the browser navigate (DEV-UI-24), so starting a run leaves the polling loop and its sample buffer untouched and the charts carry the load on both sides of the moment it began; the redirect is followed only to spend the flash message the action sets, and with scripting off the form still posts the ordinary way. The loop is never joined by a second read from the click handler — a tick never overlaps its predecessor — so the run's own phase and progress arrive on the next one-second read, and a start that left no running worker says so in the section's status line after a grace of five ticks. PHP starts the repository's Python stress client with the session's administrator id; the worker uses the internal service token and that id for API calls, not the administrator's password. It works on `StressTest01`–`StressTest40`, adding instruments, importing data and exporting as the existing stress workflow does; records are imported complete — every instrument of the project in every record, every checkbox box checked (`--fill-all`) — so the dataset grows dense as well as large. The action is repeatable: a target name already in use is **adopted** — its events, instruments and field dictionary are read back over §4.5/§4.9/§4.10/§4.11 and imported into exactly as a created project would be, with the acting administrator's own membership token (§4.6) rather than a reissued one — and only a missing target is created, so pressing the button again grows the dataset the first press built instead of failing on a name in use (DEV-UI-23). Record identifiers continue above the highest one those projects already export, which is what makes a repeat run add rows where it would otherwise update them. Its progress is atomically written to a private temporary directory and included in the same one-second Monitoring data region; the browser renders phase and progress without reaching the API. It runs out of the HTTP request so the Monitoring page and PHP workers remain available. The projects and data remain after completion; the view says another run adds to what is there and that removing the projects resets the test. No project-delete API is introduced (DEV-UI-22).

### 5.12 Authentication Test section (`GET /admin?section=auth`, `is_admin`, REQ-AUTH-085)

## 6. Project Workspace

### 6.1 The project page (`GET /projects/{id}`, REQ-UI-017)

The project page is a left-panel shell (§2.4 B): its left panel lists the project's own functions, and the right-hand panel shows the section selected there (master spec: "selecting different functions (like setup) should load the corresponding page in the right hand panel"). Data: `GET /api/v1/projects/{id}` — full metadata + structure, whose `permissions` block (REQ-API-126) decides both which entries appear and which section opens. Gating: project visibility (REQ-API-007).

**Left-panel entries**, in this canonical order, each present **only** when the acting user may use it (REQ-UI-003):

| Entry | Route | Required permission | Master-spec option |
|---|---|---|---|
| Overview | `/projects/{id}/overview` | project visibility | (project summary and mode) |
| **Setup** | `/projects/{id}/setup` (§6.2) | `project_admin` | i) setup the project; iii) create arms and events; iv) assign instruments to arms and events |
| Design | `/projects/{id}/design` (§7.1) | `project_admin` | ii) design all instruments — the list adds, edits, reorders and removes them (REQ-UI-067) |
| **Record Status Dashboard** | `/projects/{id}/record-status` (§6.3) | data access ≥ `read_only` | (participant overview) |
| **Export** | `/projects/{id}/export` (§6.4) | a non-`export_none` level on at least one (instrument, event) pair (REQ-API-075, REQ-AUTH-069) | vi) export |
| Members · Roles | `/projects/{id}/members` · `/roles` (§5.3 · §5.4) | `is_admin` | v) administer users in the project (match roles to permissions) |
| Groups | `/projects/{id}/groups` (§5.5) | data access ≥ `read_only` (mutate: `project_admin`) | (record scope) |

- **Default section** (REQ-UI-017). `GET /projects/{id}` is the entry point PHP resolves rather than a page of its own: it reads the project and answers `303 See Other` to the first available entry **after Overview** — `/setup` for a member allowed to change the setup, otherwise `/record-status` for a member with data access ≥ `read_only`, otherwise `/overview`. Clicking a project on the overview screen therefore lands a project administrator on **Setup** and a data-entry member on the **Record Status Dashboard**, without a per-project permission read on the overview page itself (the list endpoint does not carry one, REQ-API-049). The left panel still lists everything else the user may use, so each remains one click away.
- **Overview** (`GET /projects/{id}/overview`) — the project's own summary page: record count, instrument count, field count (REQ-API-051), the metadata block (name, organization, PI, REK number, dates — read-only display; editing goes to §5.2 for `project_admin`), the mode badge and its control (§6.6, REQ-UI-033), and the End provision card (§6.5, `is_admin`, BR-009).
- **Header breadcrumb** — the project's name links back to Overview; the brand link leaves the project for the project overview (`/`) (§2.4).

### 6.2 Setup page (`GET /projects/{id}/setup`, `project_admin`, REQ-UI-018)

One page, three structure blocks and a naming-mode block: **A arms**, **B events per arm**, **D the instrument × event matrix**. (The former **block C — instruments** is now part of the Designer's instrument list, §7.1 / REQ-UI-067 / DEV-UI-21; the letters here stay as they are so older references keep resolving.) **Arm-dependent blocks are presented as tabs, one per arm, with arm 1 (`arm_1`) displayed by default** (master spec: "as arms will be used rarely, all arm dependent sections can be hidden using a tab-interface; the information of the first arm (arm_1) should be displayed by default"). Phase 1 starts with a single arm (REQ-DB-011), so the tab strip initially shows one tab; adding an arm adds a tab.

**Block A — Arms** (all arms; not tabbed): a list of arms (`arm_num`, `name`); **Add arm** form (`name`) → `POST …/arms`; **Rename** — edit form (`name`, the instrument-edit flow of §7.1 in miniature) → `PUT /api/v1/arms/{id}` (label only, REQ-API-150; REQ-UI-048); **Reorder** (up/down or drag) → `PUT …/arms/order` with the **full** ordered id list — ids and `arm_num`s never change (REQ-API-129); **Remove** (confirmation) → `DELETE /api/v1/arms/{id}` — rejected with the 409 message while the arm still has events or data (§3.4, DEV-API-6), except as the project's **last remaining arm**, which is renamed to `arm_1` instead (200 with the renamed object, REQ-API-128).

**Block B — Events** (per arm, tabbed): a table of the arm's events — `event_name`, `unique_event_name` (derived `<label>_arm_<n>`, REQ-DB-011), `period` (the **timepoint**, days after baseline — blank when the event has **no timepoint**, GD-15), `safe_region_start`/`safe_region_end` (± days), `position`. **Add event** form (label, optional timepoint, safe region) → `POST …/events` (duplicate label in the arm → 409; a blank timepoint stores `period = null`). **Edit** row → `PUT /api/v1/events/{id}` (label change re-derives `unique_event_name`; collision → 409; clearing the timepoint makes the event user-orderable). **Delete** row (confirmation modal, §3) → `DELETE /api/v1/events/{id}` — while it is the project's **last remaining event**, the call resets it to the plain `baseline` state instead of deleting it (200 with the renamed object; the confirmation text says so), and the table refreshes from that response (REQ-API-133). Renaming and reordering every event stay available. A new project already contains its first event `baseline` (REQ-API-050).

**Ordering (GD-15, REQ-DB-011):** the table is displayed in the **canonical per-arm order** — timepoint events first, sorted by `period` ascending (ties in position order); then no-timepoint events in position order. **Reorder controls** (up/down arrows) are offered on the **no-timepoint events** (and on ties among timepoint events): they submit `PUT /api/v1/projects/{id}/events/order` with the **full** ordered id list of the arm (`API_Endpoints_Design.md` §4.9, REQ-API-103); timepoint events without ties are not reorderable — their place is fixed by their timepoint (the owner changes that by editing `period`).

**Block C — Instruments → moved to §7.1** (REQ-UI-067, DEV-UI-21): the list of instruments and its **Add** / **Edit** / **Reorder** / **Remove** controls live on the Design page now, beside the field editor they feed and the import that creates them. This page reads `GET …/instruments` for block D's rows and writes nothing to it; a line above the tabs says so and links to §7.1.

**Block D — Instrument × event mapping** (per arm, tabbed; REQ-UI-018, REQ-API-072/073): a **checkbox matrix with instruments as rows and events as columns** (master spec orientation), one matrix per arm tab; each cell = that instrument mapped to that event. An instrument may be assigned to none, one, or several events; it is active for data entry once mapped to ≥ 1 event (REQ-DB-012). **Apply** submits the full matrix of the tabbed arm → `PUT …/instrument-event-mapping` (idempotent; unknown instrument/event name → 400). This is the “design of a project’s arm” (master spec, data model).

**Record naming mode** (all arms; not tabbed): choose how new participants are named — **Auto-name** (plain numeric ids) or **type record_id** — saved with `record_naming` → `PUT /api/v1/projects/{id}` (REQ-UI-052, REQ-API-151). The Record Status Dashboard (§6.3) then emits only the chosen mode’s new-participant control, and the GD-8 identifier renders static text under `auto`, a read-only text input under `manual` — presentation only, the stored design never changes.

### 6.3 Record status dashboard (`GET /projects/{id}/record-status`, REQ-UI-019)

Data: `GET …/record-status` (data access ≥ `read_only` + record visibility, REQ-API-074/REQ-AUTH-045). This is the **participant overview** (master spec): it lists all participants (records) and is where a new participant is created.

- **New participant** (master spec: "create a new participant (enter record_id string)"): a form at the top of the dashboard emitting exactly one naming path, chosen by the project's record naming mode (REQ-UI-052, REQ-DB-045) and never both — under `manual` a `record_id` **input** the user types; under `auto` a single action whose request calls the data API `generateNextRecordName` (≥ `view_edit` on the target arm, REQ-API-023) via PHP and takes the next plain numeric name. Creating the participant opens the data-entry view (§8) for that (record, first event, first active instrument) — in `auto` mode PHP generates the name and redirects straight there; the record is persisted on first import (REQ-API-033) — a save of any form, or getting a survey link for it (§8.7, REQ-UI-051) — and takes the member's active data-access group or none (REQ-API-093). Present only when the member has data access ≥ `view_edit` on some arm (REQ-UI-003).
- **The table**: rows = records (visible under the DAG rule, REQ-AUTH-045); columns = events, grouped per arm (arms tabbed as in §6.2); within each event, the arm's instruments **in order** (REQ-API-074). Each (record, event, instrument) cell shows a **color-code** (the "small graphic" of the master spec):

| State | Color | Meaning | Source |
|---|---|---|---|
| no data | grey | no field of the (record, event, instrument) has a value | derived (any field has a value = false) |
| some data | amber | at least one field has a value | derived (any field has a value = true) |
| finished | green | data entry for this instrument is complete | **user-assigned** (§8.5) |

> **Backend (Open Item 1, §11 — resolved).** The three states are in the baseline: `record-status` returns `no_data` / `some_data` / `finished` per (record, event, instrument) (REQ-API-074), where `finished` is read from `instrument_completion` (REQ-DB-036, `Database_Schema_Design.md` §6) and the other two are derived from whether any field holds a value — so grey/amber can never disagree with the stored data, and green otherwise only ever comes from the user's own assignment. Setting it is REQ-API-110 (§8.5); a survey-marked instrument shows **green automatically** — `record-status` reports it as `finished` without any stored assignment (GD-9; master spec "Instrument level completion info").

- **Sparse cells** (REQ-API-149, `API_Endpoints_Design.md` §4.13). The read lists, per record, the events it reports and only the cells that are not `no_data`; the columns come from the project structure the page already rendered. The `records` data region relays it as `{record_id, events: [<unique_event_name>…], cells: {"<event>|<instrument>": state}}`, and `record-status.js` draws a column of a reported event without a cell as **grey**, and a column of an unreported event as an empty cell — no claim about a pair the API did not evaluate.
- **Virtually rendered grid** (AGENTS.md "use Tabulator", §3.7). Each arm's `records` region is a Tabulator grid. The page renders the arm's table head — event column groups, instrument columns carrying their `data-col` keys — with a loading row; `record-status.js` reads that head as the column structure and builds the grid in the table's place: the record column frozen and sortable, the events as column groups, condensed and bordered like the other tables (`table-sm`). Rows and columns render virtually, so only those in view are in the DOM however many participants and (event, instrument) pairs the project holds; every row keeps one height (a repeating cell's dots stay on one line). An arm whose tab is hidden builds its grid the first time the tab is shown, from the same single fetch. Header and cell content is created as DOM nodes and never handed to the library as an HTML string (REQ-UI-004).
- **Navigation**: a record row (or a specific instrument cell) links to the data-entry / record view for that (record, event, instrument) — §8.
- **Repeating instruments** (REQ-UI-055, REQ-API-156). The column of an instrument repeating at that event (`repeating_events` of `GET …/instruments`, REQ-API-154) is marked ⟳. Its cell shows a dot per instance listed in the read's `instances` — each linking to the record view on that instance (`?event=&instrument=&instance=n`); the first five, then a **+k** link to the record view for the rest — or one grey dot for instance 1 when none is listed; then **+**, linking to the instance after the highest listed (1 when none). **+** is emitted only where the member may enter data on the pair (REQ-AUTH-069) and never in analysis mode (REQ-UI-035). The `records` region relays the instances as `instances: {<event>|<instrument>: [[n, state], …]}`; the header cell carries `data-repeating` and, where **+** is offered, `data-add`.
- The response MUST NOT contain field values (REQ-API-074); the dashboard reveals only the completion state.

### 6.4 Export action (`GET /projects/{id}/export`, REQ-UI-020)

- A control offering **CSV** or **JSON** (`format=csv|json`, default `csv`) — the two export formats of the master spec (REQ-API-075).
- **Arm selector** (REQ-UI-020): one checkbox per arm the member may export, all checked by default; the selection is sent as repeated `arm=` parameters. This is how a member with different levels on different arms obtains the higher sensitivity for a single arm — deselecting the weaker arm raises the applied level for that download (§4.3 of `Data_Export_Anonymization_Design.md`; REQ-EXP-003). A project with one arm hides the selector.
- **Values / headers** (REQ-EXP-010): a raw-vs-labels switch (`rawOrLabel`) and a header switch (`rawOrLabelHeaders`), mirroring the data API's axes — these are available on this surface too, not only on the data API.
- **CSV options** (REQ-UI-020, REQ-EXP-013/015/016, DEV-EXP-6), shown only while CSV is selected: the delimiter (comma, semicolon, tab, pipe → `csvDelimiter`), the decimal separator (period, comma → `decimalCharacter`), and a "mark the file as UTF-8 for Excel" checkbox. The form names each choice and the controller maps it to the character, so no character travels in the page URL. Their pre-selection follows the session's UI language: `nb` and `nn` (`ExportController::COMMA_DECIMAL_LANGUAGES`) start on semicolon, comma and the mark ticked — what Norwegian spreadsheet software reads as columns, numbers and `æøå` — every other language on comma, period and no mark, which are also the API's defaults. The user may change each before downloading. The mark is written by the PHP route ahead of the first proxied byte (`EF BB BF`); the API never emits one, and JSON downloads carry neither the mark nor the decimal option.
- **Sensitivity indicator**: a visible badge stating the level being applied for the selected arm(s) — `export_full` / `export_no_identifiers` / `export_de_identified` — so the user knows exactly what they are downloading (REQ-UI-020). For a multi-arm export the **lowest (most protective)** level among the selected arms is the one shown and the one applied (REQ-EXP-003, D-4) — never the highest any single arm would allow. The badge recomputes when the arm selection changes, so unchecking an arm visibly raises the stated level before the download starts.
- The download **streams** (REQ-TECH-011); the PHP route proxies the streamed response, so large exports do not buffer.
- **Data dictionary download** (REQ-UI-020): a second control beside the data form offers `?download=dictionary`, which streams the API's REDCap instrument ZIP (`GET …/instruments/export`, REQ-API-153) under the name the API gives it, `<project>_<YYYY-MM-DD>_<HHMM>.zip`: `instrument.csv` in REDCap's data-dictionary headings — every instrument's rows, its name in `Form Name` — and `OriginID.txt`. It is the file the instrument import reads (§7.6), so a design moves between projects. It carries design only, no record values, so the CSV options and the sensitivity badge govern the data download alone; a refusal becomes a flash line on the page like any other failure.
- **CDISC ODM download** (REQ-UI-069, REQ-ODM-005): an additional card appears only for `is_admin` and offers `?download=odm` with two selectors — a version selector for ODM 1.3 and 2.0 (1.3 selected by default) and a contents selector for **Project and data** or **Project only** (`odm_content=project_and_data|project_only`, the whole study selected by default, REQ-ODM-066) — streaming from `GET …/export/odm?odm_version=…&odm_content=…`. A project-only download is the study definition with no record values in it, so an administrator can hand a CRF to a partner without sending data. This is a separate whole-project interchange format; it does not inherit the tabular form's controls. The controller refuses a direct non-admin request and displays API refusals as a flash message.
- Gating: present only when the member holds a non-`export_none` level on at least one (instrument, event) pair (REQ-UI-017/020, REQ-API-075); no exportable pair at all → the card is absent (REQ-UI-003), and a partly permitted scope is stated on the card rather than hidden (REQ-UI-020).
- Every call is audit-logged with `surface:"ui"`, the project, and the sensitivity level (REQ-API-076, `Audit_Logging_Design.md` §3.5).

### 6.5 End-of-Project Provision (Overview card, `is_admin`, BR-009)

Present on Overview (§6.1) **only** for `is_admin` (REQ-UI-003; the action is `is_admin`-gated at the API, `API_Endpoints_Design.md` §4.20). The operator's cue is the REK end date in the §6.1 summary (`rek_end_date`, `Data_Export_Anonymization_Design.md` §7.1) — nothing runs automatically (no scheduler, `Project_Charter_Design.md` §5).

- **Action**: `POST` to the project route (CSRF, §3.3) → `POST /api/v1/projects/{id}/end-provision` (contract `API_Endpoints_Design.md` §4.20; rules `Data_Export_Anonymization_Design.md` §7).
- **Choice** — a radio pair in the confirmation modal:
  - `delete` — removes the project's stored record data (values, record entities, survey links, anonymization offsets); project metadata, structure, roles, and the audit trail remain (`Data_Export_Anonymization_Design.md` §7.3);
  - `anonymize` — applies the de-identified pipeline **in place**; every later read and export of the project returns the anonymized form — irreversible (§7.4).
- **Confirmation modal** (§3.5 — destructive and hard-to-reverse): states the chosen provision and the one-shot consequence, requires an explicit confirm click.
- **Result**: on 200, a success line naming the provision and the affected records/values; on 409 (already executed) the conflict line per §3.4.

### 6.6 Project mode (GD-20, REQ-UI-033)

Overview (§6.1) shows the current mode as a **badge** next to the project name — `development` / `production` / `analysis` — from `GET …/mode` (visible to every member; the header breadcrumb carries the same badge beside the project name in a project context, §2.4). Data pages state the active design they serve when a staging set is open (§6.7).

The **Mode card** (`is_admin` only — a project's own `project_admin` gets no mode control; REQ-UI-003) offers `PUT /api/v1/projects/{id}/mode` through `?action=` on the project route (CSRF, §3.3), presenting **only the allowed transitions**:

| Transition | Confirmation modal |
|---|------|
| development → production | asks whether previously stored data should be **kept or deleted** (radio pair); choosing delete states the consequence in full — every record value is removed, metadata/structure/memberships/audit remain (same scope as §6.5 `delete`) — and requires a second explicit confirm click (§3.5) |
| production → development | "all data is kept" |
| production → analysis | "all data is kept", plus the warning that data entry stops for everyone from then on (§8.1) |
| analysis → production | "all data is kept"; setup goes back behind staging (§6.7) |
| analysis → development | "all data is kept" — offered so a project can leave analysis without re-entering production (GD-20, 2026-09-27) |

**No transition is offered while a staging set is open**: the Mode card points at the staging banner instead (§6.7), and a stale page that posts anyway gets the 409 (§3.4).

`development → analysis` is never offered — analysis is entered only from production (`API_Endpoints_Design.md` §4.21). On success the badge updates and a translated line names the new mode; on 409 the conflict reason is shown per §3.4.

### 6.7 Staged setup changes in production (GD-20, REQ-UI-034)

When `mode = production`, the Setup (§6.2) and Designer (§7) pages carry the staging controls; in development they are absent and edits apply directly.

- **Start staging** button → `POST …/staging`. Once a set is open, every setup/design page shows a persistent banner: **"Staging open — your changes are staged, data collection continues on the active design"** with **Commit staged changes** and **Discard** (§3.5 confirmations for both).
- The pages then read and write the **staged** design (the API serves it to `project_admin`, `API_Endpoints_Design.md` §4.21); response shapes are unchanged, so every §6.2/§7 control works identically on the staged state. A "view active design" toggle links the plain reads for comparison.
- **Commit** opens a dialog fed by `GET …/staging`: the staged changes listed in two groups — **non-breaking** and **breaking**, each breaking entry with its reason (classification normative in `API_Endpoints_Design.md` §4.21). Committing is disabled until an explicit acknowledgement checkbox ("I understand these changes make existing data inaccessible") is ticked, then `POST …/staging/commit` with `{ "acknowledge_breaking": true }`; a commit without breaking changes posts directly. On success the banner closes and a line names the applied counts; on 409 (breaking not acknowledged) the dialog stays open with the list refreshed.
- **Discard** → `POST …/staging/discard` (confirmation naming the number of staged changes thrown away); the pages revert to the active design.

### 6.8 Setup changes in analysis mode (GD-20, REQ-UI-037)

Analysis mode keeps the Setup (§6.2) and Designer (§7) controls exactly as development has them — no banner, no staging buttons, edits save directly — and adds one interception (REQ-API-111):

- A save that the API rejects with 409 `conflict` naming a breaking change reopens the edit with a confirmation dialog above it: the change in plain words, the consequence from the API's reason string ("deleting a field removes its stored values"), and a **Delete anyway** / **Cancel** pair (§3.5).
- Confirming resubmits the identical request with `acknowledge_breaking: true`; success states that the change is live now, since nothing stages it and there is no commit to undo it from.
- Non-breaking saves are unaffected — no dialog, no extra click, so the guard costs nothing on the edits that dominate designer work.

The dialog text is the same string set the production commit dialog uses (§6.7), which keeps one classification vocabulary in the UI for both paths.

## 7. Instrument Designer (`project_admin`)

### 7.1 Instrument list and selection (`GET /projects/{id}/design`, REQ-UI-021, REQ-UI-067)

The designer lists the project's instruments in position order (`name`, `field_count`, `is_survey`, `branching_logic`); selecting one opens the field editor for it (§7.2, `GET /projects/{id}/design/instruments/{iid}`). The list is also where an instrument itself is made and changed (REQ-UI-067, DEV-UI-21 — formerly §6.2 block C), under the same mode rules as every other structure edit (§6.7/§6.8): controls absent while production has no open staging set.

* **Add** (`name`, unique per project) → `POST …/instruments` (REQ-API-065); a duplicate name is the API's 409, shown verbatim (§3.4). The new instrument collects no data until Setup maps it to an event (§6.2 block D, REQ-UI-018).
* **Reorder** (up/down) → `PUT …/instruments/order` with the **full** ordered id list; the GD-8 record-identifier invariant MUST hold after the change — a violation returns 400 and is shown per §3.4 (`API_Endpoints_Design.md` §4.10).
* **Edit** (name, survey flag, branching logic) → `PUT …/instruments/{iid}`, opened by `?edit_instrument=<iid>` as a card under the row and closed again by Save or Cancel (the same flow the arm rename follows, REQ-UI-048); invalid branching → 400 `validation_error` with the reason shown, REQ-VAL-029.
* **Remove** (confirmation modal, §3 — naming how many fields and values go) → `DELETE …/instruments/{iid}`; a surviving expression naming one of its fields → 409 shown per §3.4 (REQ-API-127). As the project's **last remaining instrument** it only deletes the fields and renames the instrument to `instrument` (200 with the object; the confirmation text says so, REQ-API-127). A new project already contains its first instrument `instrument` (REQ-API-050).

The strings of these controls keep their `setup.instrument.*` keys (`web/app/i18n/en.php`): the nb/nn drafts in `tools/i18n/` are keyed by them, and renaming would strand every translated row. The **instrument import** below the list (§7.6) is the other way in — whole instruments from REDCap dictionaries.

**Repeating** (REQ-UI-054, DEV-UI-17). A column of the list holds, per instrument, a dropdown whose button names the events it repeats at (*No* when none) and whose menu lists one switch per event of every arm (an arm heading when there are several): on where the instrument repeats, disabled with *not used at this event (Setup)* where it is not mapped. A switch submits the instrument's whole set at once — `POST …/design?action=save_repeating` → `PUT …/instruments/{iid}/repeating` (REQ-API-154) through the structure-write path of §6.7/§6.8 — and `design.js` hides the Save button that stands in without JavaScript. The first instrument, the record-identifier instrument, and a survey instrument show the reason they cannot repeat instead of switches; an instrument mapped nowhere points to Setup. The menu states that turning repeating off keeps the further instances, hidden until it is turned on again (REQ-DB-048). Where structure writes are closed (production without an open set) the switches show the state disabled. The menu uses Popper's fixed strategy so the responsive table does not clip it.

### 7.2 Field editor (`GET /projects/{id}/design/instruments/{iid}`, REQ-UI-021)

Data: `GET …/instruments/{iid}/fields` (fields in position order, all data-dictionary attributes — REQ-DB-013). Presentation: an ordered field table (name, label, type, required, position, section header) plus, per field, an **edit form** with the full attribute set:

| Attribute | Control | Notes |
|---|---|---|
| `field_name` | text | `^[a-z0-9_]+$`, unique in the project (409 on duplicate); **a warning — not an error — when > 26 characters** (REQ-VAL-013, REQ-UI-021); reserved names `redcap_event_name`/`redcap_repeat_instrument`/`redcap_repeat_instance` rejected (`Data_Validation_Design.md` §9) |
| `field_label` | text area (one row) | the question/description; a text area so a label over several lines — as REDCap's imported labels are — keeps its line breaks (§8.2) |
| `field_type` | select: `text` / `notes` / `dropdown` / `radio` / `checkbox` / `yesno` / `matrix` / `description` / `header` / `calculated` / `transfer` | type-specific sub-controls below; `yesno` (REQ-DB-043) and `notes` (REQ-DB-044) show neither the choice editor nor the validation type — the API fixes both; `transfer` shows the instruction textarea in place of the choice editor |
| `section_header` | text area (one row) | group heading in the form; keeps line breaks |
| `choices` | list editor: `code`/`label` rows | for `dropdown`/`radio`/`checkbox`/`matrix` — the `code$label##…` encoding (REQ-VAL-022); codes unique, letters, digits, `-`, `_` — a plain text input, no numeric keyboard — and for a `checkbox` lower-case letters, digits, `_` only; a `checkbox` requires at least one choice and exports one `___<code>` column per choice (REQ-DB-042); for a `transfer` field the control is instead a **raw textarea** holding the copy instructions (REQ-DB-050), mirroring the calculation editor of §7.3 — unparseable or unresolved instructions are rejected on save with the API's reason (§3.4, REQ-VAL-046) |
| `field_note` | text area (one row) | help text; keeps line breaks |
| `validation_type` | select: empty / built-in `integer` / `floating point` / `date` / `datetime` / every entry of the validation-type registry (`email`, `MRN`, `international phone`, `national phone`, … — listed from `GET /api/v1/validationTypes`, REQ-API-104) | + `validation_format` for date/datetime (§4.1 of `Data_Validation_Design.md`); `validation_min`/`max` for integer/float only (REQ-VAL-015/016/020); unknown names rejected at design time (REQ-VAL-010/042) |
| `required` | checkbox | REQ-VAL-028 |
| `personal_information` | checkbox | feeds anonymized export (REQ-DB-013) |
| `direct_identifier` | checkbox on any field; preset when the validation type is `email`/`MRN`/phone; clearing such a preset requires an explicit action and shows a warning | removed at de-identified export (REQ-EXP-020/021, DEV-EXP-5) |
| `matrix_group` | text | for `matrix` rows (REQ-DB-014) |
| `branching_logic` | expression editor (§7.3) | display-only logic (GD-13) |
| `field_annotation` | text area | REDCap action tags and notes, stored as given (REQ-DB-046); `@READONLY` makes the field read-only in the form and on the survey page (§8.2), other content has no effect |

**Actions**: **Add** (append at end, `POST …/fields`), **Edit** (`PUT …/fields/{fid}` — idempotent; rename renames stored values in-transaction, REQ-VAL-014), **Remove** (confirmation stating stored values are removed in-transaction, DEV-API-5; a field referenced by an active expression → 409, §3.4), **Reorder** (up/down) → `PUT …/fields/order` with the full ordered id list; the GD-8 record-identifier invariant MUST hold after reordering (400 on violation, §3.4).

**Move** (REQ-UI-056). Beside **Edit** and **Remove** each row carries **Move** (accessible name *Move field <name>*), which opens one dialog shared by the page: **Instrument** — every instrument of the project, the current one selected — and **Move before** — the fields of the selected instrument, `name — label` with the label shortened to 60 characters, then *(end of the instrument)*. `design.js` fills in the field the row names and, for another instrument, its fields from the page route's data region (§3.7): the Designer's region adds `instruments: [{id, name, fields: [{id, field_name, field_label}]}]` to `references`, every instrument read once, only when the dialog or the picker asks (Setup's region stays `references` alone). Confirming posts `POST …/design/instruments/{iid}?action=relocate_field` (`field_id`, `target_iid`, `before_field_id` — a field id or `end`) → `POST …/fields/{fid}/move` (REQ-API-157) through the structure-write path of §6.7/§6.8, and returns to the **target** instrument's field list with *Field "<name>" moved.*; a refusal — the record identifier while records exist (GD-8) — returns to the current one with the API's reason (§3.4). The dialog says that the field keeps its name and values, that the target instrument's events, repeating and access rights apply to it from then on, and that what the target does not show stays stored but hidden until the field is moved back (REQ-DB-049). Without an open staging set in production neither the buttons nor the dialog are emitted. The row buttons and the **Instrument** picker are emitted `disabled` and `design.js` enables them once it has wired the dialog: the dialog depends on the script for the field id and for every instrument switch, so a script that did not run — a stale cached copy, a failed load — leaves visibly inactive controls instead of a picker whose change re-populates nothing.

Every design-time rejection (ill-formed expression, unknown/inactive reference, cycle, malformed name) is shown with the API's `validation_error` reason (§3.4, REQ-VAL-029, REQ-UI-021/022).

### 7.3 Expression editors — branching logic and calculations (REQ-UI-021/022)

Both editors are the same component, configured per grammar:

- **Branching logic** (GD-13, `Data_Validation_Design.md` §7.1): references `[event][field]` (or the shorthand `[field]`, which resolves at the project's first event in canonical order GD-15), string/numeric constants, comparisons `= != < > <= >=`, functions `text_contains` / `is_blank` / `is_not_blank`, logical `&&` / `||`, parentheses — and REDCap's spellings `'…'`, `and` / `or`, `<>`, `[field(code)]` (REQ-VAL-044), which the highlighter colours like their counterparts.
- **Calculation** (GD-11, `Data_Validation_Design.md` §6.1): references `[event][field]`, numeric constants, `+ - * /`, parentheses.

Editor assistance (REQ-UI-021/022, "reference assistance"): a reference-picker that offers the project's **active** `[event][field]` references (from the data dictionary + mapping) for insertion, plus quick-insert buttons for the operators/functions of the active grammar. The editor is syntax-aware (highlighting references, constants, operators) but performs **no** validation — validation is the API's (design-time, REQ-VAL-029/034/035), and its rejection reason is shown inline (§3.4). Cycles in a calculation are rejected by the API (REQ-VAL-035).

### 7.4 Test a calculation (`REQ-UI-023`)

A panel on the calculated-field editor: a **record picker** (visible records, REQ-AUTH-045) + an optional **draft expression** field + a **Test** button → `POST …/records/{record}/fields/{fid}/test` (optionally `{ "expression": "…" }`; omitted = the field's stored expression, `API_Endpoints_Design.md` §4.11).

Presentation of the result: the computed **value**, and — **every evaluation problem flagged visibly** (REQ-VAL-038) — one line per problem: the offending operand + the `problem` code (`missing_value` / `non_numeric_operand` / `division_by_zero`). The test is a dry run: it MUST NOT store or modify anything (REQ-API-096).

### 7.5 Survey flag (REQ-UI-024)

Marking an instrument as a survey is the `is_survey` attribute in §7.1 / §7.2 (`PUT …/instruments/{iid}`). Consequences surfaced in the UI:

- Only survey-marked instruments can be filled via a public link (REQ-AUTH-038); the record view (§8.7) then offers the copy/revoke link actions for it.
- On survey instruments the trailing completion field (§8.5) shows the completed state read-only — filled in automatically, no dropdown, no assignment (GD-9; master spec "Instrument level completion info").

### 7.6 Instrument import (REQ-UI-053)

An **Import instruments** card below the instrument list of §7.1 imports REDCap instrument ZIPs and data-dictionary CSVs through `POST …/instruments/import` (`API_Endpoints_Design.md` §4.10, REQ-API-152). It is present where the page offers edit controls (production: only while a staging set is open, §6.7) and follows the mode rules of every structure write (§6.8). FIONA's setup is one folder of ZIPs per project; the person imports a folder's ZIPs into the project named after it, all at once.

1. **Choose files** — a multi-file picker (`accept=".zip,.csv"`) posted as `multipart/form-data` to `POST /projects/{id}/design?action=import_preview`. PHP reads the uploads, keeps them in the session until import or cancel, and calls the API with `"dry_run": true` and the files in **file-name order** — for FIONA's `Incoming` folder `IncomingStudies`, `Series`, `Transfers`.
2. **Preview** — rendered from the dry run:
   - the files in import order, each with up/down controls (`?action=import_reorder` — the order decides which field becomes the record identifier, so changing it runs the dry run again) and its origin (`OriginID.txt`, e.g. `fiona.ihelse.net`);
   - one line on the **record identifier** (GD-8): "`study_instance_uid` moves into `instrument` and becomes the record identifier", or "The record identifier stays `record_id`";
   - per instrument to be created, a condensed table (`table-sm`, §1) — row, field name, REDCap type → type here, validation, and a status: *new*, *converted*, *renamed from …*, *skipped* — with each warning's message beside its row;
   - **problems** above everything else, each naming its file and row (e.g. "`dictionary.csv`, row 12: form `demographics` was interrupted by `followup` at row 9"); while any problem is listed the **Import** button is disabled and the person corrects the file and chooses it again.
   Warnings need no acknowledgement.
3. **Import** — `POST /projects/{id}/design?action=import_instruments` sends the stashed files in the shown order without `dry_run`. Success clears the stash and returns to the instrument list with the flash message: "Imported N instruments with M fields. They collect no data until they are assigned to an event on the Setup page" — with a link to Setup block D (§6.2). The import never ticks a mapping (REQ-API-152). A refused import shows the API's problems the way the preview does (§3.4).

**Cancel** clears the stash. The stash holds the uploaded bytes only, never parsed content: the API is the only reader of the files (DEV-API-27).

## 8. Data Entry and Record View (`GET /projects/{id}/records/{record}`, REQ-UI-025…028)

### 8.1 Navigation and selection

Reached from the record status dashboard (§6.3): selecting a participant (record) opens this view; the user then selects the **event** and **instrument** (tabs/selects — the instrument must be mapped to the event, REQ-DB-012) to render the form. The unit of the form is a **(record, event, instrument)** triple (the "instrument display of a record", REQ-API-081).

**Instances** (REQ-UI-055). For an instrument repeating at the selected event the view shows one instance at a time — `?instance=n`, default 1, ignored for a form that does not repeat: the instrument list marks it ⟳ and carries **+** next to its name (the instance after the highest the record-status read lists; offered where entry is), and above the form a row of instance pills — every listed instance, instance 1, and the open one — with their states. The form posts `repeating=1` and `instance=n`; the save sends `redcap_repeat_instrument`/`redcap_repeat_instance` (REQ-API-155) and returns to the same instance; the completion control (§8.5) sends `instance`; the per-field history asks for `?instance=n`; the delete scope of the instrument becomes **Delete instance #n** (`repeat_instance`, §8.7). Prefill keys a further instance's values `<event>|<field>#<n>` from the history's `instance` (REQ-API-156); references outside the form read first instances (REQ-VAL-045).

Gating: the view requires data access ≥ `read_only` on the record's arm + record visibility (REQ-AUTH-045); **changing values requires ≥ `view_edit`** — a `read_only` member sees the values but the submit control is absent (REQ-UI-003, REQ-API-033). In an **analysis-mode** project the submit control is absent for everyone including `project_admin` — data entry is disabled (GD-20, REQ-UI-035); the form renders read-only with a translated "analysis mode — data entry is closed" notice, and the record-status dashboard's new-participant affordance (§6.3) is likewise absent.

### 8.2 Form rendering (REQ-UI-025)

The instrument's fields for the selected (record, event) render in position order. Field-type → control mapping:

| `field_type` | Control | Notes |
|---|---|---|
| `text` | `<input type=text>` (multi-line free text is a `notes` field) | free-text values render as their allowlist HTML on display (§3.2); validation type drives input hints (built-in integer/float/date/datetime; registry types — email, phone, … — drive the advisory `pattern` from the client-side copy of the registry, never trusted server-side, REQ-VAL-002) |
| `dropdown` | `<select>` | choices as `code`/`label` (stored value = code, REQ-VAL-022) |
| `notes` | `<textarea>` | multi-line free text (REQ-DB-044); renders as allowlist HTML on display like free-text `text` (§3.2) |
| `radio` | radio group | one input per choice |

| `checkbox` | checkbox group | one box per choice, each its own value column `<field_name>___<code>` (REQ-DB-042): a checked box posts `1`, an unchecked one nothing — a stored box the user unchecked is sent as an explicit empty under §8.6's policy. Read-only, the checked choices are listed. Branching reads a box as `1` while checked and `0` otherwise (REQ-VAL-044, `Data_Validation_Design.md` §7.3); a required checkbox is empty while no box is checked |
| `matrix` | a row per matrix sub-field (rows expanded, REQ-DB-014), sharing the group's choices/validation | the matrix header states the coding once (master spec) |
| `description` | static text (no input) | does not accept values (REQ-VAL `NON_VALUE_FIELD`) |
| `header` | section heading (no input) | |

**Date and date-time controls** (REQ-UI-072, DEV-UI-19). A `text` field whose `validation_type` is `date` with the default format `Y-m-d`, or `datetime` with the default `Y-m-d H:i`, renders as the browser's native date control — `<input type="date">` / `<input type="datetime-local">` — with an inline **now** button beside it that fills in the current date (and time) in the field's own format; any other `validation_format` keeps the `<input type=text>` and its placeholder, because a native control cannot express one. The native value form is mapped back to the storage grammar (`YYYY-MM-DD`, `YYYY-MM-DD HH:MM`) by the PHP layer before the import (REQ-VAL-041), and a date field whose control still shows the value it was opened with is submitted as its **stored** value — collection offset included — so GD-14's re-submission of untouched fields cannot re-stamp an offset the user never changed (§8.6). The control shows the day in the browser's locale; the read-only display, the per-field history and export keep showing the stored canonical form (§1).

**Read-only fields.** A field whose annotation holds `@READONLY` (REQ-DB-046) renders the way a member without edit rights sees it — the stored value as text, no input, marked *read-only* — here and on the survey page (§8.8). It takes no part in the change tracking of §8.6, and PHP drops any value posted for it before the import, reading the instrument's fields (record view) or the link's metadata (survey) to know which (the browser is not trusted); the data API can still write it. **Line breaks** in labels, section headers and field notes are kept: the text is escaped, then each newline becomes `<br>` (§3.2). **Required fields** are marked (label suffix + control styling) and checked before submission (REQ-VAL-028, REQ-UI-025). **Branching logic** (field and instrument level) shows/hides fields and whole instruments while the expression evaluates to 1 — evaluated client-side per §8.4, re-evaluated when a referenced value changes (GD-13, REQ-VAL-040). A hidden instrument hides all its fields (REQ-VAL-040).

**Record identifier (GD-8).** The record-identifier instrument is the earliest instrument by position that has fields, and its first field by position is the identifier regardless of its name. That field displays the record's name even when the selected event has no stored value for it. It is read-only in both record-naming modes and is never submitted as an editable field; changing it requires a separate record-rename operation, which is not yet available.

**Transfer buttons** (REQ-UI-065). A `transfer` field renders as a standalone button in the form flow — it has no input, carries no value, and posts nothing on submit (§8.6); its label and note render like any other field's. The page asks the availability probe once per instrument — `GET …/records/{record}/transfers?instrument=…` (`API_Endpoints_Design.md` §4.27) — alongside the form's other data, and emits the button only when the member may edit (§8.1, ≥ `view_edit`) **and** the probe answered enabled for that field; otherwise it is **absent — never merely disabled** (REQ-UI-003), with no reason shown for its absence because the probe discloses none (REQ-API-166). Pressing it opens a confirmation naming what will be created or updated (§3.5's modal pattern); on confirm the form posts `?action=transfer` to `RecordController` with the field name and the (event, instrument) context, and PHP calls the execute endpoint `POST …/records/{record}/transfers` with the member's administration identity (the button rides the administration API, never the member token — DEV-API-31). Success flashes naming the target record — created or updated per the response (`Transferred to followup / MOBA042`); a failure maps through §3.4: the uniform 403 line for any denial, `validation_error` shown verbatim (it names the unexecutable design or rejected value, REQ-VAL-029). On the survey page (§8.8) the field renders as nothing (REQ-UI-065).

### 8.3 Current values and per-field history (REQ-UI-026)

Both come from the **record history endpoint** `GET …/records/{record}/history?instrument=&event=` (data access ≥ `read_only`; paginated, `API_Endpoints_Design.md` §4.16 — prefill reads it most-recent-first with `order=newest`, REQ-API-137):

- **Prefill**: each field's **current value** is the most recent non-null value for that field across the (instrument, event)-filtered history (a `create`/`update` entry's `new`; a trailing `delete` → empty). The form opens with existing values filled into all fields (master spec: "existing values filled into all fields").
- **Per-field history button + table** (REQ-UI-026, REQ-API-081; master spec "Record history by field"): next to each field's description and value sits a small **history button**; clicking it opens a table of that field's previous values — **who** entered or changed each one (user account display name), **when** (UTC), and the **old → new** values; for deletions the deleted value. It fetches `GET …/records/{record}/history?instrument=&event=&field=` (the field filter of REQ-API-080) and pages with `limit`/`cursor`. A checkbox's history is that of its boxes (REQ-DB-042): the filter on its name matches every choice column, and each change names the box it belongs to. The table is a read-only overlay (Bootstrap modal or popover, §3 per the destructive-action pattern's shell only): no control writes to it — the view stays read-only with respect to the audit trail (REQ-AUD-002). Values escaped per §3.2.
- The UI pages through the filtered history with `limit`/`cursor` (§3.6) to derive the current values and the per-field lists. Prefill reads with `order=newest` (REQ-API-137, DEV-API-23): walking most-recent-first it stops per field at the first entry seen, so opening a form costs pages over recent changes instead of the record's whole history (§11 item 3 — resolved).
- **Opening the record is recorded** (REQ-AUD-035): before the form reaches the browser, PHP calls `POST …/records/{record}/read?event=&instrument=&instance=` (`API_Endpoints_Design.md` §4.28, REQ-API-167), which writes one `record_read` event naming the record and the triple about to be displayed — no values, `source=ui`. A call that fails for any reason renders §3.4's error instead of the form, so a stored record is never shown unrecorded (REQ-AUD-033's order); the new-record form skips the call, having nothing stored to disclose, and so does a render with no instrument to show the record on (REQ-AUD-004). The history endpoint stays side-effect-free (REQ-AUD-002), so one page view costs exactly one entry however many pages the walk above needed. The trail answers "who opened this record" from the Control Panel's **Events** log (`record_read`, §5.6) beside "who pulled it" in **Record views**.

### 8.4 Client-side validation and branching (advisory, REQ-VAL-002)

- **Advisory validation**: as the user types, the record module (`web/assets/js/record.js` — REQ-UI-045) validates the value against the field's type/choices/min/max (`Data_Validation_Design.md` §4) and marks required empties (REQ-VAL-028). A client pass is **not** a guarantee — the API is authoritative and re-validates every value before storage (REQ-VAL-001/002); a server rejection is shown per §3.4/§8.6.
- **Branching evaluator**: the same vanilla-JS evaluator implements the normative semantics of `Data_Validation_Design.md` §7.3 (operand resolution, choice-label→code, comparison kinds, truthiness, functions, `&&`/`||`) and re-runs on any referenced field's change (§7.4). It is **display-only**: it never blocks or alters the submitted values (DEV-VAL-5) — the API stores what is sent. One module implements it, imported by both the data-entry form and the public survey page (§8.8), so the two cannot diverge.

### 8.5 Completion state per instrument (master spec)

At the **end of each instrument's form — always displayed as the last field** (master spec "Instrument level completion info") — a **dropdown** lets the user set that (record, event, instrument)'s completion state: *no data / some data / finished*. Selecting "finished" is the user's completion assignment that drives the green color-code in §6.3. The dropdown is present when the member has data access ≥ `view_edit` on the arm. On a **survey-marked instrument** the same trailing field instead shows the completed state **read-only** — filled in automatically (green, §6.3), no control and no assignment (§7.5, GD-9).

The control maps onto one call — `PUT …/records/{record}/events/{event}/instruments/{iid}/completion` (REQ-API-110, `API_Endpoints_Design.md` §4.13): **finished** → `{ "state": "finished" }`; **no data** or **some data** → `{ "state": "unfinished" }`, after which the dashboard re-derives which of those two to show from the stored values (REQ-API-074). The two non-finished choices are therefore one action, not two — the UI never asserts a filled/empty state the data contradicts, and the dropdown's current selection for an unfinished instrument reflects the derived state rather than a stored one.

> **Backend (Open Item 1, §11 — resolved):** the assignment persists in `instrument_completion` (REQ-DB-036) and is returned by `record-status` as the third state; each set or clear is audit-logged (REQ-AUD-026).

### 8.6 Submitting values — the data-API import path (ASM-API-3, REQ-API-031/035)

The form `POST`s to the PHP route (CSRF token, §3.3). PHP then, server-side:

1. **Obtain the member's project token.** From the session cache (`proj_token_{id}`) if present; otherwise call `GET /api/v1/projects/{id}/users/{uid}/token` (**self-service fetch, REQ-API-102** — `{uid}` is the acting member) and cache the result in the session for that (user, project). This is the only sanctioned source: the session stores it as a **cache** (invalidated per step 3), never as an authorization input (permissions stay API-derived, REQ-AUTH-033 — this refines, not overrides, `Authentication_Authorization_Design.md` §3).
2. **Present it to the data API**: a `data`-carrying `content=record` call (REQ-API-012) with the form's values as `data[]` entries for the (record, instrument, event) (`API_Endpoints_Design.md` §3.7) — **submission policy (GD-14, REQ-UI-031):** the `data[]` payload contains exactly (a) the fields that **carry a value** in the form, and (b) the fields that **had a stored value that the user removed** (the client tracks each field's prefill value of §8.3 and sends an explicit empty string for those). Fields that had no value and were left empty are **not sent at all** — an empty value reaching the API clears the stored value (REQ-VAL-024), so unsent fields keep their previous values and a partially filled instrument stores only what was entered. For date/date-time fields the call carries the browser's timezone as the collection zone (the `tz` parameter — GD-16, REQ-VAL-041, §1). The API validates every value (REQ-VAL-001), stores all-or-nothing per record (REQ-API-035), and recomputes calculated fields in the same transaction (REQ-API-095). A new record is assigned to the member's active data-access group or none (REQ-API-093).
3. **Stale-token handling**: if the data API answers **401 `Invalid token`** (the token was rotated/revoked since the cache, REQ-AUTH-030), PHP discards the cached token, re-fetches per step 1, and **retries once**. A **403** is a permission result — it is surfaced per §3.4 and NOT retried.
4. **Render the result** (`API_Endpoints_Design.md` §3.7.2): per record — `import_record_id` `1` (added) / `2` (updated) → a success line; `0` → the per-field validation detail from `import_form_name` (rule codes + messages, `Data_Validation_Design.md` §3) listed per field, with the offending inputs highlighted. The completion dropdown (§8.5) submits alongside, as part of the same PHP action.

All successful imports are audit-logged with user, token, record, and changed fields (REQ-API-035, `Audit_Logging_Design.md` §3.2) — the UI shows no audit data for this (the per-field history panel, §8.3, is the read side).

### 8.7 Record actions (REQ-UI-027)

Present per the member's levels (REQ-UI-003):

- **Delete** (**delete instrument values** on the pair; for a whole record, on every pair where it holds values): delete the whole record or scoped values (by instrument/event), behind an explicit confirmation naming the scope (GD-3, REQ-API-036). PHP presents the member's token to the data API `content=record&action=delete` (same acquisition/stale handling as §8.6). Deletions are audit-logged **with the deleted values** (REQ-AUD-009).
- **Data access group** (record visibility, REQ-AUTH-045): show the record's current group; for `project_admin` — an assign/change control (group select incl. "none") → `PUT …/records/{record}/data-access-group` (REQ-API-091). Members who are not `project_admin` see the group read-only.
- **Survey link** (survey-marked instruments, data access ≥ `view_edit` on the pair): its **state** — never issued / live / submitted on <date> / revoked — read from `GET …/instruments/{iid}/survey-link` (`API_Endpoints_Design.md` §4.17), with **Copy link** beside it while it is live (one link per (record, instrument, event), `Database_Schema_Design.md` §8); **Get a new link** → confirmation → `POST …/survey-link`, which replaces the live token and is refused 409 while this instrument still holds values for this record at this event — the message points at the delete action above rather than leaving the member to find it (REQ-API-146, REQ-UI-028); **Revoke link** → confirmation → `DELETE …/survey-link` (effective immediately, REQ-AUTH-040). Absent for non-survey instruments (REQ-AUTH-038). **A participant not stored yet** (opened from §6.3, nothing imported): there is no link to report — the API answers 404 for a record it does not hold — so the section states "never issued", says that getting the link stores the participant, and offers **Get link** → a confirmation naming exactly that → PHP first sends the import a save of the empty form sends (`content=record&action=import` with the identifier alone at the selected event — GD-8, §8.6; the form carries `create_record=1`), which creates the record in the member's active group and audits its creation (REQ-API-093), then `POST …/survey-link`; the redirect back renders the live link with **Copy link**. A refused import issues nothing and its reason is flashed; analysis mode removes the control, since that import would be refused (REQ-UI-051, REQ-UI-035).

### 8.8 Public survey page (`GET /s/{link}`, GD-9, REQ-UI-028)

A standalone PHP route — **no login, outside the session** (GD-1, REQ-API-084, DEV-UI-1), rendered as a single centered panel with no left panel and no account menu (§2.4). The link is `WEB_PUBLIC_URL + /s/<link token>` — the path the API itself builds when it issues the link (`API_Endpoints_Design.md` §4.17), so the value handed to `Copy link` and the route that serves it cannot drift apart.

- **Render**: PHP calls the **data API** `content=metadata` with the link token — the API admits a **live** link only to the calls that render and fill its (record, instrument, event) (REQ-API-083, `API_Endpoints_Design.md` §3.10); the page shows **only** that instrument's fields for that record — a `transfer` field renders as nothing there, its instruction text never reaches the participant (REQ-UI-065). The form is **never pre-populated**: reading back answers already given needs a read no link holds (`content=record` without `data` is the export path, 403 for a link), and under one-submission links there is nothing to re-open over — a second fill starts from an empty form reached by a new link (REQ-UI-028). Because the submission policy sends only entered values, an untouched field cannot blank what is stored (GD-14, REQ-UI-031).
- **Submit**: PHP → data API `content=record` carrying `data` (REQ-API-012) with the link token, applying the same **submission policy** as the data-entry form (GD-14, REQ-UI-031 — entered values plus explicitly cleared fields only) and sending the respondent's browser timezone as the collection zone (GD-16). The row names **no** record, instrument or event: the API resolves all three from the link, which is why the page never learns the study's record identifier (`API_Endpoints_Design.md` §3.10, REQ-API-083). Submissions pass the **same validation and audit rules as any import** (REQ-AUTH-041, REQ-VAL-001; audit `survey_submitted` — success and failure, `Audit_Logging_Design.md` §3.6). An accepted submission ends the visit on a translated closing panel that states the link cannot be used again (REQ-API-145) — the thank-you page is where the one-time rule is told, not a footnote in the form.
- **One submission per link**: the store that accepts the row consumes the link (`API_Endpoints_Design.md` §3.10, REQ-API-145), so re-opening that URL answers 410 and the page shows a translated "you have already submitted this survey — contact the study team to change an answer" state instead of a form. Changing an answer is a member action: edit under **edit collected surveys**, or clear the instrument's values and issue a new link (REQ-AUTH-042, REQ-UI-027). A row the validator rejected stores nothing and does **not** consume the link, so the respondent corrects on the spot and sends again.
- **Branching**: the same client-side evaluator (§8.4) applies — fields/instruments show or hide per their logic (GD-13, REQ-VAL-040).
- **Unknown or revoked link**: the API answers 401 `Invalid token` (REQ-AUTH-011, REQ-AUTH-040) — one translated "this link is no longer valid" state, no retry. It is deliberately not the page a spent link shows: 410 tells the respondent their answer arrived, which is exactly what keeps a finished submission from being reported as a broken link.
- **Analysis mode**: while the project is in analysis mode the import is rejected (`Project in analysis mode`, REQ-API-109) — the page shows a translated "this survey no longer accepts responses" closed state (GD-20). No call a link token may make reports the project's mode, so this surfaces on submit rather than on render.
- The browser **never** calls `/api/v1/*` from this page (REQ-UI-002, REQ-API-084); the CSRF/session rules of §3.3 do not apply (no session) — the link token is the sole credential, and it is scoped to this one (record, instrument, event) by the API (REQ-AUTH-039).

## 9. Multilingual (GD-12, REQ-UI-008/029/030)

- **Language selector** (account page — Profile, §2.8): a `<select>` of the enabled languages (`GET /api/v1/i18n/languages` — code + display name; any authenticated user, REQ-API-097). Choosing one `POST`s to the PHP route → `PUT /api/v1/users/me/ui-language` (REQ-API-098); the setting persists across sessions (REQ-DB-008) and applies **from the next page load** (the current page is already rendered). Users without a setting get English (the default, REQ-API-098).
- **Server-side resolution** (REQ-UI-008, REQ-TECH-001): every UI string — page text, labels, buttons, alerts, the §3.4 error messages — is resolved at render time via the mapping tables (REQ-DB-031) or **falls back to English**; a blank or a raw key is never rendered (REQ-UI-008). Translated strings are escaped on render (§3.2).
- **JavaScript-originated messages** (REQ-UI-008: "including JavaScript-originated messages"): since no i18n library is allowed, the server injects the page's small set of JS-visible strings as a single JSON object in a `<script type="application/json" data-i18n>` element (values escaped/JSON-encoded server-side); the shared runtime reads it once and exposes it to the page's modules (§3.7), which use those strings for toasts, confirmation texts, and the advisory-validation hints of §8.4 — a module never carries a UI string of its own (REQ-UI-045). The JSON contains **no** data values — only UI copy.
- **Translation management**: §5.7 (add/change/clear per language, missing-key visibility, empty text = removal → English fallback).
- The language setting applies to **UI strings only** — never to stored data, field labels, or choice values (GD-12, REQ-UI-008).

## 12. Implementation rules (enforced at review)

The web-layer rules most likely to be got wrong, gathered from code-level facts of the API. They bind every change to `web/` beyond any one delivery and are checked at review; code and tests cite them as "§12 rule N". Moved here on 2026-10-28 from `Plan/Web_Implementation.md` §7 with the numbering kept.

1. **Attribute whitelists.** Admin writes 400 on unknown attributes; each form's payload must match the endpoint's accepted set exactly (`REQ-API-042` idempotency assumed, not verified per field).
2. **Never call `GET …/instruments/{iid}/fields/order`.** It routes to the reorder handler and needs a body (`api/internal/admin/structure.go`). Field order comes from `GET …/fields`.
3. **Negative provisional ids.** While a staging set is open, objects created in it carry negative ids and structure reads return the staged snapshot (`api/internal/admin/admin.go`, `staged_design.go`) — forms and links must tolerate them.
4. **Project creation already seeds arm 1 and a `baseline` event** (`api/internal/admin/projects.go`). Do not create them from the UI; offer the link into setup instead (§5.2).
5. **Roles are editable, not deletable** — `PUT /api/v1/projects/{id}/roles/{rid}` (REQ-API-143) replaces a role's name, arm defaults and pair grants in one call, so the roles screen is one form in create or edit mode (§5.4). There is still no role delete and no user delete (disable only), and the UI offers neither. Deleting a role would leave its members' `role_id` null, which reads as *full permissions* (`REQ-AUTH-022`) — a deletion endpoint must not be added without first closing that fail-open path (master-spec finding F20).
6. **Login's 2FA responses are non-standard 401s** (`mfa_required` with `method`, `tfa_enrollment_required` with `user_id`) — branch on `error`, not on status alone; the enrollment wizard runs pre-session using that id as `X-Internal-User-Id`. A local challenge resumes with the signed first-factor handle (`REQ-API-131`, DEV-API-19) and never with the password, and 401 `first_factor_expired` clears the pending state back to the credential form rather than showing a failure line.
7. **Token cache discipline (§8.6).** Fetch the member's project token via `GET …/users/{uid}/token`, cache per (user, project) in the session, and on data-API **401 `Invalid token`** discard + refetch + retry exactly once; a 403 is a permission result and is never retried.
8. **Submission policy (GD-14).** Send only fields carrying a value plus fields whose stored value the user removed (tracked client-side against the §8.3 prefill). An empty value that reaches the API clears the row (`REQ-VAL-024`).
9. **Time handling.** Display system timestamps as returned (UTC `YYYY-MM-DD HH:MM:SS`); display clinical dates exactly as stored, offset included; send the browser zone as `tz` on import (`GD-16`). No locale reformatting anywhere.
10. **Rate limiting and lockout.** Forward `X-Real-IP` as `Request::clientIp()` derived it — the connection address unless a peer listed in `TRUSTED_PROXY_CIDRS` forwarded another, so a browser cannot rotate addresses past the limiter (finding F9); surface 429 with the retry/lockout duration on login and reset (`REQ-AUTH-035`).
11. **Log hygiene.** Tokens, the service secret and record values never in logs at any level (`REQ-API-005`); audit payloads displayed escaped, never copied into other page elements (§5.6).
12. **Status codes.** `DELETE` returns 204, creates return 201 (member add included — that response carries the one-time token), most mutations 200. Do not branch on 200 uniformly.
13. **Bounded API calls per render.** `REQ-TECH-010` targets < 300 ms p95: no N+1 fan-out per table row (the FIONA `admin.php` refetch-three-endpoints-then-fan-out-per-row pattern is the anti-pattern to avoid); one bundle fetch for i18n; cursor and filters live in the query string so a page reloads (§3.6).
14. **Prefill cost.** Current values come from paging the record-history endpoint with `order=newest` (`REQ-API-137`): walk most-recent-first and stop per field at the first entry seen, so a form open costs pages over recent changes, not the whole history. Measure with seeded data — if it hurts even backwards, that is another API addition, not a UI workaround.
15. **The permissions block is disclosure, not a credential.** Fetch `GET /api/v1/projects/{id}` once per project page and hand the levels to templates through `Permissions.php` — never re-request it per widget, and never carry levels into the session (they go stale; `REQ-AUTH-033`). It answers rendering only: whatever is shown still has to survive the API's own check.
16. **Content negotiation belongs to the router.** One dispatch in `Router.php` decides page vs data region from `Accept` (`REQ-UI-044`); a controller or template that inspects the header, re-implements the split, or reaches for its own `/json` route is a defect — as is a data region whose payload discloses more than the same user's rendered page would.
17. **One module per section, no bundler.** Section behaviour goes in `web/assets/js/<section>.js`, loaded by the pages that need it through the shared runtime (`REQ-UI-045`); shared code is imported, not duplicated — and no fix for the file count may introduce a build step (`REQ-TECH-001`).
