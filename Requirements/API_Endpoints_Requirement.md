# API Endpoints — Requirements Analysis

**Project:** Clinical Study Management System (REDCap API Replacement)\
**Source plan:** `Plan/API_Endpoints.md`, `VISION_AND_REQUIREMENTS.md` (master spec)\
**Status:** Approved for development handoff\
**Date:** 2026-09-18

## 1. Purpose

Defines the API surface requirements: the REDCap-compatible data API for external callers (Fiona/RIS) and the administration API used exclusively by the PHP web application. `Design/API_Endpoints_Design.md` contains the normative endpoint contracts: parameter tables, request/response schemas, and error formats.

## 2. Common Requirements (both surfaces)

| ID | Requirement |
|---|--------|
| REQ-API-001 | A single Go API process (REQ-TECH-003) MUST expose exactly two API surfaces: the REDCap-compatible data API at `/api/` and the administration API under `/api/v1/`. No application endpoints MAY exist beyond these, the API documentation, and the health endpoint (REQ-API-003). |
| REQ-API-002 | Both surfaces MUST be described by an OpenAPI (Swagger) specification and served at a stable URL with an interactive documentation UI (REQ-TECH-004, BR-005). |
| REQ-API-003 | An unauthenticated health/readiness endpoint (path per design document) MUST report process and database liveness without returning data. |
| REQ-API-004 | All **system** timestamps in requests and responses (audit, `created_at`, `creation_time`, history, …) MUST be UTC (GD-7, as scoped 2026-09-22); clinical date/date-time **values** carry their collection timezone in the canonical form (GD-16, REQ-VAL-041). All string content MUST be UTF-8. |
| REQ-API-005 | Tokens, the service secret, and record values MUST NOT appear in application logs at any log level (REQ-TECH-016). |
| REQ-API-006 | Administration API errors MUST be JSON objects with a consistent shape (`error` machine code, human-readable `message`, `status`); stack traces and internal details MUST NOT be exposed. |
| REQ-API-007 | Access to a project or record the caller is not entitled to MUST be rejected without disclosing its existence (consistent 403/404 semantics); a project is visible only to `is_admin` or members (BR-010, REQ-AUTH-026). |
| REQ-API-008 | The administration API is versioned in the path (`/api/v1/`); breaking changes MUST be introduced only under a new major version. |

## 3. REDCap-Compatible Data API (`/api/`)

### 3.1 Protocol

| ID | Requirement |
|---|------|
| REQ-API-009 | All REDCap protocol operations MUST be available on a single endpoint, `POST /api/` with a form-encoded body (`application/x-www-form-urlencoded`). `GET /api/` MUST be refused as 405: the token travels in the request body (REQ-API-010), so a GET is a request that cannot authenticate, and a URL is what proxies log (DEV-API-30, master-spec finding F19). |
| REQ-API-010 | The caller's token MUST be read from the `token` **request-body** parameter only — never from the query string, and never from an `Authorization` header (GD-5, REQ-AUTH-031, DEV-API-30). A request whose query string carries a `token` MUST be refused as a 400 naming the fix, before any token lookup and without echoing the value: a caller still sending the credential in a URL has to be told what to change rather than answered `Invalid token`, which REQ-API-011 reserves for credentials that were actually wrong. Parameters other than `token` keep their query-string fallback (DEV-API-30). |
| REQ-API-011 | A missing, invalid, or disabled token MUST produce HTTP 401 with a REDCap-style `Invalid token` error in the requested response format, without disclosing whether the token exists (REQ-AUTH-032). |
| REQ-API-012 | Every call MUST specify a supported `content` value: `project`, `metadata`, `event`, `formEventMapping`, `exportFieldNames`, `generateNextRecordName`, or `record`. For `content=record` the operation is decided by the request itself, as REDCap does: a call carrying a `data` parameter is an **import**, one without it an **export** (the recorded callers of the replaced system send no `action` at all — DEV-API-24); deletion MUST be requested explicitly with `action=delete`. An explicit `action` of `export` or `import` stays accepted and never overrides the `data` rule. Unknown or missing `content`, or `record` with any other `action` value, MUST be rejected with a REDCap-style error. |
| REQ-API-013 | `format` and `returnFormat` MUST accept `json` and `csv`; when omitted the response MUST default to `csv` (REDCap default) and a present `returnFormat` MUST take precedence for the response encoding. |
| REQ-API-014 | `type` MUST accept `flat` and `wide`; when omitted it MUST default to `flat` (REDCap's default). `flat` (used by all known callers) is normative: one row per (record, event). `wide` MUST be accepted for caller compatibility with the simplified semantics of DEV-API-1. |
| REQ-API-015 | Array parameters (`records[]`, `fields[]`, `forms[]`, `events[]`) MUST be accepted both in REDCap array syntax (`records[0]=…&records[1]=…`) and as repeated single values. |
| REQ-API-016 | The parameters `exportSurveyFields` and `exportDataAccessGroups` MUST be accepted without error and ignored (these REDCap flags stay out of scope; surveys per GD-9 and data access groups per GD-10 do not change the handling of these parameters; DEV-API-2). `exportCheckboxLabel` MUST be accepted and honored as in REDCap: it selects how a label export writes checkbox values (REQ-EXP-053). |
| REQ-API-017 | Unknown parameters MUST be accepted and ignored, never rejected, so that existing callers sending extra parameters keep working. |

### 3.2 Read operations

| ID | Requirement |
|---|------|
| REQ-API-018 | `content=project` MUST return the project identification (id, name/title, description, PI name/email, REK/IRB number, start/end dates, creation time); any valid token for the project suffices. Standard REDCap project-info keys the system does not store (e.g. `surveys_enabled`, `randomization_enabled`, and `project_end_provision` since GD-17) MUST be returned with neutral values (`0`/`\"\"`/`false`) rather than omitted, so naive parsers keep working (master spec example response). |
| REQ-API-019 | `content=metadata` MUST return the full data dictionary in REDCap metadata shape (field name, instrument, section header, field type, label, choices, note, validation type/min/max, required, branching logic, matrix group, field annotation `field_annotation` — REDCap's own key, REQ-DB-046 —, identifier flag `record_identifier`), plus this system's `direct_identifier` flag as an additional key (REQ-DB-013 — extra keys are tolerated by naive parsers, cf. REQ-API-018), with matrix rows expanded per REQ-DB-014, and MUST additionally carry REDCap's combined `select_choices_or_calculations` key beside `choice_codes`/`choice_labels` (`code, label \| code, label`; the calculation expression on a calculated field, empty elsewhere) so REDCap-keyed parsers find their column. Requires data access level ≥ `read_only` (GD-2). |
| REQ-API-020 | `content=event` MUST return one row per event with `event_name`, `arm_num`, `unique_event_name`, `custom_event_label`, `event_id` (master spec; `custom_event_label` is not stored and is always `null`, an empty cell in CSV), **in the canonical per-arm order** (GD-15, REQ-DB-011: timepoint events by `period` ascending — ties by position — then no-timepoint events by position). Requires data access level ≥ `read_only` (GD-2). |
| REQ-API-021 | `content=formEventMapping` MUST return the instrument-by-event mapping per arm (instruments, events, arm, mapping flag). Requires data access level ≥ `read_only` (GD-2). |
| REQ-API-022 | `content=exportFieldNames` MUST return the project's field names, restricted to the given `forms[]` when supplied. Requires data access level ≥ `read_only` (GD-2). |
| REQ-API-023 | `content=generateNextRecordName` MUST return the next record name following the project's participant naming pattern, supporting both styles of REQ-DB-007 (digit placeholders `8DISC[0-9][0-9][0-9]` and counter prefix `0001_01` with preserved width), and MUST NOT return a name that an existing record already holds. The next name is derived from the greatest existing record name of the same shape (max + 1); names freed by deleted records are NOT reused — gap-filling is not desired (e.g. with `0001_01` and `0003_01` present after `0002_01` was deleted, the result is `0004_01`). Requires data access level ≥ `view_edit` on the target arm (GD-2). |

### 3.3 Record export (`content=record` without `data`, REQ-API-012)

| ID | Requirement |
|---|------|
| REQ-API-024 | The export MUST honor optional filters `records[]`, `fields[]`, `forms[]`, `events[]` (combined); with no filters, all records of the project visible to the holder under the data access group rule (REQ-AUTH-045) MUST be returned. |
| REQ-API-025 | `filterLogic` MUST be supported: at minimum equality conditions on string fields of the form `[field]=\"value\"` (Fiona's use case, master spec); compound conditions (`&&`, `||`) and comparison operators SHOULD be supported per the design document. A field reference without an event (`[field]`) MUST resolve against the project's **first event** in canonical order (GD-15) — the fallback defined by `Data_Validation_Design.md` §7.1. The expression reads only what the response delivers verbatim: every reference MUST name a value the caller's export level carries untransformed at the pair it resolves to, so a pair the caller may not export, a stripped direct identifier, a hashed personal field, an unapproved free text and a shifted date are all out of reach (REQ-EXP-054). Such a reference MUST be refused **before any record is read**, as a 400 carrying the body an unparseable expression answers — one answer for every reason, so the filter enumerates no field the caller may not read (REQ-API-039) — with nothing written to either audit table (REQ-AUD-004). The bound is the level and never the `fields[]`/`forms[]` selection: a value the caller may export but did not request stays filterable. |
| REQ-API-026 | The sensitivity of the export MUST be determined by the token holder's export level **for the (instrument, event) pair of each exported column** (GD-2, REQ-AUTH-017/069): `export_full` → full dataset; `export_no_identifiers` → all identifier fields removed; `export_de_identified` → de-identified per `Data_Export_Anonymization_Requirements.md`; `export_none` → **that pair contributes no columns** (REQ-API-075). A request whose requested scope contains no permitted pair at all is rejected 403 with nothing written to either audit table (REQ-AUD-004). |
| REQ-API-027 | `rawOrLabel` MUST accept `raw` (default) and `label` (choice labels for dropdown/radio fields, `Yes`/`No` for yesno fields — REQ-DB-043); `rawOrLabelHeaders` MUST accept `raw` (default), `label`, and `both` for field names. |
| REQ-API-028 | Export rows MUST contain the record identifier's value under its field name (GD-8) — in both layouts, and also when a `fields[]` or `forms[]` filter leaves the identifier out (it is then added without bringing its instrument's columns or completion into the export) — a `redcap_event_name` per row for projects with events (flat), and empty strings for missing values — matching the response shapes in the master spec examples. With `rawOrLabel=label`, `redcap_event_name` MUST carry the event's name as REDCap writes it: `<event_name>` in a project with one arm, `<event_name> (Arm <n>: <arm name>)` otherwise (the arm name defaulting to `Arm <n>`). An export listing only the record identifier (`fields[]=<identifier>`) MUST return one row per (record, event) that holds data. |
| REQ-API-029 | CSV export MUST be streamable (REQ-TECH-011), MUST honor `csvDelimiter` with the value set of REQ-EXP-013 (empty value = default comma), and MUST quote fields per standard CSV rules; formula-triggering leading characters MUST be neutralized per REQ-VAL-032. Record export MUST honor `decimalCharacter` (REQ-EXP-015); no response carries a byte-order mark (REQ-EXP-016). |
| REQ-API-030 | Every record pull via this action MUST be written to the record-view audit table with the token, records, and instruments accessed (BR-007; `Audit_Logging_Requirements.md`). |
| REQ-API-134 | Every export row MUST end each instrument's field block with an `<instrument>_complete` column carrying that instrument's three-state completion for the row's position as `0` (not complete), `1` (in progress) or `2` (complete) — the same state the record-status dashboard derives (REQ-API-074, REQ-DB-036): stored `finished` → `2`, else any value of that instrument at that position → `1`, else `0`; a never-marked instrument therefore exports `0`, never an empty cell, wherever it is mapped to the row's event. At an event the instrument is **not** mapped to there is no pair and no state: the cell MUST be empty, as in REDCap — a survey-marked instrument included. A survey-marked instrument always exports `2` (GD-9) where it is mapped. A `finished` assignment on an unmapped (event, instrument) pair stays invisible until the pair is mapped back (REQ-DB-036). The column belongs to whole-instrument exports — it appears when the export keeps an instrument's field block (a full export or one filtered by `forms[]`, where the instrument contributes at least one value column), and MUST be **absent** when `fields[]` restricts the export to a specific list of fields (the web application exports whole instruments and gets the column; a field-list export returns exactly the requested fields). It keeps its raw name under `rawOrLabelHeaders` (it names no field) and appears in JSON exports as an ordinary key; the wide type repeats it as `<instrument>_complete_<unique_event_name>` for instruments active in several events (REQ-API-028 shapes unchanged otherwise). Import does NOT accept the column — a `<instrument>_complete` key stays an unknown field (REQ-API-032). |

### 3.4 Record import (`content=record` with `data`, REQ-API-012)

| ID | Requirement |
|---|------|
| REQ-API-031 | Imports MUST accept values in the REDCap import shape: entries of (record, form/instrument, event, field, value); each value MUST be stored under the EAV key of REQ-DB-015. The `data` parameter MUST be accepted in both REDCap encodings: indexed form parameters (`data[0][<identifier>]=…`) and a single `data` parameter holding a **JSON array of record objects** (the recorded caller's encoding), whose non-string values — numbers, booleans — are coerced to their string spelling. A row MUST name its record under the **record identifier's field name** — the first field of the first instrument (GD-8), the key an export writes it under (REQ-API-028) — and under no fixed key: `record_id` names the record only in a project whose first field is called so, and is an ordinary field name (or an unknown one) everywhere else. A row MAY omit `form_name`: such a **flat row** stores every supplied field on its own instrument from the data dictionary (the event rules apply unchanged — a project with events still requires the row to name its event). An import MAY carry an optional `tz` parameter (IANA timezone name or `±HH:MM` offset) supplying the **timezone of collection** for the date/date-time values of the call; without it, the deployment default `APP_TIMEZONE` applies (GD-16, REQ-VAL-041, REQ-CFG-026). |
| REQ-API-032 | Every value MUST pass the field's validation rules (`Data_Validation_Requirements.md`) before storage; invalid values MUST NOT be stored. |
| REQ-API-033 | Imports MUST upsert (REQ-DB-016): entering values for a new record or changing values of an existing record requires the data access level ≥ `view_edit` on the record's arm; a token at `read_only` or `no_access` MUST be rejected (GD-2). |
| REQ-API-034 | Import responses MUST use the REDCap result codes: `1` record added, `2` record updated, `0` validation errors (with per-field error detail), `255` fatal error. |
| REQ-API-035 | A record's imported values MUST be stored all-or-nothing (single transaction per record); every successful import MUST be audit-logged with user, token, record, and changed fields (`Audit_Logging_Requirements.md`). |
| REQ-API-095 | An import MUST reject a value for a calculated field (its value is system-managed, REQ-VAL-036); a recomputation triggered by the import MUST complete in the same transaction as the imported value (REQ-VAL-037, REQ-AUD-023). |
| REQ-API-138 | An import row MUST accept `redcap_event_name` as a synonym of its `event_name` key — the name a flat export uses for the same value (REQ-API-028) — so an export → edit → import round trip needs no renaming by the caller. The two keys name one value and an empty value counts as not supplied (the REQ-VAL-024 reading of empty), so exactly one spelling is in force per row; where both are present with **different** values the row MUST be rejected with nothing of it stored (REQ-API-035) — choosing an event silently could write the row into the wrong event. Neither name may be a project field (`Data_Validation_Design.md` §9 reserved names), so the alias can never shadow a field value. The row's error detail names the key the caller used, not the canonical spelling (REQ-VAL-008). A project **without** events stores under the empty event name, so the alias names nothing there and MUST be ignored; whether a named event sent to such a project should instead be rejected is open — it is stored under that name today. |
| REQ-API-139 | A rejected import row's error detail MUST be deterministic: its field problems in data-dictionary order, then its unknown keys in dictionary order, joined by `; ` (REQ-API-034). Identical input MUST produce a byte-identical message — ordering noise from map iteration would leave a caller comparing two responses, or an audit comparison of two rejected batches, unable to tell whether the data changed. |
| REQ-API-140 | **Draft — open decision, not implemented.** A call whose rows repeat one invalid value MUST report it once per problem class rather than once per row: the master spec asks for `{"error":"The following values of redcap_event_name are invalid: v1_arm_1_arm_1"}` where eight rows share an unknown event (`VISION_AND_REQUIREMENTS.md`, "Error messages by api"); today the call answers eight identical per-row details (REQ-API-034). Two decisions come with it. **(a)** Whether the aggregate is a request-level §3.2 error body — which fails the whole call, so rows that would have succeeded never report their `1`/`2` and REQ-API-035's per-record granularity is lost for the batch — or an addition to the §3.7.2 result set alongside the per-row detail. **(b)** Whether a row stops at its first tuple problem (an unknown event currently short-circuits the rest of that row's field detail) or reports every problem it has, as REQ-VAL-008's "per-field details" reads. Aggregation MUST NOT weaken all-or-nothing storage (REQ-API-035), the logging of rejected submissions (REQ-AUD-021), or the no-internals-leak rule (REQ-API-039). |
| REQ-API-142 | An import MUST accept `returnContent`. With `returnContent=count` the response MUST be the number of rows applied (added + updated) as `{"count": N}` in JSON and a bare count line in CSV — the response the recorded import callers parse; rejected rows are not counted and per-row detail is not rendered in this mode. Any other value keeps the §3.7.2 result rows (REQ-API-034); unlike REDCap, whose default is `count`, an omitted `returnContent` keeps the result rows — the web application consumes them (DEV-API-24). |
| REQ-API-155 | **Repeating instruments in the data API** (REQ-DB-047/048), in REDCap's shape: an import row MAY name `redcap_repeat_instrument` (an instrument repeating at the row's event) and `redcap_repeat_instance` (a positive integer) and then fills that instance — instance 1 being the first instance's storage, so an exported row imports back where it came from. Such a row carries that instrument's fields only; its empty cells of other instruments are ignored, and the record identifier is not stored on a further instance (GD-8). A row naming neither fills first instances; `redcap_repeat_instance` without an instrument is accepted only as `1` (no repeating events). A flat row without `form_name` and without repeat columns MUST treat an empty value of a field whose instrument repeats at the row's event as not supplied rather than a clear (REQ-VAL-024), because a REDCap export leaves those cells empty on the event's own row. The flat export (REQ-API-028) MUST write, per record and event, the event's own row with the repeating instruments' columns empty, followed by one row per instance (ascending) of each instrument repeating there that holds a value or is finished, naming it in `redcap_repeat_instrument`/`redcap_repeat_instance` with that instrument's columns and `<instrument>_complete` only; the two repeat columns MUST appear only in projects with at least one repeating pair (REDCap's shape), and a JSON export MUST write `redcap_repeat_instance` as a number on instance rows (an empty string on the event's own row); the wide layout (DEV-API-1) MUST add after an instrument's block one block per further instance `n` up to the highest among the exported records, its columns suffixed `__<n>`. `action=delete` MUST accept `repeat_instance` narrowing the delete to one instance (without it every instance in scope goes, hidden ones included). `content=repeatingFormsEvents` MUST list the repeating pairs as `event_name`, `form_name`, `custom_form_label` (empty) — read-only; and `content=project` MUST report `has_repeating_instruments_or_events` = `1` when a pair repeats. Hidden instances (REQ-DB-048) are neither exported nor writable. |

### 3.5 Record deletion (`content=record&action=delete`, GD-3)

| ID | Requirement |
|---|------|
| REQ-API-036 | The deletion MUST remove the record's values (scoped by the supplied `records[]`/`events[]`/`fields[]`, or the whole record) and, when a record's last value is removed, the record itself. Permission is the **delete instrument values** right of the (instrument, event) pair the values belong to (REQ-AUTH-018): a scoped deletion naming one instrument's fields requires the right on that pair; a whole-record deletion requires it on **every** pair where the record holds values, and MUST remove nothing when one of them lacks it (all-or-nothing). The deletion including the deleted values MUST be audit-logged (GD-3). |

### 3.6 Compatibility and limits

| ID | Requirement |
|---|------|
| REQ-API-037 | Every Fiona call example in `VISION_AND_REQUIREMENTS.md` (PHP and cURL) MUST succeed against this API without modification of the caller (charter success criterion 1) and MUST be encoded as executable regression tests (REQ-TECH-022). |
| REQ-API-038 | Optional rate limiting (REQ-CFG-020): when enabled, the API MUST limit requests **per source IP address** per minute — on both surfaces (`/api/` and `/api/v1/`, so web-application traffic and external scripts alike) — and answer HTTP 429 with a REDCap-style error body when the limit is exceeded. Exceeding the budget additionally blocks the source IP for the configured blockout period (REQ-API-113). The source IP is derived per REQ-API-125; the enable flag and the thresholds are system settings stored in the database and editable in the administration interface (REQ-API-112; master spec "Rate limitter"). |
| REQ-API-125 | The rate-limit source identity MUST be the caller's IP address: when the direct TCP peer is inside a configured trusted-proxy range (`TRUSTED_PROXY_CIDRS`, `System_Configuration_Design.md` §3.9), the proxy-provided `X-Real-IP` header is authoritative; otherwise the connection's remote address is used. A client-supplied `X-Real-IP` from an untrusted peer MUST be ignored, and the reverse proxy overwrites the header on every routed request (no forwarded-for chains; `Technology_Stack_Design.md` §5). The deployment MUST supply the header so every external caller keeps a distinct address — without it all web-application traffic would share the single application-host address (master spec "Rate limitter": unique incoming IPs verified). The web layer applies the same test one hop earlier: what it forwards in `X-Real-IP` is its own connection address (`REMOTE_ADDR`) unless that peer sits inside `TRUSTED_PROXY_CIDRS`, so a browser-supplied header never becomes the caller identity (finding F9; `Technology_Stack_Design.md` §5, `Web_Implementation.md`). |
| REQ-API-113 | When a source IP exceeds its per-minute budget (REQ-API-038), the API MUST reject further requests from that IP for **`rate_limit_block_minutes`** (system setting, default 10 minutes; master spec "Rate limitter"), answering HTTP 429 with the §3.2 error body and a `Retry-After` header naming the remaining seconds. The blockout starts at the first rejection and lasts exactly the configured period: rejections during the block MUST NOT extend it, so continued calls can never lock the address out indefinitely. When the period elapses the IP is admitted again from a fresh window with no memory of the offence. Blocking keys on the source IP alone, so a block tripped on one surface covers the other (one limiter per API process). The blocked state is in memory like the window — the API stays stateless and a restart clears it (`API_Endpoints_Design.md` §3.9). |
| REQ-API-039 | Data API error responses MUST carry a machine-readable `error` string in the body rendered in the requested format, with 4xx HTTP status (400 invalid request, 401 invalid token, 403 insufficient permission, 410 survey link already submitted — REQ-API-145); error text MUST NOT leak internal implementation details. |
| REQ-API-144 | A request too large to parse MUST be refused as a 400 naming the limit it crossed, **before any token lookup**, and never as a 401. An indexed call (`data[i][key]`, `records[i]` — REQ-API-015) carries one parameter per cell, so it is bounded by the body size of REQ-TECH-011 and by a parameter count of **250,000**; that pair clears a 1,250-row × 200-field import. The count MUST NOT sit at the 10,000 Go's `net/url` applies to one urlencoded string from Go 1.27 (`net/url.defaultMaxParams`), which the recorded batches cross at 50 rows × 200 fields (DEV-API-24). Parsing such a request to an empty parameter set is forbidden: it answers a valid token with `Invalid token` (REQ-API-011) and, where `data` decides import from export (REQ-API-012), can hand a caller an export of the project it meant to write to. The error text MUST name the limit and point at the JSON `data` encoding (REQ-API-031), which carries the same batch in one parameter, without leaking internals (REQ-API-039). |

## 4. Administration API (`/api/v1/`)

### 4.1 Boundary

| ID | Requirement |
|---|------|
| REQ-API-040 | The administration API MUST be reachable only from the trusted internal path (REQ-TECH-018) and MUST be used exclusively by the PHP web application (GD-1, BR-006); the browser MUST NOT call it directly. |
| REQ-API-041 | Every request MUST present a valid `X-Internal-Service-Token` and `X-Internal-User-Id`; the API MUST reject calls violating REQ-AUTH-011 through REQ-AUTH-014. A call made for an established PHP session additionally carries `X-Internal-Session-Epoch` (REQ-API-147). |
| REQ-API-042 | The surface MUST use JSON request/response bodies with conventional REST semantics (GET read, POST create, PUT update, DELETE remove); all PUT endpoints MUST be idempotent. |
| REQ-API-043 | Every mutating call MUST be audit-logged with the acting user, the target project, and the operation (`Audit_Logging_Requirements.md`). |
| REQ-API-147 | A call that carries `X-Internal-Session-Epoch` MUST be accepted only while that value equals the acting account's stored session epoch; any other value, including one that is not an integer, MUST be rejected 401 `session_revoked` and audit-logged as `admin_rejected` with reason `session_revoked` (REQ-AUTH-074). A call without the header is not checked — the pending identity of a two-factor enrollment (`Authentication_Authorization_Design.md` §2.7) has no session yet — so PHP MUST send it on every call made for an established session. The check runs after the account-active rule: a disabled account keeps its 403. |

### 4.2 Session

| ID | Requirement |
|---|------|
| REQ-API-044 | `POST /api/v1/auth/login` (called by the PHP app after successful OAuth2/LDAP authentication, **or with `source: "local"` and the password for table-based login** — GD-18, REQ-AUTH-050/051) MUST accept the authenticated user's identity (email) in a JSON body, plus an optional `source_name` — the authentication-source name the user selected on the login page, recorded in the login audit details and nothing else (REQ-AUTH-067); for local login it MUST verify the stored argon2id hash in constant time first (mismatch or absent hash → 401 `bad_password`, never logged, REQ-AUTH-036); then verify that the user row is active (REQ-AUTH-006: `enabled`, not expired `valid_until`, not inactive — `account_disabled`/`account_expired`), apply the bootstrap-admin promotion (REQ-AUTH-007), set `last_login_at` (REQ-AUTH-053), record a login audit event with the source (REQ-AUTH-008), and return the user object (id, email, display name, `is_admin`, authentication source, `ui_language`, `ui_theme` — GD-26, `session_epoch` — REQ-AUTH-074). The API is stateless with respect to sessions (GD-1): it MUST NOT create or store a session. |
| REQ-API-045 | `POST /api/v1/auth/logout` MUST record a logout audit event (REQ-AUTH-008) and return a 200 response; destruction of the PHP session remains the responsibility of the PHP layer before this call (GD-1, REQ-AUTH-015). |
| REQ-API-148 | `POST /api/v1/auth/session-replay` (no body) MUST raise the acting account's session epoch and record `session_replay_detected` with the presenting address, in one transaction (REQ-AUTH-073, REQ-AUD-030), answering 200 `{ "status": "ok" }`. PHP calls it as the account whose replaced session id came back — `X-Internal-User-Id` without `X-Internal-Session-Epoch`. The API stores no session for it (GD-1). |
