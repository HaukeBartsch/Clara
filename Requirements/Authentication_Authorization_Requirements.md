# Authentication & Authorization — Requirements Analysis

**Project:** Clinical Study Management System (REDCap API Replacement)\
**Source plan:** `Plan/Authentication_Authorization.md`, `VISION_AND_REQUIREMENTS.md` (master spec)\
**Status:** Approved for development handoff\
**Date:** 2026-09-18

## 1. Purpose

Defines the authentication (**named authentication sources** resolving to OAuth2, LDAP(s), or table-based local-password authentication — GD-18, master spec "Authentication order"), account validity and inactivity rules (GD-19), account onboarding and password lifecycle (GD-22/GD-23), and authorization (RBAC, per-arm permission levels) requirements. `Design/Authentication_Authorization_Design.md` contains the login sequences, session schema, and trust model.

## 2. Authentication Requirements

| ID | Requirement |
|---|------|
| REQ-AUTH-001 | The system MUST authenticate users against an external OAuth2 server using the authorization-code flow: redirect to provider → code returned → code exchanged for a token → local session established. |
| REQ-AUTH-002 | The system MUST support multiple OAuth2 providers (generic integration) configured per REQ-CFG-011 and presented to the user for selection by authentication-source name before login (REQ-AUTH-063/066). |
| REQ-AUTH-003 | LDAP servers are queried **within the selected authentication-source set** (REQ-AUTH-065): all LDAP sources registered under the selected name are tried **in parallel**, first successful bind wins — superseding the earlier sequential fallback of servers 1→2→3 (DEV-AUTH-14). |
| REQ-AUTH-004 | The user's identity MUST be mapped to a system user by email address from the provider assertion, the LDAP directory attributes, or the local login's email (institutional email is the identity for all paths, master spec "Details"). |
| REQ-AUTH-005 | The successful authentication source MUST be recorded on the user record (`auth_source` = `oauth2`|`ldap`|`local`) and in the audit log. |
| REQ-AUTH-006 | A user account MUST exist and be **active** for login to succeed: `enabled = 1`, not expired (`valid_until`, REQ-AUTH-052), and not inactive (REQ-AUTH-053). Otherwise the login is rejected with the specific reason (`account_not_found` / `account_disabled` / `account_expired`) and the failure is audit-logged. The same active rule applies at every authentication check (login, administration-API calls, data-API token checks — REQ-API-048). |
| REQ-AUTH-007 | The bootstrap admin (`ADMIN_BOOTSTRAP_EMAIL`, GD-4) is provisioned **at startup** as an operator setup action: with `ADMIN_BOOTSTRAP_PASSWORD` configured the API MUST ensure the account exists, is enabled, and has `is_admin = true` (GD-4; table-based provisioning per REQ-AUTH-051). At **login**, an email match MUST only create the row when it is absent (first-install case), MUST never re-enable a disabled account, and MUST set `is_admin = true` on an existing enabled row only when the login source is `local` or no other enabled administrator exists (security finding F10, DEV-AUTH-15) — an IdP whose `mail` attribute users can control must not (re)acquire administration. Ongoing administration after setup is assigned through REQ-API-136, not by the bootstrap path. |
| REQ-AUTH-008 | Login attempts (success and failure) and logouts MUST be audit-logged (see `Audit_Logging_Requirements.md`). |
| REQ-AUTH-085 | The Control Panel MUST provide an administrator-only diagnostic page for configured LDAP and OAuth/OpenID Connect sources. LDAP checks MUST use credentials supplied for that check and MUST NOT create a CLARA login; OAuth checks MUST use the configured authorization-code flow without establishing a CLARA login. The page MUST show useful connection stages, configured non-secret settings, and allowlisted identity/group claims. It MUST NOT render or log passwords, client secrets, authorization codes, access tokens, or ID tokens. Provider groups and roles are diagnostic information only and MUST NOT grant CLARA permissions. |

### 2.1 Table-based (local) authentication (decision GD-18)

| ID | Requirement |
|---|------|
| REQ-AUTH-050 | The system MUST support a third authentication path: **table-based (local) login** with the user's email and password, verified against the account's stored argon2id hash (`users.password_hash`, REQ-DB-008; DEV-AUTH-16). A local password is the **only** credential the system MAY persist — never plaintext, never logged; the OAuth2 and LDAP paths remain passwordless (REQ-AUTH-036 revised). |
| REQ-AUTH-051 | Local login is one of the credential-checked sources tried **in parallel** under the selected authentication-source name (REQ-AUTH-065; supersedes the earlier local-first-then-LDAP-falls-through ordering, DEV-AUTH-14). The bootstrap admin (GD-4) MUST be usable on a first installation without any OAuth2 provider or LDAP server: when neither is configured, the API MUST provision the bootstrap account's local password from `ADMIN_BOOTSTRAP_PASSWORD` (configuration, REQ-CFG-025), and the system MUST refuse to start in that configuration without it (startup rule, `System_Configuration_Design.md` §4.1). An administrator MAY set, reset, or clear a user's local password through the users API (REQ-API-047/048); the password value MUST NOT appear in logs or audit details. |
| REQ-AUTH-052 | **Account validity:** an account MAY carry a validity period, stored as the end date `valid_until` (date, UTC; `NULL` = indefinite). The period is supplied as days (`0` = indefinite) at account creation or update (REQ-API-047/048); `valid_until = today + valid_days`. An account whose `valid_until` is before today MUST be rejected at every authentication check with `account_expired` (the account stays enabled; an administrator restores access by setting a new validity period). |
| REQ-AUTH-053 | **Inactivity auto-disable:** `last_login_at` (UTC) MUST be set on every successful login (any source). At an authentication check, an account whose `last_login_at` is older than `AUTH_INACTIVITY_LIMIT_DAYS` (configuration, REQ-CFG-024; default 180; `0` = rule off) MUST be **auto-disabled** — `enabled` set to `0`, the inactivity clock reset — the check MUST be rejected as `account_disabled`, and the event MUST be audit-logged as `account_auto_disabled` (REQ-AUD-024). An administrator MUST be able to re-enable such an account (REQ-API-048); re-enabling MUST reset the inactivity clock (the account is then usable until its next login ages out again). The user overview MUST show last login, validity end, and the account's status (REQ-UI-011). |

### 2.2 Session (decision GD-1)

| ID | Requirement |
|---|------|
| REQ-AUTH-009 | The session MUST be owned by the PHP web application (PHP-native session, `HttpOnly`/`Secure`/`SameSite=Lax` cookie, named with the `__Host-` prefix whenever it is `Secure` — REQ-AUTH-075). The session MUST store at least: user id, email, display name, `is_admin`, authentication source, issue time, the time of its last request, the time of its last id rotation, and the account's session epoch (REQ-AUTH-015/072/074). |
| REQ-AUTH-010 | The browser MUST NOT call the administration API (`/api/v1/*`) directly; all administration API calls are made server-side by PHP with the session context. |
| REQ-AUTH-011 | PHP MUST identify itself to the API with the shared service token and the user id: headers `X-Internal-Service-Token` (shared secret) and `X-Internal-User-Id`. The API MUST reject `/api/v1/*` calls lacking a valid service token. |
| REQ-AUTH-012 | The API MUST compare the service token in constant time and MUST NOT log its value. |
| REQ-AUTH-013 | The API MUST treat `X-Internal-User-Id` as authoritative for authorization on `/api/v1/*`; the user MUST exist and be enabled, else the call is rejected (403) and audit-logged. |
| REQ-AUTH-014 | The reverse proxy MUST strip `X-Internal-Service-Token`, `X-Internal-User-Id` and `X-Internal-Session-Epoch` from all externally-originated requests; `/api/v1/*` MUST not be routable from the public network (REQ-TECH-018). |
| REQ-AUTH-015 | Sessions MUST end after a configurable inactivity timeout (`SESSION_IDLE_TIMEOUT`, default 30 min; `0` = off), after a configurable absolute lifetime counted from sign-in however active the session was (`SESSION_LIFETIME`, default 8 h), and on explicit logout. Logout MUST call `POST /api/v1/auth/logout` (audit) before destroying the session. A session ended by either bound MUST lead to the login page with a translated line saying why (REQ-UI-007). *(Amended 2026-10-11, DEV-AUTH-17: the 8 h value had been the only bound and was enforced as an absolute lifetime; the idle timeout is new.)* |
| REQ-AUTH-072 | **Session id rotation.** An authenticated session MUST move to a new session id at least every `SESSION_ROTATE_INTERVAL` (default 15 min; `0` = off), automatically, on its first request after the interval has passed. The replaced id MUST keep nothing but a reference to its successor — no identity, no CSRF token, no cached credential. For a grace window of 60 s it continues in the successor (requests a page already had in flight still carry it); after that it MUST NOT open any session. The interval MUST be at least twice the grace window. Sign-in and a session's own credential change (REQ-AUTH-074) move the id with no grace window. |
| REQ-AUTH-073 | **Replay detection.** A replaced session id presented after its grace window means two parties held the session, and it MUST be treated as theft: the presenting session ends, every session of the account ends (REQ-AUTH-074 — the legitimate holder cannot be told from the other), `session_replay_detected` is audit-logged with the presenting address (REQ-AUD-030), and the login page tells the user they were signed out everywhere (REQ-UI-007). Session ids MUST NOT appear in logs or audit details. |
| REQ-AUTH-074 | **Session revocation (session epoch).** Each account MUST carry a session epoch (REQ-DB-008), returned with the user object at login and stored in the session; every administration-API call PHP makes for an established session MUST present it (`X-Internal-Session-Epoch`, REQ-API-147), and the API MUST refuse a call whose epoch differs from the account's (401 `session_revoked`), whereupon PHP MUST end the session. The epoch MUST be raised by every write of the account's local password (self-service change, reset, invite completion, administrator set or clear), by every transition of `enabled` to `0` (administrator disable, inactivity auto-disable), by an administrator's two-factor reset, and by a reported replay (REQ-AUTH-073) — so each of these ends all of the account's sessions at their next API call, while the API still stores no session (GD-1). A session that raised its own account's epoch — a self-service password change, or an administrator acting on their own row other than disabling it — adopts the new value and continues under a new id. Supersedes DEV-AUTH-13. |
| REQ-AUTH-075 | **Session cookie hardening.** With `APP_ENV=production` the web layer MUST refuse to start when `SESSION_COOKIE_SECURE=0` (REQ-CFG-017). A `Secure` session cookie MUST be named `__Host-` + `SESSION_COOKIE_NAME`, with `Path=/` and no `Domain`, so a browser accepts it only from this exact host over HTTPS; `HttpOnly` and `SameSite=Lax` stay (REQ-AUTH-009 — `Lax` rather than `Strict` because the OAuth2 callback is a cross-site top-level navigation that has to carry the session, `Authentication_Authorization_Design.md` §2.1). |
| REQ-AUTH-016 | `POST /api/v1/auth/login` (called by PHP after successful IdP authentication, **or with `source: "local"` and the password for table-based login** — REQ-AUTH-050) MUST: for local login, verify the stored hash in constant time before any other step (mismatch or absent hash → `bad_password`, no disclosure difference); then verify the user row exists and is active (REQ-AUTH-006), apply the bootstrap-admin promotion (REQ-AUTH-007), record a login audit event with the source, set `last_login_at`, and return the user object including `is_admin`. The local password MUST NOT be logged or stored anywhere except as the argon2id hash. When the account has two-factor authentication enabled, the first-factor success MUST be answered with an `mfa_required` indication instead of the user object — login completes only when the second factor verifies (GD-21, REQ-AUTH-054…058; REQ-API-114). |

### 2.3 Two-factor authentication (decision GD-21)

| ID | Requirement |
|---|------|
| REQ-AUTH-054 | Each user account MUST support a **by-user configurable two-factor authentication** with the methods `off` (default), `totp`, and `email`. `totp` is RFC 6238 time-based one-time codes from a phone authenticator app (works without internet access); `email` sends a random one-time code to the account's email address. The user selects and changes the method self-service; the administrator sees each account's method but the choice remains the user's unless mandated (REQ-AUTH-059). |
| REQ-AUTH-055 | The second factor MUST be verified **after a successful first factor on the CLARA-verified login paths** — the local (table-based, Sequence F) and LDAP form logins (Sequences B/F) — and **before** any session is established; without a valid second factor no session data or user object is returned. The OAuth2 path (Sequence A) is exempt: MFA there is the identity provider's responsibility (DEV-AUTH-10). Survey link access and API-token calls are unaffected (GD-5, GD-9). |
| REQ-AUTH-056 | **Enrollment (self-service).** TOTP: the system generates a shared secret, presents it as a QR code plus manual-entry key, and activates only after the user returns one valid current code. Email: activation only after the user confirms a code delivered to the account's address. On activation the system MUST issue a set of single-use **recovery codes** shown exactly once; they verify in place of a regular code. The secret is never displayed again after enrollment, and secrets, sent codes, and recovery codes MUST NOT appear in logs or audit details (REQ-AUTH-036 extended). |
| REQ-AUTH-057 | **Email delivery.** The one-time code MUST be cryptographically random (≥ 6 digits), delivered via a configured SMTP relay (`System_Configuration_Requirements.md` REQ-CFG-028), expire after a configurable TTL (default 10 minutes), and be single-use. Sending MUST be rate-limited per account. Without SMTP configuration the `email` method MUST NOT be selectable, and an account already on it MUST fall back to its recovery codes with a clear administrator-actionable error. |
| REQ-AUTH-058 | **Verification rules.** TOTP codes verify per RFC 6238 (30 s step, ±1 step clock-skew window) and each accepted step or code MUST be recorded so a code cannot be replayed. Failed second-factor attempts MUST be audit-logged (`login_failure`, reason `bad_mfa_code`) and MUST count toward the brute-force lockout of REQ-AUTH-035; while locked, no second factor is verified and no new email code is sent. |
| REQ-AUTH-059 | **Mandate and reset.** An installation-wide configuration (`AUTH_REQUIRE_2FA`, REQ-CFG-027) MUST be able to require 2FA: with it on, an account whose method is `off` MUST be directed — after first-factor success, before session establishment — to enroll before login completes. An administrator MUST be able to **reset** a user's two-factor authentication (lost phone, unusable email); the reset clears method, secret, pending codes, and recovery codes, is audit-logged (`tfa_reset`), and under a mandate sends the user through enrollment at the next login. Enrollment, activation, and disable events MUST be audit-logged (REQ-AUD-028). |

### 2.4 Account onboarding and password lifecycle (decisions GD-22/GD-23)

| ID | Requirement |
|---|------|
| REQ-AUTH-060 | **Emailed invite (local accounts).** When an administrator creates a local account without a password, the system MUST offer to send an invitation: an email to the account's address carrying a link with a cryptographically random single-use token (`crypto/rand`, ≥ 128 bits; stored only as a one-way hash in `password_tokens`, REQ-DB-039) to the set-password page (public PHP route, no session). The token MUST expire after `AUTH_PASSWORD_TOKEN_TTL_DAYS` (REQ-CFG-030, default 7), be consumed on first successful use, and be invalidated by a re-invite. Completing it sets `password_hash` (argon2id, REQ-AUTH-050) and marks the account as having a usable local credential; the user then logs in normally — the second factor is **not** bypassed (Sequence C step 1.5 still applies). Invitations apply only to local accounts; an OAuth2/LDAP-only account MUST NOT receive one. When no SMTP relay is configured (REQ-CFG-028), the invite action MUST be unavailable and the admin sets the password directly. Token values MUST NOT appear in logs or audit details. |
| REQ-AUTH-061 | **Self-service local password change.** A signed-in account with a local credential MUST be able to change its own password on the account page by proving the current password (verified against `password_hash` before the change is accepted; failure is shown generically and audit-logged). The change takes effect immediately for subsequent logins. The account's **email address is not self-editable** — it is the identity across all authentication paths (REQ-AUTH-004) and changes only by an administrator. Changing a password MUST NOT terminate existing PHP sessions (the API is stateless, GD-1); they end via logout or the inactivity timeout (REQ-AUTH-015) — an accepted phase-1 trade-off, recorded as DEV-AUTH-13. |
| REQ-AUTH-062 | **Forgot-password reset (local accounts).** The login page MUST offer a password-reset request: submit an email address; the response MUST be identical whether or not an account with a local credential exists (no enumeration oracle — corrects the reference's `newPassword.php`). When a matching active local account exists, the system sends an email carrying a single-use token link (same token mechanics as REQ-AUTH-060); the completion page takes the **new password directly** — no temporary password is ever generated, transmitted, or stored. Requests MUST be rate-limited per address and per source IP (stricter than the general limiter; default 3 per 15 minutes per address). Reset applies only to active local accounts; disabled/expired accounts get the same generic response and remain subject to REQ-AUTH-006 at next login. OAuth2/LDAP-only accounts are unaffected (their credential lives with the IdP/directory). All events audit-log per REQ-AUD-029 without token values or password material. |

### 2.5 Named authentication sources and authentication order (master spec "Authentication order")

| ID | Requirement |
|---|------|
| REQ-AUTH-063 | **Named authentication sources.** Before a user logs in, the system MUST present the configured authentication sources for selection by name; a name presented to the user SHOULD read like "Hospital 1", "Hospital 2". Each source resolves internally to exactly one kind — table-based (local), LDAP(s), or an OAuth2 provider. A login attempt MUST be made only against the sources registered under the name the user selected; credentials entered for a name MUST NOT be sent to any other source. |
| REQ-AUTH-064 | **Many-to-many names.** More than one authentication source MAY share the same name, and one source MAY carry more than one name. The login page presents the distinct set of names across all configured sources; selecting a name selects its entire set of sources. |
| REQ-AUTH-065 | **Parallel resolution — first "login ok" wins.** On a login under a selected name, every credential-checked source in that set (local and LDAP) MUST be tried **in parallel** with the submitted email+password; the first successful response wins and establishes the identity, all other responses are discarded without producing a second session, duplicate audit success, or `last_login_at`/`auth_source` update. A source-specific account-state rejection (`account_disabled` / `account_expired`, REQ-AUTH-006) on any attempted source is surfaced when no source succeeds; if all attempts fail the login fails with the generic credential failure. |
| REQ-AUTH-066 | **Interactive OAuth2 within a name.** An OAuth2 source cannot be probed without a browser round-trip, so it does not join the parallel credential race: selecting a name that maps to exactly one OAuth2 source continues directly into that provider's authorization-code flow (REQ-AUTH-001); a name mapping to several OAuth2 sources MUST present each for individual selection; a name mixing OAuth2 and credential sources offers both — the credential form is raced per REQ-AUTH-065 and each OAuth2 provider remains individually completable. |
| REQ-AUTH-067 | **Selection convenience and recording.** When exactly one distinct name is configured, the picker MAY be skipped and that name applied implicitly; sources configured with no name form one implicit default set. The selected name and the winning concrete source MUST be recorded on the login audit event alongside `auth_source` (REQ-AUTH-005) and stored in the session (REQ-AUTH-009). |

### 2.6 OpenID Connect provider assertions and assurance (security finding F8; PingFederate integration)

The OAuth2 path is the one authentication path on which CLARA does not hold a user credential. The Go API performs discovery, creates the authorization request, exchanges the authorization code, and verifies the returned ID token; PHP holds only the browser-bound transaction and establishes its local session. The API therefore satisfies itself of the provider proof before granting access (DEV-AUTH-18, REQ-AUTH-086).

**Status (2026-10-27):** REQ-AUTH-076…082 and REQ-AUTH-084 are implemented in the Go API; REQ-AUTH-083 (single sign-out) remains open. REQ-AUTH-086 assigns the complete OIDC protocol client flow to Go. The PingFederate reference SDK is a management-API client; CLARA uses the OAuth2 and OIDC protocol libraries directly for end-user login.

| ID | Requirement |
|---|------|
| REQ-AUTH-076 | **Signed provider assertion at the boundary.** The OAuth2 login request carries the provider's authorization code and the PKCE verifier; the Go API exchanges them and MUST verify the resulting signed ID token before any account is resolved or session established: signature verified against the issuer's published keys with a **pinned signing algorithm**; `iss` equal to the configured issuer; `aud` equal to the configured client id; `exp` not passed and `nbf`, when present, not in the future — each within a bounded clock-skew allowance. An assertion by the web layer that a provider login succeeded is **not** sufficient on this path. The API MUST NOT accept a PHP-supplied ID token in place of the authorization-code exchange. This closes the `source: oauth2` leg of finding F8 without retiring `INTERNAL_SERVICE_TOKEN`, which still guards every other call. |
| REQ-AUTH-077 | **Key acquisition and algorithm discipline.** Verification keys MUST be read from the `jwks_uri` named in the provider's discovery document — never derived from the issuer path, whose convention differs between providers — and cached, with a refresh on an unknown `kid` and retention of superseded keys across their published overlap. The accepted signing algorithm is configuration (`OAUTH2_N_ID_TOKEN_ALG`, default `RS256`); an assertion signed by any other algorithm MUST be rejected, **including `none` and the HMAC family**, both of which real providers advertise in metadata. |
| REQ-AUTH-078 | **Address verification assertion.** OAuth login MUST require `email_verified` to be boolean true in the same provider response (userinfo or ID-token claims) that supplies the configured email claim: a string `"true"` is not true, so the comparison is by type as well as value. An absent, false, or mistyped claim MUST be rejected as `email_unverified` before account resolution; a missing claim is a provider-configuration fault, not an unverified login. The sign-in configuration check MUST identify this as a required OAuth claim; the OAuth diagnostic report exposes the allowlisted claim so an administrator can check provider availability. Silently accepting a missing claim reopens finding F10. |
| REQ-AUTH-079 | **Assertion bound to the browser transaction.** The authorization request MUST carry a `nonce` generated by the Go API alongside `state` and the PKCE verifier and returned to PHP for storage in the same single-use browser transaction; an assertion whose nonce is present and differs MUST be rejected. Whether its absence also rejects depends on `OAUTH2_N_NONCE_REQUIRED` (REQ-CFG-035), because not every provider echoes the claim: the setting records an observed provider fact, and an unset one is reported as unknown rather than treated as satisfied. |
| REQ-AUTH-080 | **Provider subject binding.** Every successful provider login MUST record the (`iss`, `sub`) pair it verified against the system user, in an account-linkage row beside the account (the schema requirement is carried by `Database_Schema_Requirements.md`; DEV-AUTH-18 opens it). Resolution thereafter MUST prefer the subject link over email equality: an address changed or reassigned at the provider MUST NOT move an account into different hands, and MUST NOT silently lock out its owner — an unknown `sub` on a known address links on first verified login, and any other conflict is an administrator's decision, not an automatic one. A pairwise subject is opaque: never parsed, never derived from anything else; if the provider uses pairwise identifiers, its sector identifier is fixed for the life of the installation and recorded in the installation notes. |
| REQ-AUTH-081 | **Assurance gate.** Where an installation configures a minimum authentication context (`OAUTH2_N_MIN_ACR`, REQ-CFG-035), login MUST require the assertion's `acr` to be one of the configured values or its `amr` to include a configured method, and MUST **fail closed** when no assurance claim is present. The exemption of the OAuth2 path from CLARA's own second factor (REQ-AUTH-055) stands only while either such a gate is configured or the installation has recorded that the provider owns the factor; which of the two applies MUST be visible in the configuration check rather than implied by a code comment. |
| REQ-AUTH-082 | **Discovery validation and honest failure.** The `issuer` value inside the discovery document MUST equal the configured issuer; on mismatch, on an unreadable document, or on a document naming no `jwks_uri`, login MUST fail with a named provider error. Deriving `authorize`/`token`/`userinfo` paths by appending conventional names to the issuer root is withdrawn: providers whose endpoints differ — PingFederate among them, serving `/as/authorization.oauth2`, `/as/token.oauth2` and `/idp/userinfo.openid` — turn that fallback into a misleading upstream error rather than a working default. |
| REQ-AUTH-083 | **Single sign-out.** When enabled (REQ-CFG-036): signing out MUST pass through the provider's RP-initiated logout endpoint with a registered post-logout redirect; and the web layer MUST expose a back-channel logout receiver that verifies the `logout_token` to the standard of REQ-AUTH-076/077, resolves the account it names by (`iss`, `sub`) or by the session identifier that provider publishes, and ends every session of that account. Sessions MUST therefore be findable by provider subject. Where single sign-out is disabled, the configuration check and INSTALL.md MUST state plainly that signing out of CLARA leaves the provider session alive for its own lifetime, and that a revocation at the provider does not end an existing CLARA session before it expires. |
| REQ-AUTH-084 | **Assertion outcomes in the audit trail.** `login_success` and `login_failure` details MUST carry the issuer, the provider subject, the assurance claim(s) observed, and whether the address was verified; they MUST NOT carry tokens, signatures, or any other claim material (REQ-AUTH-036). A login refused by REQ-AUTH-076…081 MUST be distinguishable in the audit trail from one refused by the provider. |
| REQ-AUTH-086 | **Go-owned OIDC protocol flow.** The Go API MUST use the configured issuer's OIDC discovery document for the authorization and token endpoints, construct the authorization-code request with PKCE S256 and `openid email profile` scopes, exchange the callback code using the configured client credentials and PKCE verifier, and verify the resulting ID token per REQ-AUTH-076…082 before account resolution. PHP MUST retain `state`, the verifier, nonce, provider index, and selected source name only in its single-use browser session, compare the returned state, and relay the code/verifier/nonce to the API; PHP MUST NOT exchange the code, parse the ID token, or hold the OAuth client secret in its configuration object. The Go OAuth2 and OpenID Connect libraries used for these operations MUST be admitted in the stack allowlist (REQ-TECH-026). |

## 3. Authorization Requirements (RBAC)

### 3.1 Permission Set (decision GD-2)

| ID | Requirement |
|---|------|
| REQ-AUTH-017 | The permission set MUST be exactly (GD-2, revised 2026-10-03): per arm — a **data access level** (`no_access`, `read_only`, `view_edit`) and an **export level** (`export_none`, `export_de_identified`, `export_no_identifiers`, `export_full`), each held as the arm's default and overridable for any (instrument, event) pair of that arm (REQ-AUTH-069) — plus two **rights** held on the same scope: **delete instrument values** and **edit collected surveys**; plus the project-level `project_admin`. An arm not listed in a role defaults to `no_access` / `export_none` (no implicit access, REQ-AUTH-019). The former seven permissions (view/change/add/export_*) are superseded by these levels; `delete` and `edit_survey_responses` cease to be rungs of the data access ladder and become the two rights (REQ-AUTH-070). |
| REQ-AUTH-018 | Permission semantics (per arm, or per (instrument, event) override of it; the data access levels stay ordered — a higher level includes everything below): **data access** — `no_access` = that scope's data is hidden (absent from the UI, REQ-AUTH-027; rejected by the API); `read_only` = read its record values and the project structure; `view_edit` = additionally enter and change record values. **Rights**, independent of the levels and of each other (REQ-AUTH-070) — **delete instrument values** = delete the field values of that instrument at that event for a record, leaving the record and its other instruments standing (REQ-API-036); **edit collected surveys** = modify responses of a survey already collected at that pair (REQ-AUTH-071). **Export** — `export_none` = that scope's columns are absent from an export (REQ-API-026); `export_de_identified` = direct identifiers removed, personal fields hashed, dates shifted (`Data_Export_Anonymization_Requirements.md`); `export_no_identifiers` = all identifier fields removed; `export_full` = full dataset. **Project** — `project_admin` = modify project structure and metadata. |
| REQ-AUTH-019 | Every API operation and every UI action MUST require an explicit permission (see mapping tables in the API and UI requirement documents); there MUST be no implicit access. |
| REQ-AUTH-069 | A role MUST resolve to a data access level, an export level and both rights for **every** (instrument, event) pair of every arm it grants on. At request time a pair resolves to its own grant, falling back to the arm's default where it has none, and to `no_access` / `export_none` where neither exists (REQ-AUTH-019). When the design adds an instrument, an event, or a new mapping between them, every role of that project MUST be given an explicit grant for each new pair set to **`read_only` + `export_none`, both rights unset** (master spec, "Role adjustment") — a newly designed instrument is therefore readable and exportable by nobody until an admin edits the roles. Deleting an instrument or an event MUST delete the role grants that named it, so a re-created name inherits nothing. |
| REQ-AUTH-070 | The two rights MUST NOT be implied by a data access level and MUST NOT imply one another: `view_edit` does not grant **delete instrument values**, and neither grants **edit collected surveys** — the ordering of REQ-AUTH-018 stops at `view_edit`, and the ranking that previously placed `delete` and `edit_survey_responses` above it no longer holds (REQ-DB-009). A right set on a pair whose effective data access level is `no_access` MUST have no effect: denial wins over a right. |
| REQ-AUTH-071 | A survey response at a pair is **collected** once it carries a survey collection date (REQ-DB-041). The date MUST be stamped when a response submitted through that pair's public link is first saved, and later saves MUST NOT change it. Modifying a collected response from the interface requires **edit collected surveys** on that pair (superseding the `edit_survey_responses` level of REQ-AUTH-017). Nothing on the respondent's side needs gating against it: the submission that stamped the date also spent the link (REQ-API-145), so there is no second submission through it to gate — a correction reaches the record as an ordinary member write under this right, or as a deletion followed by a fresh link (REQ-AUTH-042, REQ-API-146). |

### 3.2 Roles

| ID | Requirement |
|---|------|
| REQ-AUTH-020 | Roles are defined per project, and a project MAY have none at all (role-less members then hold full permissions, REQ-AUTH-022). `data-manager` (suggested: `view_edit` + **delete instrument values** + `export_full`, plus `project_admin`), `data-entry` (suggested: `view_edit` + `export_none`), and `controller` (suggested: `read_only` + `export_none`) are examples/presets that a project MAY create — they are not mandatory built-ins; a project MAY create its own variants with different names, arms, and level combinations (DEV-AUTH-4, DEV-AUTH-5). |
| REQ-AUTH-021 | An administrator MUST be able to create **and edit** roles per project — the role's name, `project_admin`, and the data access level, export level and both rights of every arm and (instrument, event) pair (REQ-AUTH-017, REQ-API-057/143). Naming a new role is the act of creating it (`data-manager`, `data-entry`, `controller` are typical names); role creation MUST NOT be limited to the example presets of REQ-AUTH-020. |
| REQ-AUTH-022 | A project member without an assigned role MUST hold the highest levels on every arm and every (instrument, event) pair of the project (`view_edit` + both rights + `export_full`) plus `project_admin`, for that project only (master spec, BR-002). |
| REQ-AUTH-023 | A user with `is_admin = true` MUST hold all permission levels and rights on every arm and pair of every project (including `project_admin`) and MUST see every project in the dashboard (BR-010). |
| REQ-AUTH-068 | At least one **enabled** `is_admin` account MUST always exist: any administrative change that would reduce the set of enabled administrators to zero — revoking the flag, disabling the account, or both in one call — MUST be rejected (409, REQ-API-136); self-revocation and self-disable are permitted while another enabled administrator remains. Accepted limitations: validity expiry (REQ-AUTH-052) and inactivity auto-disable (REQ-AUTH-053) can transiently leave zero *login-capable* administrators without rejection — they run inside the authentication check and MUST NOT block there; the operator escape hatch is a restart with `ADMIN_BOOTSTRAP_EMAIL`/`_PASSWORD` configured, which re-enables and re-promotes the bootstrap account at startup (REQ-AUTH-007). |
| REQ-AUTH-024 | Roles are project-scoped: a role on project A grants nothing on project B. |
| REQ-AUTH-025 | Assigning a role to a member MUST replace the member's effective permissions for that project (no permission union across multiple roles in phase 1). |

### 3.3 Project Visibility and UI Gating

| ID | Requirement |
|---|------|
| REQ-AUTH-026 | A project MUST be visible to a user only if the user is `is_admin` or is a member of the project. |
| REQ-AUTH-027 | The UI MUST present a page, section, or action only if the user's effective permission allows it (e.g. no admin interface for non-admins; no Setup action without `project_admin`). Hidden means absent from the DOM, not merely disabled. |
| REQ-AUTH-028 | A user who is not a member of any project and not an admin MUST land on an information page explaining how to apply for project access (authentication plan, "info page only with instructions"). |

### 3.4 API Tokens

| ID | Requirement |
|---|------|
| REQ-AUTH-029 | Each (user, project) assignment MUST carry one token (UUID, GD-5). Tokens MUST be globally unique. |
| REQ-AUTH-030 | Tokens MUST be created and rotatable from the admin interface (member assignment screen); rotation MUST invalidate the previous token immediately and be audit-logged. |
| REQ-AUTH-031 | The REDCap-compatible API MUST accept the token only as the `token` request-body parameter (REDCap protocol), not in an Authorization header (GD-5). |
| REQ-AUTH-032 | Token validation MUST be a single indexed lookup (token → user, project, role); an invalid token MUST produce the REDCap-style error response without disclosing whether the token exists. |
| REQ-AUTH-033 | Token permissions MUST be the effective permissions of the (user, project) assignment at call time (role changes take effect immediately, no token refresh needed). |

### 3.5 Surveys (decision GD-9)

| ID | Requirement |
|---|------|
| REQ-AUTH-038 | An instrument MAY be marked as a survey (`is_survey`, REQ-DB-011); ONLY survey-marked instruments can be filled out via a public survey link (GD-9). |
| REQ-AUTH-039 | A survey link MUST be a record- **and event-specific** public web URL carrying an opaque link token; it MUST grant a person without a login fill-only access to exactly that (record, survey instrument, event) triple: read the instrument's field definitions for that record, and store values for it at that event — **once**, since the submission consumes the link (REQ-API-145). An instrument mapped to several events has one distinct link per event (REQ-API-082). It MUST grant nothing else (no other record, instrument, or event, no export, no structure, no administration API) and MUST NOT read back what is already stored, so the form it renders is never pre-populated. |
| REQ-AUTH-040 | Link tokens MUST be revocable; revocation MUST take effect immediately for all further calls and MUST be audit-logged (REQ-AUD-021). A submission ends a link's validity the same way (REQ-API-145): from that moment the token admits nothing, and it answers 410 so the respondent knows their answer arrived rather than being left to wonder. |
| REQ-AUTH-041 | Survey link submissions MUST pass the same field validation as any other write (REQ-VAL-001/004) and MUST be audit-logged with the link token as the acting principal (REQ-AUD-021). |
| REQ-AUTH-042 | A member modifying survey-originated responses in the UI requires the **edit collected surveys** right on the response's (instrument, event) pair (REQ-AUTH-070/071). The respondent has no such route: the link that carried their answer is spent by that submission (REQ-API-145), so a correction runs through a member — changing the stored values under that right, or clearing them with **delete instrument values** (REQ-API-036) and issuing a fresh link (REQ-API-146). |

### 3.6 Data Access Groups (decision GD-10)

| ID | Requirement |
|---|------|
| REQ-AUTH-043 | A project MAY have none, one, or several data access groups; a group name MUST be unique within the project (GD-10, REQ-DB-028). |
| REQ-AUTH-044 | A member MAY be assigned to none, one, or several groups of the project; with one or more assigned, exactly one MUST be active. Assignments are managed by `is_admin` (membership management, REQ-API-054 context); a member's own active group is visible to and switchable by the member (REQ-AUTH-046). |
| REQ-AUTH-045 | Visibility rule: a member with an active group G MUST see and access (read, export, record status, history) only the records whose data access group is G; a member without a group MUST see all records of the project regardless of their assignment; an `is_admin` user sees all records (REQ-AUTH-023). The rule is orthogonal to the permission levels (GD-2): the level governs which actions are allowed, the group governs which records they apply to. |
| REQ-AUTH-046 | A member with one or more groups MUST be able to switch the active group (self-service); the switch MUST take effect immediately for subsequent calls and MUST be audit-logged (REQ-AUD-022). |
| REQ-AUTH-047 | A record created by a member MUST be assigned to the creator's active group, or to no group if the creator has none; a record holds exactly one group (REQ-DB-029); a later import into the record MUST NOT change its group. |
| REQ-AUTH-048 | A record's group MUST be assignable or changeable after creation (GD-10); the action requires the project-level permission `project_admin` (ASM-AUTH-4) and MUST be audit-logged (REQ-AUD-022). |

## 4. Non-Functional Security Requirements

| ID | Requirement |
|---|------|
| REQ-AUTH-034 | All inter-component traffic between the web application and the API MUST be over a trusted path (loopback or internal network) or TLS. |
| REQ-AUTH-035 | Brute-force protection: after 5 failed logins for the same email within 10 minutes, further attempts for that email MUST be rejected for 15 minutes (per host, in memory or session store); failures are audit-logged. |
| REQ-AUTH-036 | User passwords MUST NOT be stored in plaintext and MUST NOT appear in logs or audit details. The **only** persisted credential is the one-way argon2id hash of a local (table-based) account's password (`users.password_hash`, GD-18, REQ-AUTH-050); the OAuth2 and LDAP paths remain passwordless (the LDAP password goes to the directory and is never persisted). |
| REQ-AUTH-037 | CSRF protection: all state-changing browser requests MUST carry a per-session CSRF token; the API's admin surface is additionally protected by the service-token boundary (GD-1). |
| REQ-AUTH-049 | The reverse proxy and web server MUST NOT write credential values to access logs — query strings are omitted or redacted wherever a credential can ride in one. Since DEV-API-30 the data API reads its token from the request body only, so `/api/` query strings carry nothing worth redacting; OAuth authorization codes returned to `/auth/callback` and the single-use invite/reset token in `/set-password?token=…` MUST NOT reach a log either (REQ-API-005). |

## 5. Assumptions

| ID | Assumption |
|---|------|
| ASM-AUTH-1 | The OAuth2 provider exposes standard authorization-code endpoints (authorize, token, userinfo or ID token with email). Provider-specific quirks are out of scope beyond generic OAuth2. Since DEV-AUTH-18 the endpoint set is read from the provider's discovery document and that document is required (REQ-AUTH-082): the conventional-path derivation this assumption once permitted is withdrawn. |
| ASM-AUTH-2 | LDAP servers accept simple bind for authentication (bind-as-user); directory reads use a configured bind DN. |
| ASM-AUTH-3 | The "administrator group" of the master spec is realized by `is_admin` (GD-4), not by an IdP group. |
| ASM-AUTH-4 | Data access group details: a record's group is per `record_id` (across all its events); a member with one or more groups always has exactly one active; a record created by a member without a group is unassigned (visible only to members without a group and to administrators); reassignment requires `project_admin` (REQ-AUTH-048); deleting a group that still has assigned records is rejected. |
| ASM-AUTH-5 | The authorization decision is a single explicit function over attributes — subject, `is_admin`, role, arm, (instrument, event) pair, data access level, export level, the two rights, active data access group (REQ-AUTH-045) — i.e. an ABAC-style evaluation implemented in the Go API; no external policy engine is required, and every decision stays explicit and auditable (REQ-AUTH-019). |
| ASM-AUTH-6 | The provider publishes an OpenID Connect discovery document naming `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint` and `jwks_uri`, accepts PKCE with `S256`, and emits only the claims its own policy maps — so claim presence is a fact of provider configuration that CLARA can require but cannot supply (REQ-AUTH-078, REQ-AUTH-081). PingFederate 11.3 or newer satisfies this; RP-initiated logout needs 12.0 and multiple client authentication methods per client only arrive in 13.1. |

|---|---|---|
| DEV-AUTH-1 | (superseded by DEV-AUTH-5) `export_non_sensitive` added to the permission set | Decision GD-2 (user-confirmed: seven permissions); the seven-permission model was reworked into per-arm levels on 2026-09-19. |
| DEV-AUTH-2 | Session ownership fixed to the PHP layer; API is stateless w.r.t. admin sessions | Decision GD-1 (user-confirmed). The plan's `POST /api/v1/auth/login` is re-interpreted as a PHP→API call establishing user state + audit, not a browser-facing session endpoint. |
| DEV-AUTH-3 | Suggested permission sets recorded for the example presets | The plan names roles but not their permission sets; suggested defaults are documented in REQ-AUTH-020, where the presets are optional. |
| DEV-AUTH-4 | The named roles are optional presets, not mandatory built-ins | Owner decision (2026-09-19): `data-entry`/`data-manager`/`controller` are examples; a project MAY define none or different versions, and permissions MUST be matchable to any defined role (REQ-AUTH-021). |
| DEV-AUTH-5 | Permission model reworked to per-arm levels (data access + export), superseding the seven atomic permissions | Owner decision (2026-09-19): make GD-2 more explicit — per-arm data viewing levels (No Access/hidden, Read Only, View & Edit, Delete, Edit survey responses) and export levels (no access, de-identified, remove all identifier fields, full dataset). |
| DEV-AUTH-6 | Surveys in scope in limited form (link-filled survey instruments), narrowing the charter's survey out-of-scope | Owner decision (2026-09-19, GD-9): instruments marked as surveys are fillable via a record-specific public link without login. |
| DEV-AUTH-7 | Data access groups added (record-level visibility grouping, orthogonal to the permission levels) | Owner decision (2026-09-19, GD-10): projects MAY have groups; a member's active group scopes the visible records; group-less members see all records. |
| DEV-AUTH-8 | Table-based (local password) authentication added as a third login path; `REQ-AUTH-036` revised from "no password storage" to "no plaintext storage; bcrypt hash only" | Owner decision (2026-09-22, GD-18; master spec "Details"): first-install usability without an IdP; bootstrap admin password from `ADMIN_BOOTSTRAP_PASSWORD`; local tried first on the password form, LDAP remains the fallback (REQ-AUTH-050/051) — the ordering was superseded by named-source parallel resolution on 2026-09-29 (DEV-AUTH-14). |
| DEV-AUTH-9 | Account validity period and inactivity auto-disable added (GD-19) | Owner decisions (2026-09-22; master spec "Details"): accounts valid for a limited time in days (`0` = indefinite); auto-disable after 180 days without login; admin re-enable; status visible on the user overview (REQ-AUTH-052/053). |
| DEV-AUTH-10 | Two-factor authentication added (GD-21), scoped to the CLARA-verified login paths | Owner decision (2026-09-28; master spec "Details"): by-user configurable 2FA with a phone-based key option and an email option. Realized as TOTP (RFC 6238 — works offline, no SMS gateway needed) and email one-time codes over a configured SMTP relay; guards the local + LDAP form logins after first-factor success. On the OAuth2 path MFA stays with the identity provider — asking CLARA's own second factor on top of an already-MFA'd IdP assertion double-prompts without adding a second, independent factor to CLARA's trust boundary (REQ-AUTH-054…059). |
| DEV-AUTH-11 | Account onboarding and password lifecycle added: emailed invite, self-service change, emailed reset (GD-22/GD-23) | Owner decision (2026-09-28): gap analysis of the FIONA reference — table-based mode (GD-18) needs a first-password path beyond admin-set passwords; users need self-service change/reset. The reference's mechanisms are adopted as *behaviors*, redesigned for security — hashed single-use tokens instead of plaintext temp passwords, generic responses instead of the enumeration oracle, current-password proof for changes (REQ-AUTH-060/061/062). |
| DEV-AUTH-12 | The reference's access-application workflow (`requestLogin.php`) stays out of scope | Owner decision (GD-24): REQ-AUTH-028's information page is the adopted form; its instructions are an admin-editable translation string (`User_Interface_Design.md` §5.7). A request intake pipeline is a workflow product, not EDC scope. |
| DEV-AUTH-13 | (superseded by DEV-AUTH-17) Password change/reset does not revoke existing PHP sessions | The API is stateless (GD-1); there is no server-side session registry to revoke against. Accepted for phase 1; exposure window bounded by `SESSION_LIFETIME` (REQ-AUTH-015). |
| DEV-AUTH-14 | Named authentication sources replace the implicit fallback chain: the user selects a source **by name** before login, and all credential-checked sources under that name are tried **in parallel** with first-success-wins — superseding REQ-AUTH-003's sequential LDAP fallback (1→2→3) and REQ-AUTH-051's local-first-then-LDAP ordering | Owner decision (2026-09-29, master spec "Authentication order"): multi-institution deployments need users to choose their own identity provider ("Hospital 1", "Hospital 2"); names relate many-to-many to sources. A side benefit is privacy: credentials now reach only the sources under the selected name, never an unrelated directory. Interactive OAuth2 cannot be raced silently against a credential form, so it stays selection-driven within the chosen name (REQ-AUTH-066). |
| DEV-AUTH-15 | Login-time bootstrap promotion narrowed (REQ-AUTH-007): never re-enable a disabled account; promote an existing enabled row only when the source is `local` or no other enabled admin exists | Owner decision (2026-10-02, security finding F10): every OAuth2/LDAP login whose email equalled `ADMIN_BOOTSTRAP_EMAIL` re-created administration — an IdP accepting unverified addresses, or one whose `mail` attribute users can edit, could take over the installation and undo a deliberate disable. The startup provisioning (the setup path of REQ-AUTH-051) is unchanged; assignment after setup runs through REQ-API-136. The PHP OAuth callback now requires boolean `email_verified = true` before it can resolve a login identity (REQ-AUTH-078); API-side signed assertion verification remains open under REQ-AUTH-076…084. |
| DEV-AUTH-16 | Local passwords are hashed with **argon2id** instead of bcrypt (REQ-AUTH-016/036/050/060; GD-18 — DEV-AUTH-8's "bcrypt hash only" now reads "argon2id hash only"). Hashes are PHC strings (`$argon2id$v=19$m=…,t=…,p=…$salt$hash`) carrying their own parameters — RFC 9106's second recommended setting, 64 MiB, three passes, four lanes; nothing else verifies, so there is no bcrypt fallback. The password policy's upper bound rises from 72 bytes (bcrypt's input limit) to 1,024 bytes, which only bounds the work one request can ask for. | Owner decision (2026-10-11; `VISION_AND_REQUIREMENTS.md` "Later: bcrypt password improvements"): bcrypt silently caps its input at 72 bytes and is cheap to attack on GPUs; argon2id is memory-hard and comes from the already-admitted `golang.org/x/crypto` module (`Technology_Stack_Design.md` §3). No installation holds local accounts yet, so no stored bcrypt hash needs carrying over. |
| DEV-AUTH-17 | Session lifecycle hardened (REQ-AUTH-015 amended; REQ-AUTH-072…075): a 30-minute idle timeout beside the 8-hour absolute lifetime; automatic session id rotation every 15 minutes with a 60-second grace window; replay detection on a rotated-away id; a per-account session epoch through which password, disable and two-factor-reset changes end existing sessions (superseding DEV-AUTH-13); production refuses non-`Secure` session cookies, and `Secure` ones carry the `__Host-` prefix. | Owner decision (2026-10-11; `VISION_AND_REQUIREMENTS.md` — the JWT/refresh-token question — and security finding F17). The general recommendation to replace stateful sessions with signed JWTs and rotating refresh tokens targets clients that call resource servers directly. In CLARA the browser talks only to PHP (REQ-AUTH-010) and the API re-reads the acting user on every call (REQ-AUTH-013/033), so a self-contained token would save no lookup, and refresh-token rotation with reuse detection needs server-side state anyway. The properties that recommendation is after — short-lived credentials, automatic rotation, theft detection, server-side revocation — are delivered on the existing opaque session instead: GD-1 holds (the epoch is account state, not a session registry) and no dependency is added. The data API's project tokens are untouched (REQ-AUTH-029…033). |
| DEV-AUTH-18 | OpenID Connect assertion verification moved to the internal boundary (REQ-AUTH-076…084; REQ-CFG-035/036): the web layer still owns Sequence A end to end, but Sequence C now carries the provider's signed ID token and the API verifies it before resolving an account. The earlier design let PHP vouch for a provider login with no artifact at all, which is the `source: oauth2` leg of security finding F8. This is **not** a reopening of DEV-AUTH-17's rejection of stateless browser sessions (`Design/Authentication_Authorization_Design.md` §3.1), which concerned the browser-to-PHP hop and still stands; `INTERNAL_SERVICE_TOKEN` is unchanged for every other call, and local and LDAP logins keep their current path. Requires an account-linkage store for (`iss`, `sub`) in `Database_Schema_Requirements.md`. |
