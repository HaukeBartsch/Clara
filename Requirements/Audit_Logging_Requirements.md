# Audit Logging — Requirements Analysis

**Project:** Clinical Study Management System (REDCap API Replacement)\
**Source:** `VISION_AND_REQUIREMENTS.md` (master spec); seeded from the area plan `Plan/Audit_Logging.md`, retired 2026-10-28 and kept in history (`git show 2b0c371:Plan/Audit_Logging.md`)\
**Status:** Approved for development handoff\
**Date:** 2026-09-19

## 1. Purpose

Defines the requirements for the system's audit trail: the two append-only audit tables, the complete event taxonomy, the minimum content of entries, the boundary between the audit trail and application logging, and the authorized read access. `Design/Audit_Logging_Design.md` contains the normative event catalog (event codes, payload schemas) and the partitioning/rollover mechanics.

## 2. Audit Store

| ID | Requirement |
|---|------|
| REQ-AUD-001 | The system MUST maintain two audit tables: `audit_events` (change/create/delete actions, project structure changes, exports, authentication, administration) and `audit_record_views` (record pulls via the data API only) (BR-007, REQ-DB-021). |
| REQ-AUD-002 | Both tables MUST be append-only: the application MUST expose no operation that updates or deletes audit entries; on MariaDB, immutability MUST additionally be enforced at the database privilege level (REQ-DB-024). |
| REQ-AUD-003 | An audit entry MUST commit in the same transaction as the operation it describes: an import, deletion, or structure change whose audit entry cannot be written MUST roll back (DEV-AUD-1); no data change MAY commit without its audit entry. |
| REQ-AUD-004 | Audit entries describe operations that completed: rejected calls (401/403/400) and validation-failed imports MUST NOT generate data-change or record-view entries (REQ-API-035 scopes audit to successful imports); security-relevant rejections remain audit-logged as authentication/administration events (REQ-AUTH-013). |
| REQ-AUD-005 | Every entry MUST carry a timestamp in UTC (GD-7). |
| REQ-AUD-006 | The tables MUST support yearly rollover without application changes: MariaDB partitioned by year; SQLite per-year tables behind stable view names. Reads MUST go through the stable names only. Writes go to the stable name on MariaDB and to the current-year physical table on SQLite, which cannot insert through a compound view (DEV-AUD-3); either way rollover requires no application change (REQ-DB-022, plan \"Table Partitioning\"). |
| REQ-AUD-007 | The audit trail is a business record, not application logging: it MAY record the token and old/new values as defined in §3–§5; application logs MUST NOT contain tokens, the service secret, or record values (REQ-API-005, REQ-TECH-016). |

## 3. Event Taxonomy — `audit_events`

| ID | Requirement |
|---|------|
| REQ-AUD-008 | **Authentication events.** Every login attempt (success and failure, with the authentication source `oauth2`\|`ldap`\|`local` and, when the user selected one, the authentication-source **name** — REQ-AUTH-067; for a credential race, exactly one event per submission carrying the winning or failed sources' outcomes in its details, `Authentication_Authorization_Design.md` §2.9), every logout, and every rejected administration API call MUST be recorded (REQ-AUTH-005/008/013/035, REQ-API-044/045). |
| REQ-AUD-009 | **Data change events.** Every record create, update, and delete MUST be recorded with the acting user, the token used, the record, and the changed fields; updates MUST include the old and new values, and deletions MUST include the deleted values, as a JSON details payload (plan \"Log Details\", GD-3, REQ-API-035/036). |
| REQ-AUD-010 | **Project structure events.** Every change to arms, events, instruments, fields (including renames, reordering, and deletion with cascaded values), the instrument-event mapping, and project metadata MUST be recorded with the acting user, the target project, and old/new values where applicable (plan \"Logged Events\", REQ-API-043, REQ-VAL-014). |
| REQ-AUD-011 | **Export events.** Every data export — data API (`content=record&action=export`) or administration API (`GET /api/v1/projects/{id}/export`) — MUST be recorded with the acting user/token, the project, the sensitivity level applied (one of the four GD-2 export levels: the most protective among the (instrument, event) pairs actually delivered, together with the count of pairs dropped for want of a level, REQ-EXP-003), and the filters supplied (REQ-API-076, BR-008). |
| REQ-AUD-012 | **Administration events.** Every user account change (create, re-enable, disable), every membership/role change, and every token issuance, rotation, and revocation MUST be recorded with the acting administrator, the target user, and the target project (REQ-AUTH-030, REQ-API-043/054/055). |
| REQ-AUD-033 | **Token view events.** Every time an administrator unmasks a just-issued project token on the Members page (REQ-UI-062), and every time a member unmasks their own token on the account page (REQ-UI-063, REQ-API-162), MUST be recorded as `token_viewed` — an entry of its own, separate from the `membership_changed` and `token_issued`/`token_rotated` entries of the add or rotation — with the acting user, the member whose token it is, and the project; each Show is one entry. A member's view of their own token is the entry whose acting user is that member. The token value MUST NOT be recorded (REQ-API-005, REQ-AUD-007). The view MUST be recorded before the value is displayed: a view that cannot be recorded is not displayed (master spec: "The user might 'show' the token … which should be logged in the audit trail as token viewed, separate from user added"; "allow the user to see his current token (audited)"). |
| REQ-AUD-021 | **Survey events.** Every survey link submission (success and failure) MUST be recorded with the link token, the project, the record, the instrument, the changed values, and the timestamp (UTC); link issuance and revocation MUST be recorded as administration events (GD-9, REQ-AUTH-039/040). |
| REQ-AUD-022 | **Data access group events.** Every group creation and deletion, every member group assignment change, every active-group switch, and every record group assignment/reassignment MUST be recorded with the acting user, the project, the affected group(s) and record(s), and the timestamp (UTC) (GD-10, REQ-AUTH-046/048). |
| REQ-AUD-023 | **Calculated field updates.** Every system-driven recomputation MUST be recorded with the triggering user, the project, the record, the calculated field, the old and new values, and the timestamp (UTC) (REQ-VAL-038). |
| REQ-AUD-024 | **Account auto-disable event.** The inactivity auto-disable of the account active rule MUST be recorded (`account_auto_disabled`, `source=system`) with the account, its last successful login, and the applied limit (GD-19, REQ-AUTH-053). |
| REQ-AUD-025 | **Project mode events.** Every mode change MUST be recorded with the old and new mode and — for development → production — the keep/delete decision; every staging set open, commit, and discard MUST be recorded, a commit additionally with the staged changes applied and the breaking changes that were acknowledged; a structure change applied in analysis mode under `acknowledge_breaking` MUST carry that acknowledgement on its own structure event (GD-20, REQ-API-105/106/111). |
| REQ-AUD-026 | **Instrument completion event.** Setting or clearing the (record, event, instrument) completion state MUST be recorded (`instrument_completed` / `instrument_uncompleted`, `source=ui`), with the record, the event, the instrument, and the resulting state (REQ-API-110). The entry carries no field values — the event changes none (REQ-AUD-007). |
| REQ-AUD-027 | **System settings event.** Every applied change of a system setting MUST be recorded (`settings_updated`) with the acting administrator and the old and new value of each changed key (`rate_limit_enabled`, `rate_limit_rpm`, …) (REQ-API-112; master spec "Rate limitter"). A PUT that changes nothing writes no entry (REQ-AUD-004). |
| REQ-AUD-028 | **Two-factor events (GD-21).** Enrollment (`tfa_enrolled` — method and acting user), self-service disable (`tfa_disabled`), and administrator reset (`tfa_reset` — acting admin and target account) MUST be recorded. A failed second-factor verification is a `login_failure` with reason `bad_mfa_code`; the successful `login_success` entry records the second factor used (`totp`, `email`, or `recovery`) in its details. Secrets, codes, and recovery codes MUST NOT appear in any audit detail (REQ-AUTH-036 extended). |
| REQ-AUD-029 | **Password lifecycle events (GD-22/GD-23).** The catalog MUST include `user_invited`, `invite_accepted`, `password_changed` (self-service), `password_reset_requested`, and `password_reset_completed`. All carry the acting user where authenticated; reset requests record the submitted address and source IP but MUST never record token values or password material (REQ-AUTH-036 extended, REQ-AUTH-060/062). |
| REQ-AUD-030 | **Session replay event.** A replaced session id presented after its grace window (REQ-AUTH-073) MUST be recorded as `session_replay_detected` with the account and the presenting address, in the same transaction that raises the account's session epoch (REQ-AUTH-074). Session ids MUST NOT be recorded. A call refused for a stale epoch is a rejected administration call (`admin_rejected`, reason `session_revoked` — REQ-AUD-008). |
| REQ-AUD-034 | **Transfer events.** Every executed cross-project transfer (REQ-API-165) MUST record in the **source** project a `transfer_executed` entry — acting user, source record and field, target project, target record, whether the record was created, and which fields were copied or skipped — carrying no values; the writes to the **target** project MUST additionally appear there as the standard data-change events (REQ-AUD-009) with a reference to the source project and record. All entries ride the operation's transaction (REQ-AUD-003); a failed transfer records nothing that did not happen. |
| REQ-AUD-035 | **Record read events.** Every display of a record's stored values in the web interface — a render of the record view (`GET /projects/{id}/records/{record}`, `User_Interface_Design.md` §8) — MUST be recorded in `audit_events` as one `record_read` entry carrying the acting user, the project, and the record in `target_record`, with `source=ui` (REQ-AUD-017/018). Its `details` name the event, instrument, and repeat instance shown and NO values — REQ-AUD-014 holds on both trails. One page view is exactly one entry, however many history pages the prefill walked (REQ-API-137): the walk itself writes nothing. The entry MUST be written before the values reach the browser: a record whose read cannot be recorded is not displayed, in the order `token_viewed` already keeps (REQ-AUD-033). A render that discloses no stored values writes no entry (REQ-AUD-004) — the new-record form, a read the actor is not entitled to (data access below `read_only`, a record invisible under the data access group rule, REQ-AUTH-045), or a page that failed to load. Record data pulled through the data API stays in `audit_record_views` and gains no `record_read` entry (REQ-AUD-013); survey-link prefills and assistant pulls are data-API reads and appear there already, so every read of record values is in the trail exactly once (ASM-AUD-2, DEV-AUD-6). |

## 4. Record View Log — `audit_record_views`

| ID | Requirement |
|---|------|
| REQ-AUD-013 | Every invocation of `content=record&action=export` MUST be recorded — regardless of initiator (external caller such as Fiona, or the PHP layer) — with: when (UTC), who (user), which records, which instruments, and which token (plan \"Storage\", REQ-API-030, REQ-DB-021). |
| REQ-AUD-014 | The record view log MUST NOT record the record values themselves, only the records and instruments accessed (plan: \"who, when, which records/instruments, which token\"). |
| REQ-AUD-015 | Reads that do not return record values (`project`, `metadata`, `event`, `formEventMapping`, `exportFieldNames`, record status) MUST NOT be written to `audit_record_views` (REQ-DB-021: record pulls via the API only). |

## 5. Entry Content

| ID | Requirement |
|---|------|
| REQ-AUD-016 | Every `audit_events` entry MUST contain at minimum: timestamp (UTC), acting user id, action (stable event code), target project (where project-scoped), and a JSON details payload (plan \"Log Details\"); the design document defines the full event code catalog and payload schemas (ASM-AUD-3). |
| REQ-AUD-017 | Every entry MUST identify the origin of the call (data API vs. administration API/UI) so the trail distinguishes direct token calls from UI-mediated actions (REQ-DB-021 `source`, DEV-DB-4). |
| REQ-AUD-018 | Data API entries MUST record the token used (plan: \"which token\"); administration API entries MUST record the acting user (REQ-API-041/043). |

## 6. Read Access

| ID | Requirement |
|---|------|
| REQ-AUD-019 | The audit trail MUST be readable only through `GET /api/v1/audit` (REQ-API-077) and the record history endpoint (REQ-API-079); both MUST be read-only and paginated; `GET /api/v1/audit` MUST be reserved to `is_admin` acting users, who MAY query all projects — a non-admin MUST receive a uniform 403 (REQ-API-078, finding F2). The record history endpoint keeps its project-visibility gate (REQ-API-079). |
| REQ-AUD-020 | The audit tables MUST be indexed to support the read access patterns: time range, project, user, event type, and record (REQ-API-077 pagination, REQ-API-079 record history, at the reference scale of REQ-DB-025; DEV-AUD-2). |
| REQ-AUD-031 | The audit trail MUST be exportable as CSV in a ZIP container through `GET /api/v1/audit/export` (REQ-API-158) — a third read path beside the two of REQ-AUD-019, under the same gate: `is_admin` only, every other acting user receiving the uniform 403 (REQ-API-078). The export MUST honor the listing's filters (`type`, `project`, `user`, `event_type`, `from`, `to`) and MUST include every matching entry regardless of pagination; it MUST be streamed without materializing the log in memory (REQ-TECH-011), and every export MUST be recorded as an `audit_export` event (REQ-AUD-011, BR-008). |
| REQ-AUD-032 | Before an export estimated to exceed 1 GiB the user MUST be warned with the estimate and asked to confirm it (master spec: "As Audits might be multi-GB in size warn the user for large exports (more than 1GB)"). The estimate is advisory — a confirmed or smaller export still delivers every matching entry (REQ-AUD-031). |

## 7. Assumptions

| ID | Assumption |
|---|------|
| ASM-AUD-1 | Retention beyond the yearly rollover is an operational decision; the schema supports indefinite retention (yearly partitions/tables, REQ-DB-022) and defines no expiry. |
| ASM-AUD-2 | A read of record values is in the trail whichever way it arrived: through the data API as an `audit_record_views` row — the PHP layer initiating that call counts as the pull (ASM-API-3, REQ-AUD-013) — or through the web interface's record view as a `record_read` event (REQ-AUD-035, DEV-AUD-6). The record status dashboard and structure reads return no record values and belong to neither trail (REQ-AUD-015). |
| ASM-AUD-3 | The exact event codes and payload schemas are normative in the design document; this document fixes the taxonomy and the minimum entry content. |

## 8. Deviations from Plan

| ID | Deviation | Rationale |
|---|---|---|
| DEV-AUD-1 | The audit entry commits atomically (same transaction) with the audited operation | The plan mandates logging but is silent on transactional coupling; atomicity guarantees no data change ever commits without its audit entry (REQ-AUD-003). |
| DEV-AUD-2 | Explicit indices for the audit read patterns (time range, project, user, event type) | The plan is silent on audit indexing; required for the paginated read API (REQ-API-077) to stay responsive at the reference scale (REQ-DB-025). |
| DEV-AUD-3 | On SQLite the application writes the current-year physical table rather than the stable view name | A `UNION ALL` view is not insertable in SQLite, so the original "read and write through the stable names only" would make every audit entry fail from the first day of the second year. An `INSTEAD OF INSERT` trigger cannot fix it — SQLite has no dynamic SQL, so a trigger body cannot derive the target table from `NEW.created_at`. Reads keep the stable name; the writer resolves the year from the timestamp it stores (REQ-AUD-006, `Design/Audit_Logging_Design.md` §6.2). |
| DEV-AUD-4 | The audit tables' primary key is composite — `(id, created_at)` — not the single-column `id` of REQ-DB-004 | MariaDB requires every unique key of a range-partitioned table to include the partitioning column (error 1503), so a year-partitioned audit table cannot carry `id PRIMARY KEY`. Consequence: `id` is unique within a year only, and an audit entry is addressed by `(id, created_at)` (`Design/Audit_Logging_Design.md` §6.1). |
| DEV-AUD-5 | Login events carry the user-selected authentication-source name; a named-source credential race produces exactly one `login_failure` per submission with per-source outcomes in `attempts` | Owner decision (2026-09-29, master spec "Authentication order"; `Authentication_Authorization_*` DEV-AUTH-14): parallel attempts under one name would otherwise emit a failure event per source — one event per submission keeps the trail aligned with the single user-facing login action, while `attempts` preserves the diagnostic detail (REQ-AUD-008). |
| DEV-AUD-6 | A browser read of a record is audited as a `record_read` event in `audit_events`, not as an `audit_record_views` row | Owner decision (2026-10-19, master spec "Next things": "Why is the record view in audits empty even if I have opened a record in the record viewer before?"). The view log was specified for API pulls only and is keyed by the call's token — `token` NOT NULL, "the only actor a record pull has" (`Design/Audit_Logging_Design.md` §4) — whereas a record view presents no token: it is an administration call made by the acting account (`source=ui`, REQ-AUD-018). A separate event keeps both shapes intact instead of making the key nullable and rewording REQ-AUD-001/013/015, and rides the write order `token_viewed` proved (REQ-AUD-033). Consequence for the Control Panel: the **Record views** log keeps its precise meaning — record pulls through the data API — and browser reads appear in the **Events** log, selectable as `record_read` (`Design/Audit_Logging_Design.md` §3.9). |
