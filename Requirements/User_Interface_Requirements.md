# User Interface — Requirements Analysis

**Project:** Clinical Study Management System (REDCap API Replacement)\
**Source plan:** `Plan/User_Interface.md`, `VISION_AND_REQUIREMENTS.md` (master spec)\
**Status:** Approved for development handoff\
**Date:** 2026-09-19

## 1. Purpose

Defines the web user interface requirements: the views, the permission gating of every page/section/action, and the UI obligations parked in the other area documents (record history, data access groups, calculated-field test, survey page, escaping in value views). `Design/User_Interface_Design.md` contains page layouts, component details, and interaction specifications.

## 2. Common Requirements (all views)

| ID | Requirement |
|---|------|
| REQ-UI-001 | The UI MUST be plain HTML and vanilla JavaScript with Bootstrap as the only UI library; no frontend framework and no build step (REQ-TECH-001). Pages are rendered by the PHP layer, which delegates all data access to the API (REQ-TECH-006, master spec). |
| REQ-UI-002 | The browser MUST talk only to PHP routes; it MUST NOT call `/api/v1/*` directly — PHP invokes the API server-side with the service token and acting user id (GD-1, REQ-AUTH-010, REQ-TECH-006). |
| REQ-UI-003 | Every page, section, and action MUST be present in the UI only when the acting user's effective permissions allow it (REQ-AUTH-027); "hidden" means absent from the DOM, not merely disabled. |
| REQ-UI-004 | All user-supplied content MUST be rendered safely: free-form text values are stored sanitized and rendered as allowlist HTML (REQ-VAL-030/031); **all other** content (choice values, labels, record names, user names, audit fields) MUST be escaped server-side (REQ-TECH-020); the Content-Security-Policy header MUST be sent (REQ-TECH-020). |
| REQ-UI-005 | All state-changing browser requests MUST carry the per-session CSRF token (REQ-AUTH-037). |
| REQ-UI-006 | A user who is neither an administrator nor a member of any project MUST be shown an information page explaining how access is granted (REQ-AUTH-028), not an empty dashboard. |
| REQ-UI-007 | Login is the PHP-side flow **against the authentication-source name the user selected** (REQ-AUTH-063…067, master spec "Authentication order"): an OAuth2 provider redirect for a name mapped to a provider (REQ-AUTH-001/066), or the email+password form, which races the local and LDAP sources under the selected name **in parallel** with first-success-wins (GD-18, REQ-AUTH-050/051/065); the login page MUST show provider buttons only for providers under the selected name and the email+password form whenever credential sources exist under it (it is the only path on a first install without an IdP); on session inactivity timeout or logout the user MUST be returned to the login page (REQ-AUTH-015); logout MUST call the API's logout endpoint before destroying the session (REQ-API-045). |
| REQ-UI-008 | The UI MUST be multilingual with English as the default and fallback (GD-12): every UI string — including JavaScript-originated messages — MUST be translated via the mapping tables (REQ-DB-031) or fall back to English, never a blank or a raw key; Norwegian Bokmål (`nb`) and Nynorsk (`nn`) are the first target languages; translations MUST be applied server-side at render time (no i18n JavaScript library, consistent with REQ-TECH-001); responsive Bootstrap layout. |
| REQ-UI-032 | **Layout, style, and client-side data binding (reference application).** The web application MUST adopt the layout and visual style of the historic FIONA reference in `assets/table_based_authentication_plus_user_management/` (master spec, "Details"): the left **sidebar + content-panel** pattern on the pages that carry several switchable sections — the project page and the Control Panel (REQ-UI-046) — the Bootstrap grid, **`table-sm`** condensed tables, and a **responsive** layout that adjusts to tablet and phone widths. The reference's single global sidebar is **not** adopted: which pages carry a left panel, and what is in it, is fixed by REQ-UI-046 (DEV-UI-14). It MUST also adopt the reference's *interfacing style* for the presentation layer (REQ-TECH-025): the PHP layer renders each page's shell, structure, and static content, and the client populates **data regions** — list rows, table bodies, `<select>` options — by pulling JSON from PHP endpoints and writing it into DOM targets; the client performs **no page switching** (no SPA; REQ-UI-001, REQ-TECH-001). The reference is a style and interaction model, **not** a technology one: it is realized with **Bootstrap 5.3.x** (not the reference's Bootstrap 2.x) and **vanilla ES2020** (not jQuery). Where the reference diverges from a fixed convention it is **not** adopted: client-populated content MUST use safe DOM APIs (`textContent`/`createElement`) for all content except the stored free-text allowlist HTML (REQ-UI-004, REQ-TECH-020); UI strings remain translated server-side (REQ-UI-008); mutations remain CSRF-protected `POST`s to PHP routes (REQ-UI-005); and the browser talks only to PHP routes, never `/api/v1/*` (REQ-UI-002). The reference's `AC.php` is the model for the PHP session-establishment flow (GD-1, `Authentication_Authorization_Design.md` §3), not for the authentication mechanism. |
| REQ-UI-038 | **Two-factor challenge at login (GD-21, REQ-AUTH-055).** When the first factor succeeds on an account with a method other than `off`, the login page MUST present a second step — a single code field ("Enter the code from your authenticator app" for `totp`; "We sent a code to your email address" with a resend action for `email`) plus an alternate-entry link for recovery codes. A wrong or expired code shows the translated failure line and counts toward the lockout (REQ-AUTH-058); no session content is reachable between the two steps. With `AUTH_REQUIRE_2FA` on and no enrolled method, the first-factor success leads to the enrollment wizard of REQ-UI-039 before login completes. |
| REQ-UI-042 | **Source-name picker at login (master spec "Authentication order", REQ-AUTH-063/064/067).** Before credentials are entered, the login page MUST present the distinct set of configured authentication-source names ("Hospital 1", "Hospital 2", …) as a selectable choice; selecting a name reveals only what its sources offer — the email+password form when local/LDAP sources exist under it (submitting races them, REQ-AUTH-065), provider buttons per OAuth2 source under it (each initiating its own redirect, REQ-AUTH-066). With exactly one distinct name configured the picker is skipped; changing the selection clears any entered credentials. No name is preselected: until the user chooses one, neither the credential form nor any provider button is shown, and choosing a name applies it at once, with no separate confirm button (DEV-UI-13). The selected name is carried through the login exchange and shown nowhere else to the user afterward. |
| REQ-UI-039 | **Two-factor settings (self-service).** An account page — reachable from the signed-in shell for every user — MUST show the current method (`off` / `totp` / `email`) and offer: enable TOTP (QR code plus manual-entry secret, one confirmation code, then the recovery codes shown exactly once with a copy affordance), enable email (confirmation code delivered to the account address; the option is absent when SMTP is not configured — REQ-AUTH-057), and disable (asking for a current code). The secret and codes never reappear after their one-time display (REQ-AUTH-056); all actions are CSRF-protected `POST`s (REQ-UI-005) bound to the endpoints of REQ-API-115. |
| REQ-UI-044 | **Data-region JSON is served by the page routes, content-negotiated.** The JSON the client binds data regions from (REQ-UI-032, REQ-TECH-025) MUST be served by **the same route as the page it fills**, selected by the request's `Accept`: a request preferring `application/json` receives that route's data region as JSON, any other request receives the rendered page. No separate proxy-route family is introduced — the route set of `Design/User_Interface_Design.md` §2.1 stays the complete set of browser-reachable routes (REQ-UI-002). The negotiation MUST be implemented **once, in the router**; adding a page MUST NOT require per-page routing code for it. A data request passes the same session guard, permission gate and acting-user resolution as the page render it stands for: it discloses no more than the rendered page would (REQ-UI-003), exposes no API path or token (REQ-UI-002), and reports failure with the HTTP status and stable `error` code of `API_Endpoints_Design.md` §4.2 so the client shows the translated line of `User_Interface_Design.md` §3.4. Content negotiation covers **reads**; every mutation stays a CSRF-protected `POST` to the page route with `?action=<name>` (REQ-UI-005). |
| REQ-UI-045 | **Client script packaging — ES modules per view/logical section.** Application JavaScript MUST be vanilla ES2020 ES modules served same-origin and loaded with `<script type="module">`; no bundler, transpiler or other build step is introduced (REQ-UI-001, REQ-TECH-001, ASM-TECH-2). The client MAY be split across as many module files as the surface needs — a shared runtime (`web/assets/app.js`: fetch + CSRF helper, data-region binding, the JS-visible string block of `User_Interface_Design.md` §9) plus one module per view or logical section (record form, setup, designer, each administration page, the survey page) — and each page MUST load only the modules it uses. Modules MUST be addressable by relative path from the page, so no import map (an inline `<script type="importmap">`, which a `'self'` script source blocks) is needed and every module fetch stays same-origin (REQ-TECH-020); they are static files, emitted at most as a list of `src` references at render time. Vendored libraries remain under `web/assets/vendor/` (REQ-TECH-026/027) and UI strings remain injected server-side (REQ-UI-008). |
| REQ-UI-046 | **Page shells — where a left panel appears.** The signed-in surface uses three shell shapes, and a left panel appears only on a page that has several switchable sections (DEV-UI-14): the **project overview** (`GET /`) is header + one content panel + footer with **no left sidebar** (REQ-UI-009); the **project page** (`/projects/{id}` and its sections) carries a left panel of that project's functions and shows the selected one in the right-hand panel (REQ-UI-017); the **Control Panel** (`/admin` and its sections) carries a left panel of the administration sections and shows the selected one in the right-hand panel (REQ-UI-047). All three share one header — brand (linking to the project overview), the project name with its Overview link inside a project context, and the `is_admin` Control Panel button — and one footer: language selector (REQ-UI-029), theme selector (REQ-UI-041), the self-service account links (REQ-UI-039, and the password page only when the account has a local credential, GD-23) and Sign out (REQ-UI-007). Selecting a left-panel entry is a plain `GET` to that section's route rendered into the same shell — no client-side page switching (REQ-UI-001) — and an entry the acting user may not use, or whose section this build does not serve, is absent from the panel rather than disabled (REQ-UI-003). The login page, the public password pages, and the public survey page render a single centered panel with no header navigation and no account footer (no session). |

## 4. Administration Interface (`is_admin` only)

| ID | Requirement |
|---|------|
| REQ-UI-047 | **Control Panel (`GET /admin`).** Every installation-administration function lives on one page — the **Control Panel** — reachable from the header button of REQ-UI-009 and nowhere else (DEV-UI-15). Its left panel lists the sections **Users** (REQ-UI-011), **Projects** (REQ-UI-012), **Audits** (REQ-UI-016), **Translations** (REQ-UI-030) and **Settings** (REQ-UI-043); the right-hand panel shows the section selected there (REQ-UI-046). One route serves them all — `GET /admin?section=<name>`, defaulting to the first available section — and its data region is scoped to that section (REQ-UI-044); a `section` value this build does not serve renders the first available one, and a section whose function the acting user may not use is absent from the panel (REQ-UI-003). The whole page is `is_admin`-gated. Project-scoped administration — assignments, roles, data access groups (REQ-UI-013/014/015) — stays on the project page, because its permission is the project's own rather than the installation's. |
| REQ-UI-011 | **User accounts.** A list of accounts (email, display name, enabled, `is_admin`, authentication source — incl. `local`, **last login**, **validity end**, the derived status active / disabled / expired / auto-disabled — GD-19, REQ-AUTH-052/053 — and the **two-factor method** off / totp / email — GD-21, REQ-API-116) and actions to create an account (email + display name, optional validity in days with `0` = indefinite, optional local password), set/extend the validity, set or reset the local password, re-enable a disabled (incl. auto-disabled) one — which MUST restart the inactivity clock — disable one, and **reset two-factor authentication** for an account that lost its device or email access (confirm first; REQ-AUTH-059, REQ-API-116). Auto-disabled accounts MUST be visually distinguishable with the inactivity reason (REQ-AUTH-053). |
| REQ-UI-012 | **Projects.** A project creation form covering the simplified creation fields of REQ-DB-006 (name, organization = main supporting institution, PI name/email, data manager, REK/IRB number, REK start/end dates, start/end dates, participant naming pattern — GD-17; the option flags, end provision, end-user-contract confirmation, and initial-events list are **absent**) and a project edit form for the same metadata (REQ-API-050/052). Events are created in the project's Setup page (REQ-UI-018). |
| REQ-UI-013 | **Assignments.** Per project: the member list with role, data access groups, and token state; assign a member choosing a role from the project's actual roles — which MAY be empty — plus "no role" (full permissions, REQ-AUTH-020/022); issue and rotate tokens, displaying the new token exactly once with an explicit copy affordance (REQ-API-055); set a member's data access group assignments and active group (REQ-API-089, REQ-AUTH-044). |
| REQ-UI-014 | **Role editor.** Create and edit a role: naming it is how a new one is made (`data-manager`, `data-entry`, `controller` are typical names; the presets MAY be offered as starting points only — REQ-AUTH-020/021), and an existing role's whole permission set is editable in the same form (REQ-API-143). The form carries one section per function group, each introduced by an `<h4>` heading, in this order: **Permissions per instrument and event** — a table of the role's grants, one row per (instrument, event) pair mapped in the arm, with the arms behind tabs and the first arm shown by default (master spec "Arms, events and instruments"). Its column groups are **data access** — radio `no_access` / `read_only` / `view_edit` — and **export** — radio `export_none` / `export_de_identified` / `export_no_identifiers` / `export_full` — followed by two checkbox columns, **delete values** (**delete instrument values**) and **edit surveys** (**edit collected surveys**) (REQ-AUTH-017/069). A row's radios and checkboxes are independent of one another (REQ-AUTH-070); a checkbox on a `no_access` row has no effect and MUST be rendered disabled rather than silently ignored (REQ-UI-003), and an arm tab with no grant of its own shows the arm default each of its rows inherits (REQ-AUTH-069). **Project administration** — the `project_admin` checkbox (GD-2). A further function group joins this screen as another `<h4>` section when it gains a requirement; nothing else may be added to the role. The table renders condensed and responsive (`table-sm`, `User_Interface_Design.md` §1) with both header rows sticky, and offers per-column bulk setting (set all rows of an arm to one level) because a project's pair count is unbounded. |
| REQ-UI-015 | **Data access groups.** Create groups (name, unique per project) and delete them, with a warning that deletion is rejected while records are still assigned (REQ-API-087/088). |
| REQ-UI-016 | **Audit view.** A paginated, read-only table of audit entries with a project filter and the acting-user/target fields (REQ-API-077/078, REQ-AUD-019); a non-administrator sees only entries of their own projects; values MUST be escaped (REQ-UI-004). |
| REQ-UI-043 | **System settings.** A settings page showing the current system-wide runtime settings with an editor for them (REQ-API-112): the rate-limiting switch (`rate_limit_enabled`), the requests-per-minute threshold per source IP (`rate_limit_rpm`, ≥ 1) and the blockout period an over-budget source IP stays blocked (`rate_limit_block_minutes`, 1–1440 minutes, REQ-API-113) — customizable here, effective immediately after save without a restart, and audit-logged with old and new values (REQ-AUD-027; master spec "Rate limitter"). |

## 5. Project Workspace

| ID | Requirement |
|---|------|
| REQ-UI-017 | The **project page** MUST carry a left panel of the project's functions and show the selected one in its right-hand panel (REQ-UI-046). The entries are, in this canonical order: **Overview**, **Setup**, **Design**, **Record Status Dashboard**, **Export**, and — where allowed — **Members**, **Roles**, **Groups**. Each entry is present only when the acting user may use it (REQ-UI-003): Overview for every member who can see the project; Setup and Design require `project_admin`; Record Status Dashboard requires data access ≥ `read_only` on at least one (instrument, event) pair; Export requires a non-`export_none` level on at least one pair (REQ-API-075); Members and Roles require `is_admin`; Groups require data access ≥ `read_only` to read (mutating needs `project_admin`). On entering the project the right-hand panel MUST open the **first available entry after Overview** — Setup for a member allowed to change the setup, otherwise Record Status Dashboard for a member with data access — falling back to Overview when neither is allowed. Overview shows the project summary (record count, instrument count, field count — REQ-API-051), the read-only metadata block, and the mode badge (REQ-UI-033). |
| REQ-UI-018 | **Setup page.** Manage arms, events (label, **timepoint `period` — optional, blank = no timepoint** — safe region; displayed in the canonical per-arm order of GD-15 with **reorder controls for no-timepoint events** via the events-order endpoint, REQ-API-103), instruments (including the survey flag and the branching logic expression, REQ-DB-011), and the instrument-by-event mapping as per-arm checkboxes (REQ-API-058…073, REQ-API-103); an arm with events is hidden everywhere (REQ-AUTH-027) once removed. |
| REQ-UI-019 | **Record status dashboard.** A table of records × events with the instruments per arm in order and a **three-state** completion indicator per (record, event, instrument) — no data / some data / finished, grey / amber / green (REQ-API-074, DEV-UI-8) — without revealing field values (REQ-API-074, plan §6); a survey-marked instrument's indicator shows green automatically, its completion filled in without an assignment (GD-9); rows MUST be restricted to records visible under the data access group rule (REQ-AUTH-045). |
| REQ-UI-036 | **Completion control.** At the end of each instrument's form — always displayed as the last field (master spec "Instrument level completion info") — the member with data access ≥ `view_edit` MUST be able to set or clear that (record, event, instrument)'s completion state, effective immediately in the record-status dashboard (REQ-API-110). On a survey-marked instrument the same trailing field shows the completed state read-only, filled in automatically — no control, no assignment (GD-9). The control is absent for members without `view_edit` (REQ-UI-003). |
| REQ-UI-020 | **Export action.** Offer the project export in the acting user's export level (CSV or JSON), applied **per (instrument, event) pair**: the panel MUST state which levels are being applied and that an instrument the user may not export contributes no columns to the file rather than failing the download (REQ-API-075, REQ-AUTH-069); the download MUST stream for large exports (REQ-TECH-011). |
| REQ-UI-033 | **Mode.** The project home MUST show the current mode as a badge (development / production / analysis — GD-20), visible to every member. For an installation admin user (`is_admin`) it MUST offer a mode control presenting only the allowed transitions (REQ-API-105); a project's own `project_admin` sees the badge but no mode control: development → production opens a confirmation that asks whether previously stored data should be **kept or deleted**, naming the deletion consequence explicitly; production → development, production → analysis, analysis → production and analysis → development confirm with "all data is kept" (development → analysis is not offered — analysis is entered only from production). Attempting a mode change while a staging set is open shows the commit/discard prompt for **any** target mode (409 surfaced per the error mapping). Non-admins see the badge only. |
| REQ-UI-034 | **Staged setup (production).** When the project is in production mode, the Setup and Designer pages MUST present the staging controls (GD-20, REQ-API-106/108): **Start staging**; while a set is open a persistent banner ("changes are staged — not yet active") with **Commit staged changes** and **Discard**; the commit dialog lists the staged changes split into non-breaking and breaking (each breaking change with its reason) and requires an explicit acknowledgement before committing. In development mode these controls are absent — setup edits apply directly. |
| REQ-UI-037 | **Analysis-mode setup edit (GD-20).** While the project is in analysis mode, Setup and Designer changes apply directly, but one the API classifies as breaking MUST first show a confirmation naming the change and its consequence (`API_Endpoints_Design.md` §4.21); on confirm the page resubmits with `acknowledge_breaking: true` (REQ-API-111) and states that the change is now live. A non-breaking change saves with no prompt, as in development mode. |

## 7. Data Entry and Record View

| ID | Requirement |
|---|------|
| REQ-UI-025 | The data entry form MUST render the instrument's fields for the selected (record, event) — text inputs, dropdowns, radio groups, matrix rows expanded (REQ-DB-014) — and submit via the data API import path (REQ-UI-031). Client-side real-time validation is advisory only; the API is authoritative (REQ-VAL-002). Required fields MUST be presented as such and checked before submission (REQ-VAL-028); field and instrument branching logic MUST show or hide fields and whole instruments while the expression evaluates to true (1), and the display state MUST update when a referenced field's value changes (GD-13, REQ-VAL-029/040); Calculated fields MUST be rendered read-only (REQ-VAL-036). |
| REQ-UI-026 | **Per-field change history.** Next to each field's description and value in the "record instrument" web view, a small **history button** MUST open a table of that field's previous values — who entered or changed each value (user account), when, and old → new values — from the record history endpoint filtered to the field (REQ-API-079/081); values MUST be escaped (REQ-UI-004); the view MUST be read-only with respect to the audit trail (REQ-AUD-002). |
| REQ-UI-027 | **Record actions.** Offered on the **record instrument view** — the screen reached by selecting an instrument on the Record Status Dashboard (REQ-UI-019) — not on the dashboard itself: **delete this instrument's values**, present when the role holds **delete instrument values** on that (instrument, event) pair, and **delete the record**, present when it holds that right on every pair where the record has values (REQ-API-036). Both sit behind an explicit confirmation naming exactly what will be removed (GD-3). Show the record's current data access group and offer assign/change group to `project_admin` users (REQ-API-091); all actions gated per REQ-UI-003. |
| REQ-UI-028 | **Survey page.** For a (record, survey instrument) pair the record view MUST offer "copy link" (REQ-API-082) and "revoke link" (REQ-API-085). The public survey page is a standalone PHP-served route — no login, outside the session (GD-1, REQ-API-084) — showing only that instrument's fields for that record with a submit action (GD-9); the respondent may re-open the link to edit their responses (REQ-AUTH-042); submissions pass the same validation and audit rules as any import (REQ-AUTH-041, REQ-VAL-001). |
| REQ-UI-031 | **Submission policy (GD-14).** Fields may have no value; an instrument that is partially filled and saved stores only the entered values. The data entry form (and the survey page) MUST submit **only** (a) the fields that carry a value in the form, and (b) the fields that **had a stored value that the user removed** (the form tracks each field's original value and sends an explicit empty string for those); it MUST NOT submit empty values for fields that had no value and were left empty — an empty value reaching the API clears the stored value (REQ-VAL-024), so unsent fields keep their previous values. |
| REQ-UI-035 | **Analysis mode (GD-20).** While the project is in analysis mode, data entry is disabled: the data-entry form MUST NOT offer the submit control (values render read-only), the record-status dashboard's "new participant" affordance is absent, and the public survey page shows a closed state (submissions are rejected by the API, REQ-API-109). Viewing and export controls are unaffected. |
