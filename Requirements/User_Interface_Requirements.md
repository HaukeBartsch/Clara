# User Interface — Requirements Analysis

**Project:** Clinical Study Management System (REDCap API Replacement)\
**Source:** `VISION_AND_REQUIREMENTS.md` (master spec); seeded from the area plan `Plan/User_Interface.md`, retired 2026-10-28 and kept in history (`git show 2b0c371:Plan/User_Interface.md`)\
**Status:** Approved for development handoff\
**Date:** 2026-09-19

## 1. Purpose

Defines the web user interface requirements: the views, the permission gating of every page/section/action, and the UI obligations parked in the other area documents (record history, data access groups, calculated-field test, survey page, escaping in value views). `Design/User_Interface_Design.md` contains page layouts, component details, and interaction specifications.

> **Key constraints** — a summary for quick orientation; the cited IDs and sections are normative.
>
> - **The browser talks only to PHP routes**, never to `/api/v1/*` (REQ-UI-002; the one exception is the Configuration Check's exposure probe, REQ-UI-061).
> - **Hidden means absent from the DOM.** Gating is computed server-side, and the API re-checks every call (REQ-UI-003, REQ-AUTH-033).
> - **Everything is escaped server-side** except free text, which is sanitized to an allowlist when stored (REQ-UI-004).
> - **Every state-changing request carries the CSRF token** (REQ-UI-005).
> - **Plain HTML, vanilla JavaScript, Bootstrap — no build step** (REQ-UI-001).

## 2. Common Requirements (all views)

| ID | Requirement |
|---|------|
| REQ-UI-001 | The UI MUST be plain HTML and vanilla JavaScript with Bootstrap as the only UI library; no frontend framework and no build step (REQ-TECH-001). Pages are rendered by the PHP layer, which delegates all data access to the API (REQ-TECH-006, master spec). |
| REQ-UI-002 | The browser MUST talk only to PHP routes; it MUST NOT call `/api/v1/*` directly — PHP invokes the API server-side with the service token and acting user id (GD-1, REQ-AUTH-010, REQ-TECH-006). The one exception is the Configuration Check's exposure probe (REQ-UI-061), which requests an `/api/v1/` path without credentials precisely to confirm that the web server answers 404 for it. |
| REQ-UI-003 | Every page, section, and action MUST be present in the UI only when the acting user's effective permissions allow it (REQ-AUTH-027); "hidden" means absent from the DOM, not merely disabled. |
| REQ-UI-004 | All user-supplied content MUST be rendered safely: free-form text values are stored sanitized and rendered as allowlist HTML (REQ-VAL-030/031); **all other** content (choice values, labels, record names, user names, audit fields) MUST be escaped server-side (REQ-TECH-020); the Content-Security-Policy header MUST be sent (REQ-TECH-020). |
| REQ-UI-005 | All state-changing browser requests MUST carry the per-session CSRF token (REQ-AUTH-037). |
| REQ-UI-006 | A user who is neither an administrator nor a member of any project MUST be shown an information page explaining how access is granted (REQ-AUTH-028), not an empty dashboard. |
| REQ-UI-007 | Login is the PHP-side flow **against the authentication-source name the user selected** (REQ-AUTH-063…067, master spec "Authentication order"): an OAuth2 provider redirect for a name mapped to a provider (REQ-AUTH-001/066), or the email+password form, which races the local and LDAP sources under the selected name **in parallel** with first-success-wins (GD-18, REQ-AUTH-050/051/065); the login page MUST show provider buttons only for providers under the selected name and the email+password form whenever credential sources exist under it (it is the only path on a first install without an IdP); on session inactivity timeout, absolute expiry, revocation, a detected session replay, or logout the user MUST be returned to the login page — for each ended session with a translated line saying why (REQ-AUTH-015/073/074); logout MUST call the API's logout endpoint before destroying the session (REQ-API-045). |
| REQ-UI-008 | The UI MUST be multilingual with English as the default and fallback (GD-12): every UI string — including JavaScript-originated messages — MUST be translated via the mapping tables (REQ-DB-031) or fall back to English, never a blank or a raw key; Norwegian Bokmål (`nb`) and Nynorsk (`nn`) are the first target languages; translations MUST be applied server-side at render time (no i18n JavaScript library, consistent with REQ-TECH-001); responsive Bootstrap layout. |
| REQ-UI-032 | **Layout, style, and client-side data binding (reference application).** The web application MUST adopt the layout and visual style of the historic FIONA reference in `assets/table_based_authentication_plus_user_management/` (master spec, "Details"): the left **sidebar + content-panel** pattern on the pages that carry several switchable sections — the project page, the Control Panel and the account page (REQ-UI-046) — the Bootstrap grid, **`table-sm`** condensed tables, and a **responsive** layout that adjusts to tablet and phone widths. The reference's single global sidebar is **not** adopted: which pages carry a left panel, and what is in it, is fixed by REQ-UI-046 (DEV-UI-14). It MUST also adopt the reference's *interfacing style* for the presentation layer (REQ-TECH-025): the PHP layer renders each page's shell, structure, and static content, and the client populates **data regions** — list rows, table bodies, `<select>` options — by pulling JSON from PHP endpoints and writing it into DOM targets; the client performs **no page switching** (no SPA; REQ-UI-001, REQ-TECH-001). The reference is a style and interaction model, **not** a technology one: it is realized with **Bootstrap 5.3.x** (not the reference's Bootstrap 2.x) and **vanilla ES2020** (not jQuery). Where the reference diverges from a fixed convention it is **not** adopted: client-populated content MUST use safe DOM APIs (`textContent`/`createElement`) for all content except the stored free-text allowlist HTML (REQ-UI-004, REQ-TECH-020); UI strings remain translated server-side (REQ-UI-008); mutations remain CSRF-protected `POST`s to PHP routes (REQ-UI-005); and the browser talks only to PHP routes, never `/api/v1/*` (REQ-UI-002). The reference's `AC.php` is the model for the PHP session-establishment flow (GD-1, `Authentication_Authorization_Design.md` §3), not for the authentication mechanism. |
| REQ-UI-038 | **Two-factor challenge at login (GD-21, REQ-AUTH-055).** When the first factor succeeds on an account with a method other than `off`, the login page MUST present a second step — a single code field ("Enter the code from your authenticator app" for `totp`; "We sent a code to your email address" with a resend action for `email`) plus an alternate-entry link for recovery codes. A wrong or expired code shows the translated failure line and counts toward the lockout (REQ-AUTH-058); no session content is reachable between the two steps. With `AUTH_REQUIRE_2FA` on and no enrolled method, the first-factor success leads to the enrollment wizard of REQ-UI-039 before login completes. |
| REQ-UI-042 | **Source-name picker at login (master spec "Authentication order", REQ-AUTH-063/064/067).** Before credentials are entered, the login page MUST present the distinct set of configured authentication-source names ("Hospital 1", "Hospital 2", …) as a selectable choice, listed by name except that a name carried by the local source alone (e.g. "Local") comes last, after the institutions (owner decision 2026-10-13); selecting a name reveals only what its sources offer — the email+password form when local/LDAP sources exist under it (submitting races them, REQ-AUTH-065), provider buttons per OAuth2 source under it (each initiating its own redirect, REQ-AUTH-066). With exactly one distinct name configured the picker is skipped; changing the selection clears any entered credentials. No name is preselected: until the user chooses one, neither the credential form nor any provider button is shown, and choosing a name applies it at once, with no separate confirm button (DEV-UI-13). The selected name is carried through the login exchange and shown nowhere else to the user afterward. |
| REQ-UI-039 | **Two-factor settings (self-service).** A section of the account page (REQ-UI-063) — reachable from the signed-in shell for every user — MUST show the current method (`off` / `totp` / `email`) and offer: enable TOTP (QR code plus manual-entry secret, one confirmation code, then the recovery codes shown exactly once with a copy affordance), enable email (confirmation code delivered to the account address; the option is absent when SMTP is not configured — REQ-AUTH-057), and disable (asking for a current code). The secret and codes never reappear after their one-time display (REQ-AUTH-056); all actions are CSRF-protected `POST`s (REQ-UI-005) bound to the endpoints of REQ-API-115. |
| REQ-UI-044 | **Data-region JSON is served by the page routes, content-negotiated.** The JSON the client binds data regions from (REQ-UI-032, REQ-TECH-025) MUST be served by **the same route as the page it fills**, selected by the request's `Accept`: a request preferring `application/json` receives that route's data region as JSON, a request preferring `application/x-ndjson` receives it as newline-delimited JSON where the region streams (REQ-UI-074), any other request receives the rendered page. No separate proxy-route family is introduced — the route set of `Design/User_Interface_Design.md` §2.1 stays the complete set of browser-reachable routes (REQ-UI-002). The negotiation MUST be implemented **once, in the router**; adding a page MUST NOT require per-page routing code for it. A data request passes the same session guard, permission gate and acting-user resolution as the page render it stands for: it discloses no more than the rendered page would (REQ-UI-003), exposes no API path or token (REQ-UI-002), and reports failure with the HTTP status and stable `error` code of `API_Endpoints_Design.md` §4.2 so the client shows the translated line of `User_Interface_Design.md` §3.4. Content negotiation covers **reads**; every mutation stays a CSRF-protected `POST` to the page route with `?action=<name>` (REQ-UI-005). |
| REQ-UI-045 | **Client script packaging — ES modules per view/logical section.** Application JavaScript MUST be vanilla ES2020 ES modules served same-origin and loaded with `<script type="module">`; no bundler, transpiler or other build step is introduced (REQ-UI-001, REQ-TECH-001, ASM-TECH-2). The client MAY be split across as many module files as the surface needs — a shared runtime (`web/assets/app.js`: fetch + CSRF helper, data-region binding, the JS-visible string block of `User_Interface_Design.md` §9) plus one module per view or logical section (record form, setup, designer, each administration page, the survey page) — and each page MUST load only the modules it uses. Modules MUST be addressable by relative path from the page, so no import map (an inline `<script type="importmap">`, which a `'self'` script source blocks) is needed and every module fetch stays same-origin (REQ-TECH-020); they are static files, emitted at most as a list of `src` references at render time. Vendored libraries remain under `web/assets/vendor/` (REQ-TECH-026/027) and UI strings remain injected server-side (REQ-UI-008). |
| REQ-UI-050 | **Correlation reference on generic failures, development-time detail.** A generic failure line (`User_Interface_Design.md` §3.4 — "Something went wrong…") MUST show a correlation reference unique to the failed request alongside the translated text; the reference is an opaque token and discloses nothing (REQ-API-006 holds). Every web-layer log line written while serving that request MUST carry the same reference, so what the user saw greps back to the logged cause. A JSON failure envelope from the PHP layer SHOULD carry it as an additional `ref` field (additive; existing readers unaffected). The technical detail of a failure — error code, status, failing call and message; exception class and origin for fatal errors — MUST be rendered on screen only when `APP_ENV=development`; in every other environment the user-visible text stays free of internals. |
| REQ-UI-046 | **Page shells — where a left panel appears.** The signed-in surface uses four page shells, and a left panel appears only on a page that has several switchable sections (DEV-UI-14): the **project overview** (`GET /`) is header + one content panel with **no left sidebar** (REQ-UI-009); the **project page** (`/projects/{id}` and its sections) carries a left panel of that project's functions and shows the selected one in the right-hand panel (REQ-UI-017); the **Control Panel** (`/admin` and its sections) carries a left panel of the administration sections and shows the selected one in the right-hand panel (REQ-UI-047); the **account page** (`/account` and its sections) carries a left panel of the acting user's own settings (REQ-UI-063). All share one header — brand (linking to the project overview), the project name with its Overview link inside a project context, the Training link (REQ-UI-059), the `is_admin` Control Panel button, and the **account menu**, which names the signed-in user and offers the account page and Sign out (REQ-UI-007, REQ-UI-063). There is no footer (DEV-UI-18). Selecting a left-panel entry is a plain `GET` to that section's route rendered into the same shell — no client-side page switching (REQ-UI-001) — and an entry the acting user may not use, or whose section this build does not serve, is absent from the panel rather than disabled (REQ-UI-003). The login page, the public password pages, and the public survey page render a single centered panel with no header navigation and no account menu (no session). |
| REQ-UI-063 | **Account page (`GET /account`).** Every signed-in user MUST reach an **account page** from the header's account menu — a button naming the user, whose menu offers the account page and **Sign out** (REQ-UI-007), so signing out stays one choice away on every page. The account page carries a left panel (REQ-UI-046) of the user's own sections, in this order: **Profile** — name and address read-only (REQ-AUTH-061), the language selector (REQ-UI-029), the theme selector (REQ-UI-041) and Sign out; **Project tokens** — one row per project the user is a **member** of (REQ-API-161) with the role and that membership's data-API token, **masked** (`type="password"`, no value in the page) until the user chooses **Show**; Show has the API record the view and return the value in one call (REQ-API-162, REQ-AUD-033) and only then displays it, with a copy affordance; **Hide** masks it again and records nothing, and a further Show is a further entry; a refused reveal keeps the token masked with the §3.4 line; the value is kept nowhere for a later render; **Two-factor authentication** (REQ-UI-039); and **Password** (GD-23, REQ-AUTH-061) — present only when the account has a local credential (REQ-UI-003). `/account` opens on Profile. (Master spec: "The footer of Clara has language selection, theme, two-factor, password and Sign out. Those features should be moved to a dedicated account page for each user. That account page (reachable from the header) should also allow the user to see his current token (audited).") |

## 3. Dashboard

| ID | Requirement |
|---|------|
| REQ-UI-009 | The start page after login — the **project overview** — MUST be a single content panel below the header with **no left sidebar** (REQ-UI-046). It MUST list the projects visible to the user, one box per project, each carrying the quick statistics (record, instrument and field counts) as per `GET /api/v1/projects` (REQ-API-049); selecting a box's **project name** MUST open that project's page (§5). How those boxes are drawn is REQ-UI-070's, and the order they appear in is REQ-UI-071's. The header MUST carry a **Control Panel** button for `is_admin` users only (REQ-UI-003, REQ-UI-047) and no other administration entry point, and a **Training** link for every signed-in user (REQ-UI-059). |
| REQ-UI-070 | **Project boxes.** The overview presents each project as a box rather than a table row (changing REQ-UI-009's presentation, not what it shows): the boxes form a grid whose columns follow the panel's width, and every box carries the same information — project name, organization where it has one, the three quick statistics, and when the acting user last used the project (REQ-UI-071). **The arrangement follows the shape of the box**: in a wide box the identity reads down one side and the statistics across the other; in a narrow one they stack in that order. A box must not gain or lose information because of its size — only the layout changes — and it stays true when the same project lands in a different-sized box on a narrower screen, including the single-column case a phone gives (REQ-UI-008). The project name is the box's link to the project page (REQ-UI-009); no other part of a box is a control. |
| REQ-UI-071 | **Recently used projects come first and take more space.** The overview orders its boxes by when the acting user last used each project — most recent first, never-used last, and by name within one day — and gives the recently used ones a larger box than older or never-opened projects. Recency is the acting user's own newest audit event in that project, which `GET /api/v1/projects` reports per project as `last_accessed_at` (REQ-API-049): it is the user's history rather than the project's, so two members see their own order and no one sees another member's activity. A project with no event for this account shows a translated "never used" line instead of a date. The ordering is the overview's presentation decision alone: the endpoint returns its list in the same order as before, and no other page inherits it. |
| REQ-UI-073 | **The overview stays current.** While the project overview is visible it MUST re-read its data region (REQ-UI-044) every **2 seconds** and show what changed — a project created or newly visible, one no longer visible, changed counts, a new `last_accessed_at` — together with the heading's project count, without reloading the page. A read that brings the same list MUST leave the page as it is, and a redraw MUST keep the reader's place — what was in view stays in view, the page never returns to the top — and keyboard focus on the project that had it. Refreshing MUST pause while the document is hidden, and a read MUST NOT start before its predecessor has finished. A failed refresh keeps the boxes last read and tries again on the next one. A refresh is the page's timer, not the user: it MUST NOT move the session's idle bound, so an overview left open still ends its session after `SESSION_IDLE_TIMEOUT`, and once a refresh finds the session ended the page MUST go to the login page with the reason (REQ-AUTH-015). |
| REQ-UI-010 | For a member with one or more data access groups, the dashboard MUST show the currently active group and offer a switch to any of the member's assigned groups (self-service, REQ-API-090, REQ-AUTH-046); the switch MUST take effect on the next data page load. |
| REQ-UI-059 | **Training page (`GET /training`).** Every signed-in user MUST reach a **Training** page from the header, beside the Control Panel button (master spec: "linked on the first project selection screen header (next to 'Control Panel')"). It renders in the single-panel shell of REQ-UI-046 and MUST show one Bootstrap card per installed training plan — the plan's picture and a short text. Choosing a card MUST open a modal with the plan's text below a picture gallery that shows the plan's pictures in order, one at a time, with previous/next controls, a position counter and thumbnails (master spec: "similar to Bootstrap Image Gallery"). Each plan's text and pictures MUST live in a sub-directory of its own under `web/assets/training/` (master spec: "stored in individual sub-directories inside assets/ (so they are easy to add/edit)"), so a plan is added or changed by editing files, without a code change; a plan MAY carry its text in further UI languages, falling back to English (REQ-UI-008). Plan text MUST render as text, never as markup (REQ-UI-004). The installation ships example plans for creating a new project, creating data collection forms, collecting data, exporting data and exporting audit trails. |

## 4. Administration Interface (`is_admin` only)

| ID | Requirement |
|---|------|
| REQ-UI-047 | **Control Panel (`GET /admin`).** Every installation-administration function lives on one page — the **Control Panel** — reachable from the header button of REQ-UI-009 and nowhere else (DEV-UI-15). Its left panel lists the sections **Projects** (REQ-UI-012), **Users** (REQ-UI-011), **Audits** (REQ-UI-016), **Translations** (REQ-UI-030), **Settings** (REQ-UI-043), **Monitoring** (REQ-UI-064), **Authentication Test** (REQ-AUTH-085), **Configuration Check** (REQ-UI-061) and **API documentation** (REQ-UI-057); the right-hand panel shows the section selected there (REQ-UI-046). One route serves them all — `GET /admin?section=<name>`, defaulting to the first available section, so the Control Panel opens on **Projects** (master spec: "Make the 'Projects' page the first open tab in the Control Panel") — and its data region is scoped to that section (REQ-UI-044); a `section` value this build does not serve renders the first available one, and a section whose function the acting user may not use is absent from the panel (REQ-UI-003). The whole page is `is_admin`-gated. Project-scoped administration — assignments, roles, data access groups (REQ-UI-013/014/015) — stays on the project page, because its permission is the project's own rather than the installation's. |
| REQ-UI-057 | **API documentation.** The Control Panel's left panel MUST end with **API documentation** (`?section=api`), which renders the OpenAPI document of both API surfaces (REQ-TECH-004, REQ-API-002) in the Control Panel with the vendored Swagger UI bundle — the API's own `/docs` and `/openapi.json` are never routed to a browser (REQ-TECH-018), so this is where an administrator reads them. The document MUST reach the browser as the section's data region (REQ-UI-044), passed on verbatim from `GET /openapi.json`; no proxy route is added and no request leaves the application (ASM-TECH-2). The view MUST be read-only — no "Try it out", no authorization form, no external validator — because the administration API it describes is not reachable from a browser and the data API takes project tokens, not the session. The **Data API** section MUST be listed first and be the only section open when the page loads; every other section MUST start collapsed, keep the document's order, and open on its heading (master spec: "Close all API Documentation drawers but keep the Data API open (and move it to the first position)"). |
| REQ-UI-060 | **Relevance Sankey.** The API documentation section MUST open, above the OpenAPI document, with a Sankey diagram of the code-to-relevance classification (the table of `docs/Requirement_Relevance_Classification.md`, mirrored in `docs/index.md`): the codes are grouped at two levels — functional area first, rendered as one-line descriptions an end user at a hospital recognizes, then code family (`REQ-…`, `ASM-…`, `DEV-…`, and the charter's `BR-…`/`GD-…`) — and every group flows into the relevance classes it serves, one band per code-category pair (vision "Feature: Add a Sankey plot"). The diagram MUST draw with the vendored d3 + d3-sankey libraries (`Design/Technology_Stack_Design.md` §3) from a structure generated into `web/` by `tools/build_relevance_sankey.php` — production deployment carries no `docs/` folder (INSTALL.md §3), and the browser fetches nothing that is not part of the page (ASM-TECH-2). The generated structure MUST be checked against its source document in CI (`ci/run.sh`) so the picture cannot silently drift from the classification, and every visible line MUST be translated server-side (REQ-UI-008). When the generated structure is absent, the section renders without the diagram — reading the OpenAPI document never depends on it. |
| REQ-UI-061 | **Configuration Check.** The Control Panel MUST offer a **Configuration Check** section (`?section=check`), directly before API documentation, that checks the running installation against `INSTALL.md` and reports every finding as one row — a status (OK, Warning, Problem, Info, Not checked), what was checked, the finding with its remedy, and the `INSTALL.md` section that explains the setting (vision "Configuration Check"). It MUST cover the PHP runtime (version, required extensions, the LDAP prerequisites `php-ldap`, `proc_open` and a PHP CLI interpreter, OPcache, request-size and memory limits), the web layer's configuration and files (`APP_ENV`, HTTPS, `WEB_PUBLIC_URL` against the address in use, `.env` mode and `CHANGE_ME` placeholders, the session directory, writable application code, unencrypted sign-in sources, the caller address its rate limiting keys on (REQ-API-125: whether it comes from the connection or a listed proxy, rather than from whatever the browser sent), the API service and its host and the database from the facts of REQ-API-159, and — from the browser, as `INSTALL.md` §13.1's smoke checks do — that `/api/v1/*`, `/docs`, `/openapi.json` and `/healthz` answer 404 from outside, that the vendored assets are served and CLARA's own revalidated, and that HTTPS pages carry HSTS. Hardening that a development checkout lacks by design MUST be rated Info in development and Warning or Problem in production. A summary line MUST count problems and warnings; an API that cannot answer is itself a Problem row rather than an error page. No secret value is ever shown, and the section changes nothing; what cannot be seen from inside the installation (firewall, certificate trust, `mariadb-secure-installation`, backups) is listed for checking by hand. `is_admin` only, like the whole Control Panel. |
| REQ-UI-062 | **Masked token reveal.** The just-issued token of REQ-UI-013 MUST arrive masked (`type="password"`), and the page MUST NOT carry its value until the administrator chooses **Show**; Show first has the view recorded (REQ-AUD-033, REQ-API-160) and only then displays the value, with the copy affordance — a token is never copied unseen. **Hide** masks it again and records nothing; a further Show is a further entry. If the view cannot be recorded the token stays masked. The reveal ends when the administrator leaves or reloads the page, as before (master spec: "Mask the token by default from the user (type="password"). The user might 'show' the token (new button)"). |
| REQ-UI-011 | **User accounts.** A list of accounts (email, display name, enabled, `is_admin`, authentication source — incl. `local`, **last login**, **validity end**, the derived status active / disabled / expired / auto-disabled — GD-19, REQ-AUTH-052/053 — and the **two-factor method** off / totp / email — GD-21, REQ-API-116) and actions to create an account (email + display name, optional validity in days with `0` = indefinite, optional local password), set/extend the validity, set or reset the local password, re-enable a disabled (incl. auto-disabled) one — which MUST restart the inactivity clock — disable one, and **reset two-factor authentication** for an account that lost its device or email access (confirm first; REQ-AUTH-059, REQ-API-116). Auto-disabled accounts MUST be visually distinguishable with the inactivity reason (REQ-AUTH-053). |
| REQ-UI-012 | **Projects.** A project creation form covering the simplified creation fields of REQ-DB-006 (name, organization = main supporting institution, PI name/email, data manager, REK/IRB number, REK start/end dates, start/end dates, participant naming pattern — GD-17; the option flags, end provision, end-user-contract confirmation, and initial-events list are **absent**). The organization select offers the Helse Sør-Øst hospitals by short code with the hospital and its sites as option text, then NAT EU and Other; the participant naming pattern is **not displayed** — it is derived from the project name on create (upper case, spaces to underscores, `_[0-9][0-9][0-9]`) and kept unchanged on edit and a project edit form for the same metadata (REQ-API-050/052). Events are created in the project's Setup page (REQ-UI-018). |
| REQ-UI-013 | **Assignments.** Per project: the member list with role, data access groups, and token state; assign a member choosing a role from the project's actual roles — which MAY be empty — plus "no role" (full permissions, REQ-AUTH-020/022); issue and rotate tokens, displaying the new token exactly once — masked until Show, then with an explicit copy affordance (REQ-API-055, REQ-UI-062); set a member's data access group assignments and active group (REQ-API-089, REQ-AUTH-044). |
| REQ-UI-014 | **Role editor.** Create and edit a role: naming it is how a new one is made (`data-manager`, `data-entry`, `controller` are typical names; the presets MAY be offered as starting points only — REQ-AUTH-020/021), and an existing role's whole permission set is editable in the same form (REQ-API-143). The form carries one section per function group, each introduced by an `<h4>` heading, in this order: **Permissions per instrument and event** — a table of the role's grants, one row per (instrument, event) pair mapped in the arm, with the arms behind tabs and the first arm shown by default (master spec "Arms, events and instruments"). Its column groups are **data access** — radio `no_access` / `read_only` / `view_edit` — and **export** — radio `export_none` / `export_de_identified` / `export_no_identifiers` / `export_full` — followed by two checkbox columns, **delete values** (**delete instrument values**) and **edit surveys** (**edit collected surveys**) (REQ-AUTH-017/069). A row's radios and checkboxes are independent of one another (REQ-AUTH-070); a checkbox on a `no_access` row has no effect and MUST be rendered disabled rather than silently ignored (REQ-UI-003), and an arm tab with no grant of its own shows the arm default each of its rows inherits (REQ-AUTH-069). **Project administration** — the `project_admin` checkbox (GD-2). A further function group joins this screen as another `<h4>` section when it gains a requirement; nothing else may be added to the role. The table renders condensed and responsive (`table-sm`, `User_Interface_Design.md` §1) with both header rows sticky, and offers per-column bulk setting (set all rows of an arm to one level) because a project's pair count is unbounded. |
| REQ-UI-015 | **Data access groups.** Create groups (name, unique per project) and delete them, with a warning that deletion is rejected while records are still assigned (REQ-API-087/088). |
| REQ-UI-016 | **Audit view.** A paginated, read-only table of audit entries with a project filter and the acting-user/target fields (REQ-API-077/078, REQ-AUD-019); a non-administrator sees only entries of their own projects; values MUST be escaped (REQ-UI-004). |
