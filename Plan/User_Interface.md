# User Interface Plan

This document outlines the key views and layout for the clinical study management system, built using JavaScript, HTML, and Bootstrap, and served by the PHP web application. The interface exclusively uses the API to create projects, edit the setup of a project, and to store values into fields for projects.

## Layout (the shells — REQ-UI-046, DEV-UI-14, DEV-UI-18)

A left panel appears only where it switches between sections. The **project overview** (§1) is a single panel below the header; the **project page** (§3), the **Control Panel** (§2) and the **account page** (§1b) each carry their own left panel with the right-hand panel showing the selected entry. One header (brand, project breadcrumb, the **Training** link, the `is_admin` **Control Panel** button, and the **account menu** naming the user, with Account and Sign out) is shared by all; there is no footer. Selecting a panel entry is plain navigation to that route (`Design/User_Interface_Design.md` §2.4).

## Key Views

### 1. Project overview
- Purpose: Start page after login; overview of accessible projects — information, not navigation, so it has **no left sidebar** (REQ-UI-009/046).
- Components: A table with one row per project the user has access to (administrator group or project membership) and quick stats in columns (record, instrument, field counts per project). Selecting a project's **name** opens that project's page (§3), which lands on its first available section. The header shows the **Control Panel** button for `is_admin` users only.
- Not a requirement today: "recent activity" and "notifications". An earlier draft of this plan listed them as dashboard components; nothing in the requirements or design asks for them and no API supplies them, so they are out rather than pending. Re-introducing either needs a `REQ-UI-*` entry first (with an endpoint behind it), not an implementation shortcut.

### 1a. Training
- Purpose: short step-by-step guides to common tasks for every signed-in user, linked in the header beside the Control Panel button (REQ-UI-059).
- Components: one card per training plan (picture + short text); a card opens a modal with the plan's picture gallery (previous/next, counter, thumbnails) above its text. Each plan is a directory under `web/assets/training/` holding `plan.md` (plus optional translations) and its pictures in file-name order, so plans are added and edited as files. Example plans: create a new project, create data collection forms, collect data, export data, export audit trails.

### 1b. Account page
- Purpose: each signed-in user's own settings in one place, reached from the header's account menu (REQ-UI-063, DEV-UI-18).
- Components: a left panel with **Profile** (name and address read-only, language and theme selectors, Sign out — the page opens here), **Project tokens** (one row per project the user is a member of, with the role and the token masked; **Show** has the API record a `token_viewed` audit entry and return the value in one call, then shows it with Copy; **Hide** masks it again; REQ-API-161/162, REQ-AUD-033), **Two-factor authentication**, and **Password** (local accounts only). Sign out is also in the header menu, one click from every page.

### 2. Control Panel (`is_admin`)
- Purpose: Administration for authenticated and authorized (administrator) users, on **one page** reached from the header button — all installation-administration settings live here and nowhere else (REQ-UI-047).
- Components: a left panel with the sections **Projects** (the one the page opens on), **Users**, **Audits**, **Translations**, **Settings**, **Monitoring** (the API's live performance values with vendored-d3 line charts of the configured period — `MONITORING_PERIOD_MINUTES`, ten minutes by default, older timepoints dropped — as observed since the page was opened, and the rate limiter's blocked-IP table — both refreshed once per second while the page is visible, REQ-UI-064; an administrator can also start the background Stress Test, which works on five named test projects — creating the missing ones and adding new records to those a previous run set up — and reports progress without holding the page request open, REQ-UI-068), **Authentication Test** (configured LDAP and OAuth/OIDC connection diagnostics, REQ-AUTH-085), **Configuration Check** (the installation checked against INSTALL.md — PHP runtime, configuration and files, the API and its host, the database, and the web server's routing as the browser sees it, REQ-UI-061, with the API facts of REQ-API-159), **API documentation** (the OpenAPI document of both API surfaces, read-only, Data API listed first and the only section open, REQ-UI-057, opened by the relevance Sankey of REQ-UI-060 — functional areas and code families flowing into relevance classes); the right-hand panel shows the section selected there. Project-scoped administration (assignments, roles, data access groups) belongs to the project page (§3), not to this page.
    - User accounts: Create (enable) and manage normal user accounts; show each account's two-factor method and offer an administrator reset for lost devices (GD-21, REQ-UI-011/039).

#### Login and two-factor (REQ-UI-007/038/039/042)
- The login page leads with the **authentication-source name picker** ("Hospital 1", "Hospital 2", …; skipped when only one name is configured; nothing is preselected and nothing shows below it until a name is chosen — choosing applies at once, so the page requires JavaScript, DEV-UI-13). Under the selected name it shows the provider buttons and/or the email+password form for that name's sources — a credential submit races them in parallel, first "login ok" wins (master spec "Authentication order", REQ-AUTH-063…067). When the account has a second factor configured, a follow-up step asks for the code (authenticator app or delivered by email, with resend and recovery-code entry). No session content is reachable between the steps. With the installation-wide mandate on (`AUTH_REQUIRE_2FA`), accounts without a method are taken through enrollment before login completes.
- The account page's two-factor section (§1b) lets each user enable TOTP (QR + manual key, confirm with one code, recovery codes shown once) or email, and disable it with a current code.
    - Projects: Create new projects (name, organization = main supporting institution, PI name and email, data manager, REK/IRB number, REK start/end dates, start/end dates; the participant naming pattern is not displayed but derived from the project name) and edit project metadata. The option flags, the end provision, the end-user-contract confirmation, and an initial-events list are **absent from the form** (GD-17, REQ-UI-012); creation makes the project with arm 1 only, and events are added afterwards in the project's Setup page.
    - Assignment: Assign users to projects given a role (data-manager, data-entry, controller, or a custom role). Role-less members have full permissions. The new member's token is shown once and masked; **Show** records a `token_viewed` audit entry before the value and its Copy button appear, **Hide** masks it again (REQ-UI-062).
    - Roles: Create and edit roles — naming one creates it; the permission set is a per-arm table of (instrument, event) rows with data access and export radios plus the two right checkboxes, and the project-level rights in sections below (`User_Interface_Design.md` §5.4, REQ-UI-014).

### 3. Project Workspace
- Purpose: Main hub for a specific study, shown when the user selects a project on the project overview. A left panel lists the project's functions and the right-hand panel shows the selected one (REQ-UI-017/046).
- Components:
    - Left panel entries, each present only when permitted: **Overview**, **Setup**, **Design**, **Record Status Dashboard**, **Export**, and for administrators **Members**, **Roles**, **Groups**. Entering the project opens the first available entry after Overview — Setup for a member who may change the setup, otherwise Record Status Dashboard for a member with data access, otherwise Overview.
    - Overview: Number of records, instruments, and fields in the project; the read-only project metadata; the current project mode (development | production | analysis) as a badge. Installation admin users (is_admin) can change the mode; a project's own admin sees the badge only: development to production asks whether previously stored data is kept or deleted; other transitions confirm that all data is kept. The control is offered only while no staging set is open.
    - Staging (production mode): Setup and Design pages show staging controls - start staging, a persistent "changes are staged" banner with commit/discard, and a commit dialog that lists breaking changes (each with its reason) and requires acknowledgement. In development mode setup edits apply directly; in analysis mode they do too, but a breaking change shows the same warning dialog and saves only on confirmation (REQ-UI-037).
    - Sections (presented in the left panel only if the user's role/permission allows them):
        - Setup (permission "project_admin"): Add/rename/remove arms (rename REQ-UI-048) and events, and map instruments to arms and events — the instruments themselves are added and changed on Design (REQ-UI-067); choose the project's record naming mode — Auto-name (numeric ids) or type record_id (REQ-UI-052).
        - Design: Create a new instrument, edit fields in an existing instrument. The instrument list carries the controls that make and change an instrument — **Add**, **Edit** (name, survey flag, instrument branching), **Reorder**, **Remove** — moved here from Setup (REQ-UI-067, DEV-UI-21). Import instruments from REDCap instrument ZIPs or data-dictionary CSVs — several files at once, in file-name order — after a preview that lists renames, skipped `file` fields, the record identifier and any problem by file and row; imported instruments collect no data until they are assigned to an event on Setup (REQ-UI-053). Each instrument of the list has a **Repeating** dropdown with one switch per mapped event: on, the instrument's form can be filled out more than once per record at that event (REQ-UI-054). In an instrument's field list each field has a **Move** button beside Edit and Remove: a dialog picks the target instrument (the current one preselected) and the field to put it in front of, or the end, and moves it there with its values (REQ-UI-056).
        - Record status dashboard: Show the table of records and instruments by event. A repeating instrument's cell shows one dot per instance and **+**, which opens the next instance in the record view; the record view switches between the instances and offers **+** next to the instrument's name (REQ-UI-055).
        - Export: Export project data as CSV or JSON at the acting user's export level, with an arm selector and a visible sensitivity badge (REQ-UI-020). The applied level for a multi-arm export is the **lowest (most protective)** of the selected arms; deselecting an arm raises it for that download (REQ-EXP-003). The page offers a second download next to the data: the project's data dictionary as a REDCap instrument ZIP (`<project>_<date>_<time>.zip` with `instrument.csv`, REDCap headings, instruments named in Form Name), design only and no record values, and importable into another project (REQ-UI-020, REQ-API-153). Installation administrators additionally receive the CDISC ODM project-and-data download (REQ-UI-069, REQ-ODM-005).
        - New Project: the administrator-only Projects section also imports a CDISC ODM XML document as a new project. The page collects the project metadata that overrides document metadata (REQ-UI-069, REQ-ODM-006).

### 4. Instrument Designer
- Purpose: Edit an instrument's data dictionary.
- Components: Select an instrument; edit, add, and change its fields; reorder the fields; field properties (name with a warning after 26 characters, label, type, choices, validation, required, personal-information flag).
- A `transfer` field's instructions are edited as raw text in a textarea mirroring the calculated-field editor; unparseable instructions, unresolved record-transfer targets, or an unresolved project template are rejected on save with the reason shown (REQ-VAL-046/047).
- The instrument list of a project can be reordered; the record field of the first instrument automatically becomes the record_id field for the project.
- A mapping page shows the instrument-by-event mapping (table with checkboxes) for each arm. A single arm is assumed to start with.

### 5. Data Entry Form
- Purpose: Collecting clinical data. In analysis-mode projects the form is read-only (no submit control); the survey page shows a closed state.
- Components:
    - Dynamic rendering of fields (Text, Notes — a text area, REQ-DB-044 — Dropdowns, Radio buttons, Yes/No — two radio buttons labelled in the interface language, REQ-DB-043 — Checkboxes — one box per choice, REQ-DB-042 — Matrix).
    - A `transfer` field renders as a **button**, not an input: pressing it asks for confirmation and reports the target record created or updated, or the project created/already present. The button is absent — never merely disabled — when the user may not edit data, when they lack edit rights on any target pair (checked server-side before render), and on the survey page; no part of the copy instructions is shown to a participant (REQ-UI-065).
    - Real-time validation feedback (client-side JavaScript + HTML5; authoritative validation in the API).
    - A completion control as the always-last field of each instrument's form: set or clear this record/event/instrument's "finished" state, which drives the green marker on the status dashboard (REQ-UI-036). On survey instruments the same trailing field shows the completed state read-only, filled in automatically (GD-9).
    - A **survey link** section on a survey instrument's view, for `view_edit` on the pair: the link's state — never issued / live / submitted on <date> / revoked — with copy while it is live, **get a new link**, and revoke (REQ-UI-028). On a participant not stored yet the same section offers **get link**, which stores the participant first (REQ-UI-051). Re-issue is refused while the instrument still holds values for this record at this event, so the control sits beside the delete action that clears them (`User_Interface_Design.md` §8.7, REQ-API-146). The public page never pre-populates and takes exactly one submission: its closing panel states that the link cannot be used again, and re-opening that link shows an "already submitted" state instead of a form (REQ-API-145).

### 6. Record Status Dashboard
- Purpose: Overview of data completion for a project.
- Components: Lists all record_ids in a project with their instruments sorted by event and ordered based on the order of instruments in each arm. Each instrument is rendered with a small graphic in one of **three** states — grey (no field has a value), amber (some value present), green (the user marked the instrument finished at the end of its form) (REQ-UI-019/036, REQ-API-074/110). Grey and amber are derived from the stored values; only green is stored (or automatic on survey instruments), so the indicator can never claim completion the data contradicts (REQ-API-074, GD-9). The new-participant affordance offers exactly one path per project naming mode — a typed record_id input (`manual`) or a single action that creates the participant under the next generated numeric name (`auto`) — never both (REQ-UI-052).

## UI Framework
- Framework: Bootstrap
- Themes: The page renders with the standard Bootstrap stylesheet or one installed theme file (`darkly`, `yeti`); the installation default comes from configuration (`UI_THEME`), each user may override it beside the language selector, and "Default" returns to the installation theme (GD-26).
- Description: Used for responsive layout and pre-built components (forms, buttons, modals) on plain JavaScript and HTML.
