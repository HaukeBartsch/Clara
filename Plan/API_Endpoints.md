# API Endpoint Documentation Plan

This document outlines the API for the clinical study management system, implemented in Go with Swagger/OpenAPI. In all calls the caller token is passed as the `token` parameter in the request body (REDCap-compatible protocol), not in an Authorization header.

## 1. REDCap-Compatible Data API (external callers, e.g. Fiona)
- Single endpoint: POST /api/ (also GET /api/) with form-encoded parameters.
- Requests are bounded by body size (32 MiB) and by parameter count (250,000); either bound is answered 400 naming the limit, before any token lookup and never as 401. An indexed call carries one parameter per cell, so the count sits above Go's own 10,000-per-string cap and a batch over it moves to the JSON `data` encoding (REQ-API-144, REQ-TECH-011, REQ-API-031).
- Common parameters: token, content, format (json|csv), type (flat|wide), returnFormat.
- Supported content values:
    - project: Return project info (name, description, PI, REK number, start/end dates).
    - metadata: Return the full data dictionary (fields by instrument by project).
    - event: Return the events (event_name, arm_num, unique_event_name, event_id).
    - formEventMapping: Return the instrument-by-event mapping.
    - exportFieldNames: Return the field names of the project.
    - generateNextRecordName: Generate the next record name following the project's participant naming, as one step above the greatest existing name (max + 1); names of deleted records are not reused. While the project is in `auto` naming mode it returns the next plain integer above every numeric record id instead — the first name is `1` (REQ-API-151).
    - record without `data` (export): Export records. Parameters: records[], fields[], forms[], events[], rawOrLabel, rawOrLabelHeaders, exportCheckboxLabel, exportSurveyFields, exportDataAccessGroups, filterLogic, csvDelimiter, decimalCharacter. Whole-instrument exports (full or `forms[]`-filtered) end each instrument's field block with an `<instrument>_complete` column (`0` not complete / `1` in progress / `2` complete, derived like the record-status dashboard); a `fields[]`-filtered export omits it (REQ-API-134). `filterLogic` reads only what the response delivers verbatim: a reference to a value the caller's level withholds or transforms is refused before any record is read, answered like an unparseable expression (REQ-API-025, REQ-EXP-054).
    - record with `data` (import): Store values into fields (data entry), validated against the field rules. The operation is decided by the presence of `data`, not by `action` (REDCap convention, REQ-API-012); deletion stays explicit via `action=delete`. `data` is accepted as indexed `data[i][key]` parameters or as a JSON array of record objects; a row without `form_name` stores each field on its own instrument (REQ-API-031). With `returnContent=count` the response is `{"count": N}` for the rows applied (REQ-API-142). In analysis-mode projects all writes (import, delete, survey submissions) are rejected; reads and exports are unaffected. A row submitted with a survey-link token may name none of its target: the record, instrument and event come from the link, and a row naming a different one is a 403 rather than a retarget (REQ-API-083). A row's event key is accepted as `event_name` or `redcap_event_name` (REQ-API-138); a rejected row's error detail lists its problems in a fixed order (REQ-API-139), and whether one invalid value repeated across rows aggregates is open (REQ-API-140).
- Permissions are enforced per token, **per arm as default and per (instrument, event) pair as override** (GD-2, REQ-AUTH-069): a data access level (`no_access` < `read_only` < `view_edit`) and an export level (`export_none` < `export_de_identified` < `export_no_identifiers` < `export_full`), plus the rights **delete instrument values** and **edit collected surveys**, which no level implies (REQ-AUTH-070). A call that touches several pairs is decided pair by pair: an export delivers the permitted columns and drops the rest, an import decides each row by its own pair, and a deletion needs the right on every pair it clears. The former flat set (view / change / add / export all / export anonymized) is superseded.
- Optional rate limiting applies **per source IP address** (default 600 requests/minute, disabled by default), covering both the data API and the administration surface so web-application traffic and external scripts are limited alike; over the limit answers HTTP 429 with a REDCap-style error and blocks that IP for a configurable period (default 10 minutes) after which its requests are accepted again. The caller IP comes from the reverse proxy's `X-Real-IP` when the direct peer is a trusted proxy, otherwise from the connection (REQ-API-038/111/113).
- The existing Fiona call examples (form body with token=..., content=..., filterLogic=...) must keep working unchanged. They filter on fields they export at `export_full`, so the read bound of REQ-EXP-054 leaves them untouched; a caller filtering on a value its level withholds now gets the 400 rather than results it should not have had.

## 2. Administration API (used exclusively by the web application)
- Authentication: POST /api/v1/auth/login (verify credentials for the OAuth2 callback, an LDAP bind, or a local table-based account — `source: "local"`; optional `source_name` records the user-selected authentication-source name in the audit, REQ-AUTH-067), POST /api/v1/auth/verify-password (side-effect-free hash + account-active check so the sources under a selected name can race in parallel — REQ-API-123), POST /api/v1/auth/logout. The login endpoint **does not create or store a session** (REQ-API-044): it authenticates and returns the identity, and the PHP web application owns the session it establishes from that result (REQ-AUTH-009). The Go API stays stateless. When the account has two-factor authentication enabled (GD-21), login answers `mfa_required` until the call repeats with a valid `mfa_code` (TOTP, email code, or recovery code — REQ-API-114); self-service enrollment lives on `/api/v1/users/me/tfa/*`, administrators reset any account via `POST /api/v1/users/{id}/tfa/reset` (REQ-API-115/116).
- Users: GET /api/v1/users, POST /api/v1/users (create/enable an account), PUT /api/v1/users/{id} (disable/enable, grant/revoke `is_admin` — REQ-API-136; a change that would leave zero enabled administrators is rejected 409, REQ-AUTH-068). Self-service preferences on `/api/v1/users/me/ui-language` and `/api/v1/users/me/ui-theme` (GD-26): the theme value names an installed Bootstrap theme or is `null` to follow the installation default `UI_THEME` (REQ-API-098/122).
- Password lifecycle (GD-22/GD-23): `POST /api/v1/users/{id}/invite` (is_admin — emails a single-use set-password link to a local account, 409 without SMTP) and self-service `PUT /api/v1/users/me/password` (change own password by proving the current one); pre-authentication `POST /api/v1/auth/password-reset/request` (identical response whether or not the account exists — no enumeration), `POST /api/v1/auth/password-reset/complete`, and `POST /api/v1/auth/invite/complete` redeem the hashed single-use tokens (`password_tokens`, REQ-DB-039) and set the password (REQ-API-117…121).
- Projects: GET /api/v1/projects (only accessible projects), POST /api/v1/projects (creates arm 1 together with its initial event `baseline` and one instrument `instrument` — a project always holds at least one arm, event and instrument, REQ-API-050), GET /api/v1/projects/{id}, PUT /api/v1/projects/{id} (metadata and the record naming mode `record_naming` — `auto` | `manual`, project_admin, REQ-API-151).
- Members: GET /api/v1/projects/{id}/users, PUT /api/v1/projects/{id}/users/{uid} (assign a role; issue/rotate the project token), POST /api/v1/projects/{id}/users/{uid}/token-viewed (records that the administrator unmasked the just-issued token — `token_viewed`, no value in or out; REQ-API-160). Self-service for the account page: GET /api/v1/users/me/projects (own memberships with role, no token; REQ-API-161) and POST /api/v1/users/me/projects/{id}/token-reveal (writes `token_viewed` naming the member, then returns their token; REQ-API-162).
- Roles: GET/POST /api/v1/projects/{id}/roles (create custom roles with a mixture of permissions).
- Arms: GET/POST /api/v1/projects/{id}/arms, PUT /api/v1/projects/{id}/arms/order (reorder; ids and arm numbers never change, REQ-API-129), PUT /api/v1/arms/{id} (rename — the label only; id, `arm_num` and events untouched, REQ-API-150), DELETE /api/v1/arms/{id} (permission project_admin; the last remaining arm is renamed to `arm_1` instead of deleted — 200 + object, REQ-API-128).
- Events: GET/POST /api/v1/projects/{id}/events (label, period, safe region), PUT/DELETE /api/v1/events/{id} (the last remaining event is reset to `baseline` with offset day 0 and no safe region instead of deleted — 200 + object, REQ-API-133).
- Instruments: GET/POST /api/v1/projects/{id}/instruments, PUT /api/v1/projects/{id}/instruments/order (reorder the list), PUT /api/v1/projects/{id}/instruments/{iid} (update name — a rename, unique within the project, REQ-API-130 — the survey flag and the branching logic), DELETE /api/v1/projects/{id}/instruments/{iid} (the last remaining instrument only loses its fields and is renamed to `instrument` — 200 + object, REQ-API-127). POST /api/v1/projects/{id}/instruments/import creates instruments and fields from REDCap instrument ZIPs or data-dictionary CSVs in one all-or-nothing call, with a `dry_run` preview; it maps no instrument to an event (REQ-API-152, DEV-API-27). GET /api/v1/projects/{id}/instruments/export answers the project's data dictionary as the same kind of REDCap instrument ZIP, the import's conversion run backwards (REQ-API-153, DEV-API-28).
- Fields (Designer): GET/POST /api/v1/projects/{id}/instruments/{iid}/fields, POST .../fields/bulk (create a batch in one all-or-nothing call — REQ-API-132, DEV-API-20), PUT/DELETE /api/v1/projects/{id}/instruments/{iid}/fields/{fid}, PUT .../fields/order (reorder fields).
- Mapping: GET/PUT /api/v1/projects/{id}/instrument-event-mapping (checkbox table per arm).
- Repeating instruments: PUT /api/v1/projects/{id}/instruments/{iid}/repeating `{"events": [...]}` sets the events a mapped instrument repeats at (the whole set; `[]` turns it off; never a survey or the first instrument); the instrument object lists them as `repeating_events` (REQ-API-154). The data API carries instances in REDCap's shape — `redcap_repeat_instrument`/`redcap_repeat_instance` on import and as instance rows in the flat export, `__<n>` blocks in the wide layout, `repeat_instance` on delete, `content=repeatingFormsEvents`, and the project flag `has_repeating_instruments_or_events` (REQ-API-155). Record status lists a repeating cell's `instances`, completion and history take an `instance` (REQ-API-156).
- Moving a field: POST /api/v1/projects/{id}/instruments/{iid}/fields/{fid}/move `{"instrument_id": …, "before_field_id": …|null}` puts the field before a field of any instrument of the project, its own included, or last; it keeps its id, name and values (what the target does not show stays stored, hidden until the field moves back), the record identifier stays where it is while records exist, staged in production as `field_moved` — never breaking — and audited as `field_moved` (REQ-API-157, REQ-DB-049).
- Transfers: GET /api/v1/projects/{id}/records/{record}/transfers?event=…&instrument=… answers `{field_name, enabled}` for every `transfer` field of that (event, instrument) — `enabled` means the stored instructions parse, their target references resolve against the current design, and the acting user holds the edit rights REQ-API-165 demands — so the data entry form renders each button or leaves it absent in one call; it executes nothing and discloses no target details beyond availability (REQ-API-166). POST /api/v1/projects/{id}/records/{record}/transfers (`event`, `instrument`, `field`) executes one transfer field of the addressed record in **one transaction** (ASM-API-6): resolve the target project by name, require the acting user's data access ≥ `view_edit` on every written target (instrument, event) pair plus target record visibility — a missing or forbidden target answers the uniform 403 that never discloses existence — create the target record when absent (its record name is the `create` operation's source value), then copy each configured value through the target dictionary's validation exactly as an import would. **An empty source value skips its copy and never clears a stored target value**; re-executing updates in place (idempotent — unchanged values produce no audit churn); a failed transfer writes nothing, record creation, value copies, calculated recomputation and both projects' audit entries committing or rolling back together (REQ-API-165). The response reports `{target_project, target_record, created, copied[], skipped_empty[]}`.
- Record Status: GET /api/v1/projects/{id}/record-status (records with instruments by event and a three-state completion state — `no_data` / `some_data` / `finished`; sparse — `no_data` cells are not listed, REQ-API-149). PUT /api/v1/projects/{id}/records/{record}/events/{event}/instruments/{iid}/completion sets or clears the user-assigned `finished` state; it writes no field value (REQ-API-074/110). A survey-marked instrument reports `finished` automatically — its completion is filled in without an assignment, and the PUT stays rejected for surveys (GD-9).
- Survey links: GET /api/v1/projects/{id}/records/{record}/instruments/{iid}/survey-link?event=… reports that pair's link and its state (`none` / `live` / `submitted` / `revoked`) without minting a token; POST … issues one, replacing any live link, and is refused 409 while the instrument still holds values for that record at that event — those go first, which needs the delete right (REQ-API-082/146). DELETE … revokes it (REQ-API-085). All three gate on `view_edit` on the pair plus record visibility. **A link is good for one submission**: the save that stores the submitted row stamps the collection date, and that stamp ends the link — a second call with the same token answers 410, while an unknown or revoked token keeps the uniform 401 (REQ-API-145, REQ-AUTH-039/040).
- Export: GET /api/v1/projects/{id}/export — parameters `format` (csv|json), `arm` (repeatable, restricts the export so a higher per-arm sensitivity stays reachable), `rawOrLabel`, `rawOrLabelHeaders`, `csvDelimiter`, `decimalCharacter`. The applied level is the lowest of the exported arms; unknown parameters are ignored (REQ-API-075, REQ-EXP-003/010/013/015).
- End Provision: POST /api/v1/projects/{id}/end-provision — `is_admin`; body `{ "provision": "delete" | "anonymize" }` executes the project's end provision once (a second execution → 409; the `project_ended` audit event is the idempotency state) and reports the affected record and value counts (BR-009, REQ-EXP-040).
- Audit Log: GET /api/v1/audit (read-only, authorized users only).
- Configuration check: GET /api/v1/system/check — `is_admin`; the installation facts only the API can see (its configuration, root or not, clock sync and SELinux, an unchanged bootstrap password, and the database through its own account: version, character set, time zone, `max_allowed_packet`, bind address, the audit/table grants of REQ-DB-024, audit partitions). Facts, never ratings and never a secret value; the Control Panel's Configuration Check rates them (REQ-API-159, REQ-UI-061).
- Performance metrics: GET /api/v1/system/metrics — `is_admin`; an in-memory snapshot of what the API knows about its own performance: per route pattern and method latency histograms (fixed buckets, p50/p95/p99 estimates), status classes and request/response payload byte totals; per data-API `content` value; per database statement verb count/duration/errors/rows; pool waits and dial counts; process memory and GC stats. Measured in HTTP middlewares and a transparent `database/sql` connector wrapper — never records query text or values, persists nothing, resets on restart (REQ-API-163; vision "Performance metrics as part of api").
- Rate-limit blocks: GET /api/v1/system/blocked-ips — `is_admin`; the live rate-limiter state: every source IP currently in blockout with its expiry, plus the effective enable flag and thresholds. In-memory like the limiter itself — nothing persisted, resets on restart; read-only, not audited; source addresses are personal data shown to administrators only (REQ-API-164).
- Project Modes: GET /api/v1/projects/{id}/mode, PUT /api/v1/projects/{id}/mode (development | production | analysis; permission is_admin, the installation admin rather than the project's own admin; development to production requires an explicit keep-or-delete-data decision; analysis returns directly to development and development does not jump straight to analysis. No mode change is accepted while a staging set is open — commit or discard it first.)
- Staging (production mode, permission project_admin): POST /api/v1/projects/{id}/staging (start a staging set), GET /api/v1/projects/{id}/staging (state and staged changes with breaking/non-breaking classification), POST /api/v1/projects/{id}/staging/commit (activate the whole set; breaking changes must be acknowledged), POST /api/v1/projects/{id}/staging/discard. While a set is open, structure changes apply to the staged design; data collection continues on the active design. In analysis mode structure changes apply immediately but a breaking change must be acknowledged (REQ-API-108/111).
